JavaScript 3: Additional Features

Chapters 8 and 9 gave you the language and the page. This chapter adds the features that real web apps lean on every day: array functions that replace most loops, classes and modules that organize bigger programs, asynchronous code that waits for slow things without freezing the page, the extra powers the browser offers, and data from other people's web services.

Array Functions

In Chapter 8 you processed arrays with for loops: make a counter, check it against length, add one, read array[i]. That works, but most of every loop is bookkeeping, and the one line that matters (what you actually want done to each item) is buried inside it. Arrays have built-in array functions (methods such as filter, map and reduce) that do the bookkeeping for you. You hand them a small function that says what to do with one item, and they call it for every item in turn.

The small function you hand over is a callback, the same idea you met with setTimeout and addEventListener: you do not call it yourself; the array method calls it, once per item, and passes the item in as the first argument. Data from real web services almost always arrives as an array of objects, so this section uses one array of movies all the way through.

Here is the same job done both ways: collect the titles of the animated movies. Read the two versions side by side. The array function version says what you want; the loop says how to walk the array, and the "what" is one line in the middle.

The array functions you will use most

Each method answers a different question about the array. The most important thing to learn about each one is what it gives back, because that decides what you can do next: a new array can be filtered again, but a single number cannot.

Pick a method to see what it does, when you will reach for it, what trips people up, and a commented example.

What it is. array.forEach(callback) calls the callback once for each item, in order, passing (item, index, array). It is a drop-in replacement for a loop whose job is to do something with each item: log it, draw it on the page, send it somewhere.

When you meet it. Whenever the goal is a side effect rather than a result: adding an element to the page for each product (you did exactly this in 9.2), or attaching a listener to each button.

Watch out. forEach always gives back undefined, so const titles = movies.forEach(…) stores nothing useful. If you want a new array, you want map or filter. You also cannot break out of a forEach early; use find, some or a for…of loop for that.

What it is. find walks the array and stops at the first item whose callback returns something truthy, and gives you that item. If nothing passes, you get undefined. findIndex does the same search but gives back the position instead, or -1.

When you meet it. Looking up one record: the product with a given id, the user with a given email, the first movie over two hours. Pair findIndex with splice or index-based updates when you need the position.

Watch out. Always plan for "not found". movies.find(…).title throws TypeError: Cannot read properties of undefined when nothing matched. Check the result first, or use optional chaining: movies.find(…)?.title.

What it is. filter builds a new array containing every item whose callback returns true (or anything truthy). The original array is untouched, and the new one can have anywhere from zero items to all of them.

When you meet it. Search boxes, category buttons, "show only unread", "hide sold-out items". Any time the question is "which ones?", the answer is filter.

Watch out. The callback must return the test. With braces you need the return keyword: (m) => { m.year === 2024 } returns undefined, which is falsy, so filter silently gives you an empty array. Without braces the expression is returned automatically.

What it is. map builds a new array of the same length, where each item is whatever the callback returned for the matching original item. It transforms; it never removes.

When you meet it. Pulling one property out of every object (all the titles), converting units (minutes to hours), and, very often in Chapter 11's React, turning an array of data into an array of page elements.

Watch out. To return an object from an arrow function without return, wrap it in parentheses: (m) => ({ title: m.title }). Without them, the braces are read as the function's body and the result is undefined.

What it is. reduce boils a whole array down to one value. Its callback receives an accumulator (the running result so far) and the current item, and returns the new running result. The second argument to reduce is the accumulator's starting value.

When you meet it. Totals and averages (a shopping cart's price), counting (how many movies per genre), finding a maximum, or building one object out of many items.

Watch out. Always pass the starting value. Without it, reduce uses the first item as the starting accumulator, which is an object here, and [].reduce(fn) on an empty array throws TypeError: Reduce of empty array with no initial value.

What it is. Yes-or-no questions about the whole array. some returns true as soon as one item passes; every returns true only if all of them pass, and stops at the first failure. includes(value) is the simple version for plain values: is this exact value in the array?

When you meet it. Form checks (is every field filled in?), permissions (does the user have some admin role?), enabling a button only when every item in a cart is in stock.

Watch out. On an empty array, every returns true (no item failed) and some returns false. And includes compares with ===, so it cannot find an object that merely looks the same; use some with a property test instead.

What it is. sort reorders an array in place (it changes the original) and returns that same array. You give it a comparator: a function of two items, a and b, that returns a negative number if a should come first, a positive number if b should, and 0 if their order does not matter.

When you meet it. "Sort by price", "newest first", alphabetical lists, leaderboards.

Watch out. With no comparator, sort converts every item to a string and sorts alphabetically, so [10, 9, 1, 100].sort() gives [1, 10, 100, 9]. And because it changes the original array, sorting data that other code is using can cause confusing bugs. Use toSorted (or copy first with [...array].sort()) when you want to keep the original order.

Which one should I pick?
  • "Which ones?" filter. Example: products.filter((p) => p.stock > 0)
  • "Change each one into something else" map. Example: users.map((u) => u.email)
  • "Just one, please" find. Example: users.find((u) => u.id === 7)
  • "Add them all up" reduce. Example: cart.reduce((t, i) => t + i.price, 0)
  • "Is any / is every…?" some / every. Example: fields.every((f) => f.value !== '')
  • "Put them in order" toSorted (or sort on a copy). Example: scores.toSorted((a, b) => b - a)
  • "Do something with each one" forEach. Example: items.forEach((i) => list.append(makeLi(i)))

What an array function does for you

There is no magic inside map. It is an ordinary function that takes your callback as a parameter (a function that takes or returns another function is called a higher-order function) and runs the same loop you would have written. Reading a home-made version once makes every array function easier to predict.

    Sorting: why the comparator matters

    Sorting is the array function that surprises people most. Without a comparator, JavaScript turns every item into text and sorts the text the way a dictionary would, character by character. For words that is often what you want; for numbers it is almost never what you want, because the text "100" starts with "1", which comes before "9".

    A comparator fixes this by answering one question about two items at a time: "which of these two goes first?" The sort calls it many times, with different pairs, until everything is in order.       Prototypes, Classes, and Modules

      In Chapter 8 you wrote objects one at a time with curly braces. That is perfect for one settings object or one user. But a library app has thousands of books, and every book needs the same properties and the same abilities (describe itself, check itself out, work out a late fee). Writing each one by hand would mean copying the same code thousands of times. What you want is a blueprint: describe a book once, then stamp out as many as you need.

      JavaScript has had two ways to write that blueprint. The original way uses constructor functions and prototypes; the modern way uses the class keyword, which is a friendlier way of writing exactly the same thing. You will write classes, but you need to understand prototypes to understand what a class really does, and to make sense of error messages and the DevTools console. The last part of this section, modules, solves the next problem: splitting a growing program into separate files that do not trip over each other.

      Constructor functions and new

      A constructor function is an ordinary function that is meant to be called with the new keyword. By convention its name starts with a capital letter, so readers know to use new. Inside it, this refers to the brand-new object being built, and you attach properties to it.

      The keyword new does four things, every time. Step through them.

      1. A new, empty object { }
      2. Linked to the blueprint's prototype { } — prototype → Book.prototype
      3. Book runs with this = the new object { title: 'Kindred', author: 'Octavia Butler', pages: 264 }
      4. The object is returned const a = { title: 'Kindred', … }

      1. JavaScript creates a fresh, empty object. Nothing in your function has run yet.

      2. It links that object to Book.prototype, an object that every function automatically has. This hidden link is what lets every book share methods (coming up next).

      3. It calls Book with this set to the new object, so this.title = title adds a property to that object, not to any other book.

      4. It gives the finished object back, and you store it in a variable. Forget new and none of this happens: Book(…) runs as a plain function, returns undefined, and this is not a new book.

      Prototypes: where shared methods live

      You could give each book a method by writing this.describe = function () { … } inside the constructor, but then every one of your thousand books would carry its own identical copy of that function. Instead, put the method on Book.prototype once. Every book is linked to that prototype (step 2 above), so every book can use the method, while only one copy exists in memory.

      When you ask an object for a property, JavaScript first looks at the object's own properties. If the property is not there, it follows the hidden link to the object's prototype and looks there; if it is still not found, it follows that object's link, and so on. This series of links is the prototype chain. It ends at Object.prototype, whose own link is null. If the property is nowhere on the chain, the answer is undefined.

      You have been using the chain since Chapter 8 without knowing it. An array has no map property of its own; map lives on Array.prototype, which every array is linked to. That is why every array, even one you just made, already knows map, filter and sort. DevTools shows the link as [[Prototype]] when you expand an object, and older code reaches it with __proto__.

      Classes: the modern blueprint

      The class keyword (added in 2015) lets you write the constructor and the shared methods together in one tidy block. Under the hood nothing changes: a class is a constructor function, and its methods go on its prototype, exactly as above. The syntax is just easier to read and harder to get wrong. For example, calling a class without new is an error instead of a silent bug.

      Pick a feature to see what it is for, when you will use it, the classic mistakes, and a commented example.

      What they are. A getter (get) is a method that you read like a property, without parentheses. Use it for values that are worked out from other properties. A setter (set) runs your code whenever someone assigns to that property, so it can check or convert the value first.

      When you use them. Derived values that must never go out of date (a full name built from first and last, a total built from a list), and guarding values (a rating must be 1 to 5).

      Watch out. A setter must store the value under a different name than itself. set rating(v) { this.rating = v; } calls itself forever and crashes with "Maximum call stack size exceeded". Store it in a private field such as #rating instead.

      What it is. A static method or property belongs to the class itself, not to the objects it makes. You call it on the class name: Book.fromJSON(…), never k.fromJSON(…).

      When you use it. Helpers that create objects in a special way (often called factory methods: build a Book from JSON that came back from a server), and values shared by the whole class, such as a counter of how many objects exist. You already use built-in statics: Array.isArray(), Number.parseFloat() and Object.keys().

      Watch out. Inside a static method, this is the class, not an object, so this.title is undefined there.

      What it is. class Ebook extends Book creates a subclass: every Ebook gets all of Book's methods, plus whatever you add. Inside the subclass's constructor you must call super(…) (the parent's constructor) before you touch this. A subclass can also override a method by defining one with the same name, and call the parent's version with super.methodName().

      When you use it. When one kind of thing is a special case of another: an ebook is a book with a file size, an admin is a user with extra powers. Keep chains short: one or two levels is plenty.

      Watch out. Using this before super() throws "Must call super constructor in derived class before accessing 'this'".

      What it is. A property whose name starts with # can be used only by code written inside the class. Code outside cannot read it, change it or even see it in a loop over the object's keys.

      When you use it. To protect values that must only change in controlled ways. A bank balance should change through deposit() and withdraw(), which can check the amount, never by someone writing account.balance = 1000000.

      Watch out. Private fields must be declared at the top of the class body (#balance = 0;) before you use them. Reading account.#balance from outside is a SyntaxError before your code even starts.

      What it is. Inside a method, this is the object the method was called on. But a regular function passed as a callback (to setTimeout, forEach or addEventListener) gets a different this, chosen by whoever calls it. An arrow function has no this of its own, so it keeps the method's this.

      When you meet it. The moment a class method sets up a timer or a listener. It is one of the most common class bugs.

      Watch out. The fix is almost always "use an arrow function for the callback".

      Class habits that save hours
      • Capitalize class names (ShoppingCart) and always create objects with new.
      • No commas between methods. A class body is not an object literal: describe() { … } checkOut() { … }.
      • Declare before use. Unlike function declarations, classes are not hoisted: new Book() above the class Book line throws a ReferenceError.
      • Arrow functions for callbacks inside methods, so this stays the object.

      Modules: one job per file

      So far every script on a page has shared one big global scope. Load cart.js and wishlist.js with two <script> tags, and if both declare const items, the second file crashes with "Identifier 'items' has already been declared". The order of the tags matters too: a file that uses a function from another file must come after it. In a large app, nobody can keep track of every name in every file.

      ES modules (ES stands for ECMAScript, the standard behind JavaScript) fix this. Each module file has its own scope: nothing inside it is visible to other files unless you export it, and a file that needs something must import it by name, from a specific file. Every dependency is written down at the top of the file, so you can always see where a name came from.

      Modules behave differently from ordinary scripts in a few ways that matter every day. Pick one to see what it means for you.

      What it means. A top-level const, let, function or class in a module belongs to that module only. Two modules can both have a variable called items with no conflict, and nothing lands on window.

      Watch out. Inline onclick="save()" attributes look for a global save, so they cannot see functions inside a module. That is one more reason to use addEventListener (Chapter 9) instead.

      What it means. A <script type="module"> behaves as if it had defer: it downloads in the background and runs after the HTML has been parsed, so your elements already exist. Modules also run in strict mode automatically, which turns several silent mistakes into real errors (for example, assigning to a variable you never declared).

      Watch out. Because modules wait for the HTML, a plain script that tries to use something a module provides may run first and find nothing.

      What it means. However many files import math.js, the browser downloads it once and runs it once. Every importer receives the same exports. A module that holds data (a cart, a settings object) is therefore shared by everything that imports it.

      Watch out. The order is "dependencies first": if main.js imports math.js, then math.js runs completely before the first line of main.js.

      What it means. Browsers load modules with the same safety rules as fetch() (you will meet these rules, called CORS, in 10.5). A page opened straight from your disk has a file:// address, and browsers refuse to load modules from there. You see an error like "Access to script at 'file:///…/main.js' from origin 'null' has been blocked by CORS policy".

      The fix. Serve the folder over http:// with a local server: VS Code's Live Server extension, or npx serve in a terminal. GitHub Pages serves over https://, so modules work there.

      Watch out. Import paths must start with ./, ../ or / and include the .js extension. import { sum } from 'math.js' fails with "Failed to resolve module specifier".

      What it means. Big projects have hundreds of modules plus libraries installed with npm. A bundler such as Vite, webpack or esbuild follows every import, starting from your main file, and combines everything into a few optimized files for the browser. It also lets you write import React from 'react' with no path, because it knows where npm put the package.

      When you meet it. Chapter 11: every React project starts with a bundler, and Chapter 13 uses modules on the server with Node.js.

          Asynchronous Coding with JavaScript

          JavaScript in the browser does one thing at a time. There is a single main thread, and it is shared: the same thread runs your code, draws the page, and responds to clicks and key presses. While your code is running, nothing else on the page can happen. For quick work that is fine. But some jobs are slow: downloading data from a server might take a second, a timer might wait five, reading a large file takes as long as it takes. If your code simply stopped and waited for each one, the whole page would freeze until it finished.

          So slow jobs are handled asynchronously ("not at the same time"). Your code asks the browser to start the slow job, and then carries on immediately. The browser does the waiting on its own, outside your code, and when the job is finished it arranges for a function of yours to run with the result. Code that runs top to bottom, each line finishing before the next starts, is called synchronous. Feel the difference for yourself first.

            The event loop: how one thread juggles everything

            If the main thread only runs one thing at a time, how does a timer's callback or a server's answer ever get its turn? The browser runs a simple, endless routine called the event loop. Learn its four parts and the order of almost any asynchronous code becomes predictable.

Two consequences explain most surprises: a callback never interrupts code that is already running, and promise callbacks always jump ahead of timers.                         Callbacks, and why they get messy

                        The first way JavaScript handled asynchronous work was the plain callback: pass a function, and it is called when the job is done. You already do this with setTimeout and addEventListener. It works well for one step. The trouble starts when each step needs the result of the previous one: get the user, then their orders, then the first order's items. Each step nests inside the last, the code drifts to the right, and every level needs its own error handling. Programmers call this shape callback hell or the "pyramid of doom".

                        Promises were added to the language to flatten that pyramid, and async/await (later in this section) made them read almost like ordinary code. Both are built on the same object, so learn the promise first.

                        Promises

                        A promise is an object that stands in for a value you do not have yet. A function that starts something slow can give you a promise right away; later, the promise settles with the outcome. Every promise is in exactly one of three states, and it can change state only once:

                        pendingwaiting for the result →→ fulfilledhas a value rejectedhas a reason (an error)

                        You never read a promise's value directly. Instead you register callbacks that run once it settles: .then(onFulfilled) receives the value, .catch(onRejected) receives the error, and .finally(onSettled) runs either way. These callbacks always run later, as microtasks, even if the promise has already settled.

                        Pick a part of the promise toolkit to see how it works, when you need it, and the mistakes that trip people up.

                        What it is. .then(fn) registers fn to run with the fulfilled value, and it returns a new promise. Whatever fn returns becomes that new promise's value, which is what makes chaining work. If fn returns another promise, the chain waits for it.

                        When you use it. Any time one step needs the previous step's result.

                        Watch out. Forgetting to return inside a then with braces breaks the chain: the next step receives undefined and does not wait.

                        What it is. .catch(fn) handles a rejection from any earlier step in the chain; a throw inside a then also lands there. After a catch, the chain carries on as fulfilled with whatever the catch returned. .finally(fn) runs after either outcome and receives no value.

                        When you use them. One catch near the end of every chain; finally for clean-up such as hiding a "Loading…" message or re-enabling a button.

                        Watch out. A rejected promise with no catch anywhere shows up in the console as "Uncaught (in promise)". That message means you forgot to handle a failure.

                        What it is. new Promise((resolve, reject) => { … }) creates a promise from scratch. The function you pass runs immediately and receives two functions: call resolve(value) to fulfill the promise, or reject(error) to reject it.

                        When you use it. Rarely, because fetch and most modern APIs already return promises. Its main use is wrapping an old callback-style API, such as setTimeout, so it works with await.

                        Watch out. Only the first call counts: a promise settles once, so later resolve or reject calls are ignored.

                        What it is. Four static methods take an array of promises and return one promise that settles based on all of them. They are summarized in the table below and you can race them in the simulator after it.

                        When you use them. Loading several independent things at once (a profile, notifications and settings) instead of one after another.

                        Watch out. Promise.all is "all or nothing": one failure rejects the whole thing, and you lose the results that did succeed. Use allSettled when partial results are still useful.

                        async and await

                        Promise chains are flatter than callbacks, but they still read differently from normal code. The async and await keywords let you write promise-based code as if it were synchronous. Put async in front of a function, and inside it you may write await in front of any promise. await pauses that function (not the page, not the main thread) until the promise settles, then hands you the fulfilled value, or throws the rejection as an ordinary error that try/catch can handle.

                        Pick a rule to see what it means and the mistake it prevents.

                        What it means. An async function always gives back a promise. If it returns 5, callers get a promise that fulfills with 5; if it throws, they get a rejected promise.

                        Watch out. Logging the call without await shows Promise {<pending>}, not your value. The caller must await it (or use .then).

                        What it means. await is only allowed inside an async function, or at the top level of a module (10.2). Anywhere else it is a SyntaxError.

                        Watch out. A callback is its own function. If you use await inside an arrow function passed to addEventListener, that arrow function needs async too.

                        What it means. array.forEach(async (x) => { await … }) starts every callback and moves on immediately; forEach ignores the promises they return. Code after it runs before any of them have finished.

                        The fix. Use a for…of loop to go one at a time, or map plus Promise.all to go all at once (next topic).

                        What it means. When an awaited promise rejects, await throws its reason right there, as if that line had a throw statement. Without a try/catch, the error rejects the async function's own promise and shows up as "Uncaught (in promise)".

                        Watch out. Wrap the risky awaits, and put clean-up in finally so it runs on both paths.

                        One after another, or all at once?

                        Each await waits for its promise before the next line starts. That is right when step two needs step one's result. But when the requests do not depend on each other, awaiting them one by one wastes time: the total is the sum of the waits. Start them all first and wait for them together with Promise.all, and the total is only the longest wait.

                        Using Browser APIs

                        Everything you have learned about JavaScript so far splits into two parts. The language itself (variables, functions, arrays, classes, promises) is the same everywhere JavaScript runs, including on servers in Chapter 13. The extra abilities that only make sense in a web browser (the DOM, setTimeout, fetch, console) are provided by the browser. Each of these is a browser API, or Web API: a set of objects and functions the browser hands to your code. API stands for application programming interface, a defined way for one piece of software to use another.

                        There are dozens of browser APIs. Some just work. The powerful ones that could expose private information (your location, camera, microphone, notifications) only work on a secure context (a page served over https://, or localhost while you develop), and they ask the visitor for permission first. This section covers the three the textbook highlights, Web Storage, Geolocation and Web Speech, then takes a quick tour of others worth knowing.

                        Web Storage: remembering things between visits

                        Every variable you create disappears when the visitor reloads or closes the page. Web Storage gives each website a small notebook in the browser that survives. It stores key/value pairs, where both the key and the value are strings, and it comes in two flavors with the same methods: localStorage keeps data until it is deleted, and sessionStorage keeps it only until that browser tab is closed. Storage belongs to an origin (one scheme, domain and port), so your site cannot read another site's storage.

                        What they do. setItem(key, value) saves a value under a key (replacing any old value). getItem(key) reads it back, or gives null if nothing is saved under that key.

                        When you use them. Remembering a choice: a theme, a language, the last tab a visitor opened, a draft they have not finished.

                        Watch out. Everything comes back as a string. Save the number 3 and you read back "3", so "3" + 1 is "31". Convert with Number().

                        What it is. Storage only holds strings, so an object or array must be turned into text first with JSON.stringify (Chapter 8), and turned back with JSON.parse when you read it.

                        When you use it. Saving anything with more than one value: settings objects, a list of favorites, a shopping cart.

                        Watch out. Saving an object directly stores the useless text "[object Object]". And JSON.parse throws on broken text (an old format, someone editing it by hand), so wrap it in try/catch and fall back to defaults.

                        What they do. removeItem(key) deletes one key. clear() deletes every key your origin has stored. localStorage.length and localStorage.key(i) let you list what is there.

                        When you use them. A "Reset preferences" button, logging out, removing an item from a saved cart.

                        Watch out. clear() is a sledgehammer: it wipes data that other parts of the same site saved, too. (On this course site, it would erase your progress!) Prefer removeItem with your own keys.

                        What to know. Web Storage is not secret and not secure. Any script running on your page (including a third-party analytics or ad script, or an attacker's script injected by a cross-site scripting bug from 9.2) can read all of it, and anyone using the computer can read it in DevTools under Application → Local Storage.

                        So never store: passwords, credit card numbers, or other personal data. Keep storage for harmless conveniences, and remember the visitor can clear it at any time, so your page must still work when it is empty.

                        Web Speech: reading text aloud

                        The Web Speech API has two halves.                         A quick tour of other browser APIs

                        You do not need to memorize every API. You need to know they exist, so that when a project calls for "copy this link", "load images as they scroll into view" or "draw a chart", you know what to search for. Try four of them live.

                        The Clipboard API copies text for the visitor: "Copy link" buttons, coupon codes, code samples like the ones on this page. Writing needs no permission as long as it happens in response to a click; reading the clipboard does.

                        An IntersectionObserver calls your function when watched elements enter or leave the visible area. It replaces old code that ran on every scroll event, and it powers lazy loading, "infinite scroll" and fade-in effects. Scroll the box.

                        A <canvas> element is a blank grid of pixels, and its 2D context has methods for drawing shapes, lines, text and images. Chart libraries and many browser games are built on it. Drag inside the canvas to draw, or press a button.

                        The Notifications API shows messages outside the page, in the operating system's notification area. Because notifications can be abused, browsers require permission, and most only let you ask in response to a click. Ask once, at a moment when the visitor understands why (after they choose "Remind me"), never as soon as the page loads.

                        Using External APIs

                        Browser APIs live inside the visitor's browser. External APIs (also called web APIs or web services) live on someone else's server, and your page talks to them over HTTP with the fetch you learned in 10.3. Instead of sending back web pages for people to read, they send back data, usually JSON, for your code to use. Weather forecasts, maps, book and movie catalogs, sports scores, transit times, government open data, payment processing, and AI models are all offered this way, and many have free tiers for students.

                        Every external API is a contract written by its owner: "send me a request shaped like this, and I will answer with data shaped like that." The contract is the API's documentation, and learning to read it is the core skill of this section. The rest is knowing the rules every API follows: how requests are addressed, how keys work and how to keep them safe, why the browser sometimes refuses to show you a response (CORS), and how not to get blocked (rate limits).

                        Anatomy of an API request

                        Most public APIs follow a style called REST. Each kind of data is a resource with its own address, called an endpoint, and you choose what to do with the HTTP method: GET to read, POST to create, PUT or PATCH to change, DELETE to remove. (You will build exactly this kind of API yourself in Chapter 13.) The URL of a request has parts that each mean something:

                        https://api.campusdata.example/v1base URL (and API version)/eventsendpoint (the resource)?category=music&limit=3query parameters (options)

                        GET /events/7Get the one event whose id is 7200 OK and an object, or 404 Not Found

                        Challenges

                          API keys: identification, not decoration

                          Many APIs make you sign up and give you an API key: a long, unique string that you send with each request (in the query string or, better, in a header). The key tells the provider who is asking, so it can count your requests, apply your rate limit, and bill you if the plan costs money. Providers usually offer two kinds:

                          • Publishable (public) keys are designed to sit in front-end code. They can only do harmless things and are usually locked to your website's domain in the provider's dashboard. Map and weather widgets often use these.
                          • Secret keys can do anything your account can do: spend money, read private data, delete things. They must never appear in HTML, CSS or front-end JavaScript.
                          Everything you send to the browser is public Any visitor can open View Source or the DevTools Network panel and read every key your JavaScript uses, and bots constantly scan public GitHub repositories for leaked keys, often within minutes. A secret key in a front-end file is a published key. The fix is a small program on your server that holds the secret key and calls the API for you; the browser calls your server instead. That is exactly the kind of program you will write in Chapter 13 with Node.js.

                          CORS: why the browser sometimes hides the answer

                          Browsers follow a security rule called the same-origin policy: JavaScript on a page may freely read responses from its own origin (the same scheme, host and port), but not from other origins. Without that rule, any website you visit could quietly use your logged-in sessions to read your email or your bank balance. CORS (Cross-Origin Resource Sharing) is the way a server opts in: if its response includes an Access-Control-Allow-Origin header that names your origin (or * for everyone), the browser lets your code read it.

                          1. Your page's fetch sends the request. The browser adds an Origin header saying which site is asking. Your code cannot remove or fake it.

                          2. This server answers with Access-Control-Allow-Origin: *, meaning "any site may read this". The browser hands the response to your code.

                          3. A different server answers without that header. Note that the request did reach the server and the server did answer. CORS does not stop requests; it stops your page from reading the answer.

                          4. The browser throws the response away, rejects the fetch promise with a TypeError, and prints the famous CORS error in the console. Your JavaScript cannot fix this; only the server's owner can add the header. (Or your own server can make the request instead, since CORS is a browser rule.)

                          5. Some requests (a DELETE, or a custom header such as an API key header) first trigger a preflight: an automatic OPTIONS request asking "would you accept this?"

                          6. Only if the server says yes does the browser send the real request. You will see these OPTIONS requests in the Network panel and in your server's logs in Chapter 13.

                          Rate limits: be a polite client

                          Providers limit how many requests each key or visitor may make per minute or per day, to keep the service fast for everyone. Go over and you get 429 Too Many Requests, usually with a Retry-After header saying how many seconds to wait. Pages that respect the limits share a few habits:

                          • Do not fetch inside a loop when one request with a filter or a list of ids would do.
                          • Debounce search-as-you-type (the technique from 9.4), so a ten-letter search sends one request, not ten.
                          • Cache answers that do not change often (in a variable, or in sessionStorage), and reuse them instead of asking again.
                          • Handle 429 gracefully: show "Too many requests, try again in 30 seconds" instead of a broken page.

                          Libraries built on APIs: maps and charts

                          Some APIs come with a JavaScript library that does the drawing for you. You load the library's script (and usually its stylesheet), give it an element to draw in, and pass it your data. Two you will meet often: Leaflet draws interactive maps from free OpenStreetMap tiles (Google Maps works similarly but needs a key), and Chart.js turns arrays of numbers into bar, line and pie charts on a <canvas>. Both are third-party scripts, so they need an internet connection, which is why this offline course shows them as code only.
