JavaScript 4: React

In Chapters 8 to 10 you wrote JavaScript that finds elements and changes them one step at a time. That works until an app has dozens of things on screen that all depend on the same data. This chapter shows how front-end frameworks solve that problem, then teaches React, the most widely used one: components, JSX, props, state, forms, the tools that build a React project, the life of a component, and the libraries that extend it.

How the playgrounds run React Every playground in this chapter runs your code with a small built-in copy of React called React lite, so everything works offline with no setup. It understands JSX, function and class components, the common Hooks (useState, useEffect, useRef, useContext and friends) and prints the same warnings real React prints. Real projects install the real React with npm, which you will do in 11.4. The code you write here is the same code you would write there.

JavaScript Front-End Frameworks

Think about a shopping site. The number of items in your cart appears in the header, in the cart list, in the order summary, and on the checkout button. Every time you add, remove or change an item, all four places have to change, and they have to agree. In Chapter 9 you would write that by hand: find each element and update it. Every new feature adds more elements to remember, and forgetting one of them is the most common bug in hand-written front-end code.

A front-end framework (or user-interface library) is a large body of JavaScript, written by someone else, that takes over that job. You describe what the page should look like for any given data, and the framework works out how to change the real page whenever the data changes. The data is called state, and the idea is often written as one short formula: UI = f(state). The user interface is a function of the state.

The problem frameworks solve: keeping the page in sync

    The code that just ran

    That is the whole argument for frameworks in one picture. In the imperative version every action needs to know about every place the data appears. In the declarative version, actions only change data, and one function turns data into page. Adding a fourth place (a checkout button) means changing every action in the first version, and only render() in the second.

    Imperative and declarative code

    Imperative code gives the computer step-by-step instructions: find this element, change its text, add a class. Declarative code describes the result you want and lets something else work out the steps. You already know a declarative language very well: HTML. You write <ul> and three <li> elements, and the browser figures out how to draw them. React brings that style to the parts of a page that change.

    What it is. You hold on to elements and change them one at a time, in the order you choose. It is exactly what the DOM gives you: querySelector, textContent, classList, append.

    When you meet it. In small scripts, in every page from Chapter 9, and inside every framework (the framework itself runs imperative DOM code; it just writes that code for you).

    Watch out. Each event handler must update every element that depends on the data it changed. The code grows with every place the data appears, and a forgotten update leaves the page showing two different answers.

    What it is. You write a function that returns what the page should look like for the current data. When the data changes, React calls the function again and changes only the parts of the real page that are now different.

    When you meet it. In React, Vue, Svelte, Angular and most modern front ends. You will write this style for the rest of the chapter.

    Watch out. You do not touch the DOM yourself any more. If you catch yourself writing document.querySelector inside a React component, there is almost always a React way to do it instead.

    Your turn: draw the page from state, by hand

    Single-page and multi-page applications

    A traditional website is a multi-page application (MPA): every link asks the server for a brand-new HTML page, and the browser throws away the old page (and everything typed into it) before drawing the new one. Most React apps are single-page applications (SPAs): the browser downloads one HTML page and the JavaScript once, and after that, clicking a link only asks the server for data (usually JSON) while JavaScript redraws part of the page and updates the address bar.       The virtual DOM: how React changes only what changed

      If React redraws the page from state every time, is it rebuilding the whole page on every click? No. When a component runs, it does not create real DOM elements. It returns a lightweight description of them, plain JavaScript objects like { type: 'li', props: { children: 'Milk' } }. That tree of descriptions is often called the virtual DOM. React keeps the description from the last time, compares it with the new one (a step called reconciliation, or "diffing"), and then makes only the real DOM changes needed to turn the old page into the new one. Creating objects is cheap; changing the real DOM is the expensive part, so React does as little of that as possible.

        Introducing React
        
    
        React is a JavaScript library for building user interfaces out of components. Engineers at Facebook created it in 2011 to tame the news feed and released it as open source in 2013; today it powers Facebook, Instagram, WhatsApp on the web, Netflix, Airbnb, Discord and a very large share of new web apps. React does one job: given your components and their data, it draws the user interface and keeps it up to date. Routing, data fetching and styling come from other libraries, which you will meet in 11.6.
        
    
        Three ideas carry the whole library, and this section introduces the first two:
        
    
          
      
        1. Components. The page is built from functions that each return a piece of UI. A ProductCard component can be used ten times on one page and in five places in the app.
          2. 
      
        2. JSX. Those functions describe their UI with an HTML-like syntax written right inside JavaScript.
          3. 
      
        3. One-way data flow. Data flows down from parent components to children as props, and changes happen through state (Section 11.3).
          4. 
    
        

    
        Your first React page
        
    
        A React app needs three things: an HTML page with one empty element for React to fill (by convention <div id="root">), the React library itself, and your code. The textbook starts the simplest way, by loading React from a CDN and letting a library called Babel translate JSX in the browser. That setup is fine for learning and terrible for real sites (it is slow and ships a translator to every visitor), which is why 11.4 moves to a proper build tool.
        
    
    
        Two calls do all the work. ReactDOM.createRoot(element) tells React which element it owns; React will manage everything inside it. root.render(something) draws that something into the root, replacing whatever was there (a "Loading…" message, say). In the playgrounds, React and ReactDOM are already loaded for you, so you write only the part inside the text/babel script.

        JSX: HTML-like syntax inside JavaScript
        
    
        JSX (JavaScript XML) lets you write <h1>Hello</h1> where JavaScript expects a value. It is not HTML and it is not a string: before the code runs, a tool (Babel, esbuild, or React lite in these playgrounds) translates every JSX tag into a call to React.createElement(), which returns one of those lightweight description objects from 11.1. That is why JSX can be stored in variables, returned from functions and put inside arrays, like any other value.
        
    
    
    
        Because JSX turns into JavaScript, a few rules differ from HTML. Most of them come from one fact: attribute names become JavaScript property names.

        What it is. Curly braces switch from markup back to JavaScript. Anything that produces a value can go inside: a variable, price * 1.07, user.name.toUpperCase(), a ternary, or a function call.
        
        
        When you meet it. In every component: text that changes, attribute values that change (src={photo.url}), and lists (next section).
        
        
        Watch out. Statements are not expressions. You cannot put if or for inside braces; use a ternary or map instead. And quotes make a fixed string: src="photo.url" is the text "photo.url", while src={photo.url} is the variable's value.
        
        
      
        
      
        
        
        What it is. className sets the HTML class attribute. style takes a JavaScript object whose keys are CSS properties in camelCase (backgroundColor, fontSize). A number for a length means pixels.
        
        
        When you meet it. className constantly, often computed: className={done ? 'task done' : 'task'}. Inline style mainly for values that are truly dynamic, like a progress bar's width.
        
        
        Watch out. style={{ … }} has two pairs of braces: the outer pair says "JavaScript here", the inner pair is the object. Writing style="color: red" is an error in React.
        
        
      
        
      
        
        
        What it is. A JSX expression must have one outer element, because it becomes one createElement call. When you do not want an extra <div> in the page, wrap siblings in a fragment, <> … </>, which groups them without adding anything to the DOM.
        
        
        When you meet it. Components that return a heading and a paragraph, table rows that must stay direct children of <tbody>, or list items inside a <ul>.
        
        
        Watch out. If you need a key on a fragment (in a list), use the long form <React.Fragment key={id}>; the short form takes no attributes.
        
        
      
        
      
        
        
        What it is. Every element must be closed, so empty elements end with />. Attribute values are either a string in quotes or an expression in braces. An attribute written with no value means true.
        
        
        When you meet it. Images, inputs and line breaks: <img src={url} alt="" />, <input disabled />.
        
        
        Watch out. <input> without the slash is a syntax error in JSX (the translator thinks everything after it is inside the input). React lite reports it as "Unterminated JSX contents".

        Components
        
    
        A component is a JavaScript function that returns JSX. Once it exists, you use it like a new HTML tag: <ProductCard />. React calls your function and puts whatever it returns into the page. Components can use other components, so an app becomes a tree: App at the top, made of Header, ProductList and Footer, and ProductList made of several ProductCards. It is the same parent, child and sibling family you met in the DOM, one level up.
        
    
        
      
        
        
        What it is. A function whose name starts with a capital letter and which returns JSX (or null to show nothing). Use it as <Name />.
        
        
        When you meet it. Every piece of a React app is a component, from a single button to the whole App.
        
        
        Watch out. The capital letter is required. JSX treats lowercase tags (<header>) as HTML elements and capitalized ones (<Header>) as components. A component named header would silently produce an empty HTML <header> tag.
        
        
      
        
      
        
        
        What it is. The same component written as an arrow function stored in a const. Both styles are equally common; pick one and be consistent.
        
        
        When you meet it. In many tutorials and codebases, often for small components.
        
        
        Watch out. A const component must be defined before the line that renders it runs, while a function declaration is hoisted (Chapter 8).
        
        
      
        
      
        
        
        What it is. React may call your component function many times: on every update, and sometimes twice while developing. A component should behave like a math function: the same inputs (props and state) always give the same JSX, and calling it changes nothing outside.
        
        
        When you meet it. When something "happens twice" or "happens on every keystroke": a console.log, a network request or a counter in the body of a component runs on every render.
        
        
        Watch out. Side effects (fetching data, timers, changing document.title) belong in event handlers or in useEffect (11.5), never directly in the component body.

        Rendering lists
        
    
        Real data comes in arrays, and JSX has no loop syntax. Instead you use the array method you learned in Chapter 8: map() turns an array of data into an array of JSX elements, and React draws an array of elements one after another. This is the React version of the "render a list from an array" exercise in Chapter 9, with no createElement or append in sight.
        
    
    
        Notice the key attribute. Every element in a list needs a key: a string or number that identifies that item among its siblings and stays the same as the list changes. React uses keys to match old and new items when the list updates. Without them (or with the array index as the key) React matches items by position, and if you insert an item at the top, every row "becomes" the row below it. For plain text that is invisible. For anything that keeps its own state, like a text box or a checkbox, it puts data on the wrong row.

          Conditional rendering
          
    
          Showing something only sometimes is the other everyday job. There is no v-if or *ngIf in React: you use plain JavaScript.
          
    
          
      
          
        
          What it is. An ordinary if statement in the component body, before the return. Returning null shows nothing at all.
          
        
          When you meet it. When a whole component looks different in some state: loading, empty, an error, or a user who is not logged in.
          
        
          Watch out. Keep the branches readable; if each branch is big, make each one its own component.
          
        
      
          
      
          
        
          What it is. condition ? a : b inside braces picks between two pieces of JSX (or two strings) in the middle of the markup.
          
        
          When you meet it. Toggles: "Log in" or "Log out", "Show more" or "Show less", a class name that depends on state.
          
        
          Watch out. Nested ternaries quickly become unreadable. Two levels is the limit; after that, use an if or a small component.
          
        
      
          
      
          
        
          What it is. condition && <JSX /> shows the JSX when the condition is true and nothing when it is false, because React draws nothing for false, null and undefined.
          
        
          When you meet it. Badges, warnings and optional extras: {isNew && <span>New</span>}.
          
        
          Watch out. React does draw the number 0. {items.length && <List />} shows a stray "0" when the array is empty. Compare explicitly: {items.length > 0 && <List />}.

          Props, State, Behavior, and Forms
          
    
          A component that always shows the same thing is not much use. Components become useful when they can show different data and react to the user. React gives every component two kinds of data, and telling them apart is the most important skill in this chapter:
          
    
          
      
          
        
          Props: data passed in
          
        
          Like the arguments to a function, or the attributes on an HTML tag. The parent decides them; the component only reads them. <ProductCard name="Hoodie" price={39.99} />
          
      
          
      
          
        
          State: data the component remembers
          
        
          Like a component's private memory. It changes over time, usually because the user did something, and every change makes React draw the component again. const [count, setCount] = useState(0)
          
      
          
    
          

    
          Props: passing data into a component
          
    
          When you write <ProductCard name="Hoodie" price={39.99} onSale />, React collects the attributes into one object, { name: 'Hoodie', price: 39.99, onSale: true }, and passes it to your function as its first argument. By convention that argument is called props (short for properties). The same component can be used many times with different props, exactly like calling one function with different arguments.
          
    
          
      
          
        
          What it is. Attributes on a component tag become properties of the props object. Strings go in quotes; everything else (numbers, booleans, arrays, objects, functions) goes in braces.
          
        
          When you meet it. Every time a parent hands data to a child: a product to a card, a user to an avatar, a label to a button.
          
        
          Watch out. price="39.99" passes the string "39.99"; price={39.99} passes the number. Math on a string prop gives surprising results (Chapter 8's type coercion).
          
        
      
          
      
          
        
          What it is. Most React code unpacks props right in the parameter list with object destructuring (Chapter 10), and gives optional props a default value with =.
          
        
          When you meet it. In nearly every modern component. It documents, at the top of the function, exactly which props the component expects.
          
        
          Watch out. Destructuring needs the braces: function Card({ name }), not function Card(name) (that would make name the whole props object).
          
        
      
          
      
          
        
          What it is. Whatever you put between a component's opening and closing tags arrives as a special prop called children. The component decides where to draw it.
          
        
          When you meet it. Wrapper components: cards, panels, modals, layouts. They provide the frame; the parent provides the content.
          
        
          Watch out. If a wrapper forgets to draw {children}, whatever you put inside it simply disappears.
          
        
      
          
      
          
        
          What it is. A component must never change its own props. They belong to the parent; changing them inside the child would make the page disagree with the parent's data.
          
        
          When you meet it. When you are tempted to write props.count = props.count + 1. That is the moment you need state instead (next).
          
        
          Watch out. If a child needs to change data, the parent passes down a function as a prop, and the child calls it. You will do exactly that in "Lifting state up".

          State: data that changes
          
    
          Props come from outside. When a component needs to remember something that changes, such as how many times a button was clicked, what is typed in a box, or whether a menu is open, it uses state. In function components you create state with the useState Hook. (A Hook is a special React function whose name starts with use; it lets a component "hook into" a React feature.)
          
    
    
          Why not just use a normal variable? Because React does not watch your variables. Calling the set function does two things a normal assignment cannot: it stores the new value somewhere React keeps it between renders, and it tells React to call your component again. Compare the two counters below, both drawn by React lite.
          
    
          
      
          
        
          
          let count = 0; count = count + 1
          
          
        
          
        
          
          const [count, setCount] = useState(0)
          
          
        
          
      
          
      What happened
      
            
    
            
    
            The left counter's variable really does go up (the log proves it), but the page never changes, because nothing told React to redraw. And if anything else did make the component redraw, let count = 0 would run again and start from zero. State survives between renders; local variables do not.
            

    
            Updating state correctly
            
    
            Two rules cover almost every state bug you will write.
            
    
            Rule 1: the value you read is a snapshot. Inside one render, count is a constant. Calling setCount(count + 1) does not change count on the next line; it schedules a new render in which count will be one more. So calling it three times in a row only adds one. When the new value depends on the old one, pass an updater function instead: setCount(c => c + 1). React runs updater functions in order, each with the latest value.
            
    
            
      
            
        
        
        
      
            
      
            
        
            
        
            
      
            
      
            
    
            
    
            Rule 2: never change state objects or arrays in place. React decides whether to redraw by comparing the old value with the new one using Object.is (the same idea as ===). If you push onto the array in state and pass the same array back, React sees the same array and does nothing. Always create a new array or object, usually with the spread syntax ... from Chapter 10, or with map and filter, which return new arrays.

              Several pieces of state are fine Call useState once for each independent value: const [name, setName] = useState(''), then const [age, setAge] = useState(0). Group values into one object only when they always change together. And never call a Hook inside an if, a loop or a nested function: React matches state to Hooks by the order they are called, so the order must be the same on every render.
              

    
              Behavior: handling events
              
    
              React events look like the inline HTML attributes from Chapter 9, but they take a function, not a string of code, and their names are camelCase: onClick, onChange, onSubmit, onKeyDown, onMouseEnter, onFocus. React attaches the real listeners for you, so you never call addEventListener in a component. The handler receives an event object with the same properties you used in Chapter 9: event.target, event.key, event.preventDefault().
              
    
              
      
              
        
              What it is. Define a function (usually inside the component, so it can see props and state) and pass it by name: onClick={handleClick}.
              
        
              When you meet it. Handlers that do more than one line of work. The usual naming convention is handle + event: handleClick, handleSubmit.
              
        
              Watch out. onClick={handleClick()}, with parentheses, calls the function during rendering and passes its return value. If the function sets state, that causes another render, which calls it again: React stops with "Too many re-renders".
              
        
      
              
      
              
        
              What it is. To pass something to the handler (which item was clicked), wrap the call in an arrow function: onClick={() => remove(item.id)}. The arrow is created now; the call happens on click.
              
        
              When you meet it. In lists, where every row's button must say which row it belongs to.
              
        
              Watch out. The arrow is what makes the difference. onClick={remove(item.id)} runs remove for every row the moment the list is drawn.
              
        
      
              
      
              
        
              What it is. React passes an event object to every handler. It wraps the browser's event and works the same way: target, currentTarget, key, preventDefault(), stopPropagation().
              
        
              When you meet it. Reading what was typed (event.target.value), checking which key was pressed, and stopping a form from reloading the page.
              
        
              Watch out. Returning false from a handler does nothing in React. Call event.preventDefault() explicitly.

              Lifting state up
              
    
              Sometimes two components need the same data. A search box and a results list, for example: the results depend on what is typed in the box. If the box keeps the text in its own state, the list can never see it, because data flows only down the tree. The fix is to lift the state up to their closest common parent. The parent owns the state, passes the value down to both children as props, and passes a function down to the child that changes it. Step through the diagram.
              
    
              
      
              
        
      
              
      
                
        
              1. The problem: SearchBox keeps query in its own state. ResultsList is its sibling, not its child, so it has no way to read that state.
                2. 
        
              2. Move the state to the closest common parent, App: const [query, setQuery] = useState(''). Remove it from SearchBox.
                3. 
        
              3. App passes data down as props: the value to both children (query={query}), and a function to the child that changes it (onQueryChange={setQuery}).
                4. 
        
              4. When the user types, SearchBox calls onQueryChange(event.target.value). The data travels up through a function call, not through a prop.
                5. 
        
              5. App's state changes, so React redraws App and both children with the new query. One source of truth, and both views always agree.
                6. 
      
              
    
              
    

    
              Forms: controlled components
              
    
              In Chapter 9 you read a form's values when it was submitted. React apps usually go one step further: each input's value lives in state, and the input shows whatever the state says. Typing calls onChange, which updates the state, which redraws the input with the new value. An input wired this way is a controlled component: React state is the single source of truth, so you always know the current value, and you can validate, format or limit it as the user types.
              
    
    
              React's onChange is not the HTML change event In plain HTML, change fires when a text box loses focus. React's onChange fires on every keystroke, like the input event from Chapter 9. That is why a controlled input works: state updates as fast as the user types.
              
    
              
      
              
        
              What it is. value={state} plus onChange that calls the setter with event.target.value. A <textarea> works exactly the same way in React (it takes a value, not children).
              
        
              When you meet it. Every text field you want to read, validate or reset.
              
        
              Watch out. Start the state with '', not undefined. An input whose value goes from undefined to a string switches from uncontrolled to controlled, and React warns about it.
              
        
      
              
      
              
        
              What it is. A <select> takes value on the select itself (not selected on an option). A checkbox uses checked and reads event.target.checked, a boolean.
              
        
              When you meet it. Dropdowns, settings, filters and "I agree" boxes.
              
        
              Watch out. For a checkbox, event.target.value is the text "on", not true or false. Use .checked.
              
        
      
              
      
              
        
              What it is. Keep a whole form in one state object, give every input a name that matches a key, and use one handler that copies the object and replaces the field named by event.target.name.
              
        
              When you meet it. Sign-up, checkout and settings forms with many fields.
              
        
              Watch out. Copy first with ...form; [name]: value in square brackets uses the variable's value as the key (a computed property name).

                Node.js and npm
                
    
                Every one of those tools is a JavaScript program, and they run on your computer, not in a browser. That is the job of Node.js, which runs JavaScript outside the browser (you will build servers with it in Chapter 13). Installing Node also installs npm, the Node Package Manager. npm downloads packages (libraries and tools other people publish, like React and Vite) from the public npm registry into your project, and runs the project's scripts. You talk to both through a terminal (Terminal on macOS, PowerShell or Windows Terminal on Windows, or the terminal panel built into VS Code).
                
    
    
                Each project describes itself in a file called package.json: its name, the packages it needs, and short names for the commands you run. npm reads it, and so does every other tool.
                
    
    
                
      
                
        
                What it is. Named shortcuts for commands. npm run dev runs whatever "dev" says (here, vite). It saves everyone on the team from remembering long commands.
                
        
                When you meet it. Every day: npm run dev to work, npm run build to make the production files, npm test to run tests.
                
        
                Watch out. Run npm commands from the folder that contains package.json. In any other folder, npm cannot find the scripts and says "Missing script" or "Could not read package.json".
                
      
                
      
                
        
                What it is. dependencies are packages your app needs in the browser (React, ReactDOM, a router). devDependencies are tools you need only while building (Vite, a linter, a test runner).
                
        
                When you meet it. When installing: npm install react-router-dom adds to dependencies; npm install -D vitest adds to devDependencies.
                
        
                Watch out. Nothing in devDependencies ends up in the files your visitors download. Putting a build tool in dependencies does not break anything, but it misleads the next developer.
                
      
                
      
                
        
                What it is. Versions use semantic versioning, MAJOR.MINOR.PATCH: a major bump may break your code, a minor one adds features, a patch fixes bugs. ^18.3.1 means "18.3.1 or any newer 18.x", and ~18.3.1 means "any newer 18.3.x".
                
        
                When you meet it. Every time you install or update a package.
                
        
                Watch out. The exact versions actually installed are recorded in package-lock.json. Commit it to Git, so everyone on the team (and the server) installs exactly the same versions.
                
      
                
      
                
        
                What it is. The folder where npm puts every package you installed, plus every package those packages need. A new React project easily holds 10,000 files there.
                
        
                When you meet it. After npm install. Your code imports from it by package name: import { useState } from 'react'.
                
        
                Watch out. Never commit node_modules to Git, and never edit files in it. Add it to .gitignore; anyone can recreate it exactly from package.json and the lock file with npm install.

                    When you meet it. The usual way to share one component per file: ProductCard.jsx exports ProductCard.

                    What it is. The build tool also understands imports of non-JavaScript files. Importing a CSS file adds it to the page; importing an image gives you its final URL as a string.
                    
        
                    When you meet it. In App.jsx (import './App.css') and wherever you show a picture that lives in src/assets.
                    
        
                    Watch out. A plain CSS import is global: a .card rule in one file styles every .card in the app. 11.6 shows ways to scope styles.

                    React Lifecycle
                    
    
                    Every component on the page has a life story with three chapters. It mounts: React calls it for the first time and puts its elements into the page. It updates, any number of times: its state or props change, React calls it again and patches the page. Finally it unmounts: it is no longer part of the tree (the user closed the dialog, or moved to another page), and React removes its elements. Together these phases are the component lifecycle.
                    
    
                    Most of the time you do not think about any of this: you describe the UI, and React handles mounting and updating. But some work has to happen at a particular moment in that life: start a timer when a clock appears and stop it when it disappears, fetch a user's data when the profile page appears, or update the browser tab's title when the unread count changes. That work is called a side effect, because it reaches outside the component, and React gives you one tool for it: useEffect.
                    

    
                    
      
                    
        
                    
          
                    Mountfirst appearance
                    
          →
          
                    Updatestate or props changed
                    
          →
          
                    Unmountremoved from the tree
                    
        
                    
        
                    
          Render
                    React calls your function                    →
          Commit
                    React changes the DOM                    →

                    your useEffect code runs                    →

                    1. Mount, render phase. React calls your component function for the first time. It only describes the UI; nothing is on the screen yet, so this is the wrong place to touch the DOM or start a timer.
                      2. 
        
                    2. Mount, commit phase. React inserts the real DOM elements into the page. Now they exist, and the browser can paint them.
                      3. 
        
                    3. Mount, effects. After the commit, React runs the component's effects. This is where you start a timer, fetch data or subscribe to something.
                      4. 
        
                    4. Update. State or props change, so React renders again and commits only the differences, exactly as you saw in 11.1.
                      5. 
        
                    5. Update, effects. If an effect's dependencies changed, React first runs that effect's cleanup from last time, then runs the effect again with the new values.
                      6. 
        
                    6. Unmount. The component leaves the tree. React runs every cleanup one last time and removes its DOM. A timer that was never cleared would keep running forever, updating a component that no longer exists.
                      7.

                      What it is. An empty dependency array means "this effect depends on nothing that changes", so it runs once after the component first appears.
                      
        
                      When you meet it. Setting up something for the lifetime of the component: a timer, a window listener, a connection.
                      
        
                      Watch out. If the setup uses a prop or state value, that value belongs in the array. Leave it out and the effect keeps using the value from the first render forever (a "stale" value).
                      
        
      
                      
      
                      
        
                      What it is. List the values the effect reads. React compares each one with its value from the last render and re-runs the effect only if something changed.
                      
        
                      When you meet it. Loading data for whatever the user selected: a different user id, a different search term, a different page.
                      
        
                      Watch out. A new object or array created during render is "different" every time (Object.is again), so an effect that depends on one runs after every render.
                      
        
      
                      
      
                      
        
                      What it is. A function returned from the setup. React calls it before running the effect again and when the component unmounts, so you can undo whatever the setup did.
                      
        
                      When you meet it. Every effect that starts something that keeps going: setInterval, addEventListener, a WebSocket (Chapter 13), a subscription.
                      
        
                      Watch out. A missing cleanup is a memory leak: open and close a page with a timer ten times and ten timers are running. In development, React's StrictMode deliberately runs every effect setup, cleanup, setup on mount, to expose missing cleanups early. If you see an effect run twice in development, that is why.
                      
        
      
                      
      
                      
        
                      What it is. Start a request in an effect, keep the result in state, and show a loading message until it arrives (the fetch and promises from Chapter 10). The cleanup sets a flag so a slow, outdated response is ignored.
                      
        
                      When you meet it. Any component that shows data from a server.
                      
        
                      Watch out. The setup function itself must not be async (an async function returns a promise, and React expects a cleanup function or nothing). Define an async function inside the effect and call it.
                      
        
      
                      
    
                      
    
                      You might not need an effect Effects are for talking to the world outside React. If you only need to compute a value from props or state (a total, a filtered list, a full name), compute it during render: const total = items.reduce(…). Copying it into state with an effect means an extra render and a moment when the two disagree.

                      Refs: when you really do need the DOM
                      
    
                      React draws the DOM for you, so most components never touch it. A few jobs still need the real element: moving keyboard focus into a box, measuring an element's size, scrolling to it, or handing it to a non-React library such as a map or a chart. For those, useRef gives you a box whose .current property survives every render. Put ref={myRef} on an element, and after the commit React stores that DOM element in myRef.current.
                      
    
                      
      
                      
        
                      What it is. const inputRef = useRef(null), then <input ref={inputRef} />. After the commit, inputRef.current is the real <input> element, with every DOM method from Chapter 9.
                      
        
                      When you meet it. A search box that should be ready to type in, or a dialog that moves focus to its first field when it opens.
                      
        
                      Watch out. During render, ref.current is still null on the first render: the element does not exist yet. Read refs in effects and event handlers, which run after the commit.
                      
        
      
                      
      
                      
        
                      What it is. A ref can hold any value, not just an element. Changing ref.current does not cause a render, which makes refs the right home for things the page does not show, such as a timer id.
                      
        
                      When you meet it. Storing an interval id so a Stop button can clear it, or counting something for debugging.
                      
        
                      Watch out. If the value appears on the page, it belongs in state. A ref change will not update the screen.

The checks count the timers that are actually running, so a missing cleanup will show up.

                      Extending React
                      
    
                      React itself only draws components and manages their state. A real app also needs pages with their own URLs, data shared across the whole app, styles that do not leak, forms, tests, and a fast first page load. React leaves those to an ecosystem of libraries and frameworks built around it. This section tours the most important ones, so you recognize them on a job listing and know which problem each one solves.
                      

    
                      Routing: several pages in one single-page app
                      
    
                      A single-page app still needs "pages": a home page, a course list, a page for each course, each with its own address that can be bookmarked and shared, and a working Back button. A router maps the URL to the component to show. When the user clicks a link, the router changes the address with the browser's History API (history.pushState) instead of loading a new page, then draws the matching component. The most widely used router is React Router.

                        Sharing data: prop drilling and Context
                        
    
                        Data in React flows down through props, one level at a time. That is clear and predictable, but when a value is needed deep in the tree (the current theme, the logged-in user, the language), every component in between must accept it and pass it on, even the ones that never use it. That chore is called prop drilling. React's built-in answer is Context: a component high in the tree provides a value, and any component below it can read it directly with useContext, however deep it is.

                        What it is. createContext(defaultValue) makes a context object, usually in its own file so any component can import it. The default is used only by components with no provider above them.
                        
        
                        When you meet it. For values that many components at different depths need: theme, signed-in user, language, a shopping cart.
                        
        
                        Watch out. Context is not a replacement for all props. For a value only one or two levels down, passing a prop is simpler and easier to follow.
                        
        
      
                        
      
                        
        
                        What it is. Wrap part of the tree in <ThemeContext.Provider value={…}>. Every component inside can read that value. Put state in the value, and every reader redraws when it changes.
                        
        
                        When you meet it. Near the top of the app, often in App or main.jsx. (React 19 also lets you write <ThemeContext value={…}> without .Provider.)
                        
        
                        Watch out. To let readers change the value, put a function in the value too: value={{ theme, toggleTheme }}.
                        
        
      
                        
      
                        
        
                        What it is. useContext(ThemeContext) returns the value of the nearest provider above the component.
                        
        
                        When you meet it. In the components that actually use the value, however deep they are.
                        
        
                        Watch out. Pass the context object itself (useContext(ThemeContext)), not the provider or the value.

                        State management libraries
                        
    
                        As an app grows, more state is shared between distant components: a cart, a signed-in user, notifications. Context can carry it, but large apps often reach for a state management library that keeps shared state in one store outside the component tree, with clear rules for changing it. Many of them build on one idea that React also ships: a reducer, a pure function that takes the current state and an action describing what happened, and returns the next state.
                        
    
                        
      
                        
        
                        What it is. A Hook like useState, but all the ways the state can change live in one reducer function. Components dispatch actions (plain objects with a type) instead of computing new state themselves.
                        
        
                        When you meet it. Components whose state changes in many different ways (a cart: add, remove, change quantity, clear).
                        
        
                        Watch out. A reducer must be pure: return a new state object, never change the old one, and never fetch or log inside it.
                        
        
      
                        
      
                        
        
                        What it is. Redux (2015) is the best-known store: one store for the whole app, changed only by dispatching actions to reducers. Redux Toolkit is the modern, much shorter way to write it.
                        
        
                        When you meet it. Large and older codebases, and teams that want strict, traceable state changes (Redux DevTools can replay every action).
                        
        
                        Watch out. It adds concepts and files. Many apps that used Redux in 2018 would use Context, a lighter store, or a data-fetching library today.
                        
        
      
                        
      
                        
        
                        What it is. A small store library: you create a store with a function and read it with a Hook. No providers and very little code.
                        
        
                        When you meet it. Newer apps that want shared state without Redux's ceremony.
                        
        
                        Watch out. Pick the slice of state each component needs (useCart((s) => s.items)) so it redraws only when that slice changes.
                        
        
      
                        
    
                        

    
                        Your turn: a cart with useReducer
                        
    
                        The buttons already dispatch actions. Your job is the reducer: a pure function that takes the current cart and one action, and returns the next cart without changing the old one. Adding a product that is already in the cart raises its quantity instead of adding a second line.

                        Testing React components
                        
    
                        Professional React code comes with automated tests: small programs that render a component, act like a user, and check the result, so a later change cannot silently break it. The usual pair is a test runner (Vitest or Jest) plus React Testing Library, which finds elements the way a user would: by their role and visible text.
                        
    
    
                        The playground checks in this chapter work exactly like this: they click and type in your component, then look at the page.
                        

    
                        React Developer Tools Install the free React Developer Tools extension for Chrome, Firefox or Edge. It adds two DevTools tabs: Components shows the live component tree (like the explorer in 11.2) with every component's props, state and Hooks, which you can edit to test ideas; Profiler records which components rendered and how long each took. It is the first place to look when a component shows the wrong thing.
                        

    
                        Meta-frameworks: React plus a server
                        
    
                        Remember the SPA drawback from 11.1: until the JavaScript loads, the page is an empty <div id="root">, which is slow on phones and invisible to some search engines. Meta-frameworks are frameworks built on top of React that add a server. They run your components on the server to send real HTML first (server-side rendering, SSR) or build pages ahead of time (static site generation, SSG), then let React take over in the browser (hydration). They also give you file-based routing, data loading and an API layer. The React team now recommends starting most new websites with one of them.
