Server-Side Development 1: PHP

Until now, every line of code you wrote ran in the visitor's browser. This chapter moves to the other end of the connection: programs that run on the web server, build a fresh page for every request, read what visitors type into forms, and decide which headers and status codes go back. You will learn PHP, the language behind a large share of the web, by writing real scripts that run right here on the page.

How the PHP playgrounds work Browsers cannot run PHP, so this page includes a small PHP 8 interpreter written in JavaScript. Every playground acts like a real server: the bar above the preview is the browser's address bar, Send makes a new request, links and forms in the preview send real GET and POST requests to your script, and the strip under the preview shows the status code and response headers. Warnings and errors look exactly like PHP's. It covers the language this chapter teaches; it has no database and no files to read.

What Is Server-Side Development?

Think about the pages you have built so far. When someone asks for about.html, the web server finds that file on its disk and sends it, unchanged, to everyone who asks. That is a static page: the same bytes for every visitor, every time, until you edit the file. JavaScript (Chapters 8 to 11) makes a page interactive, but it only starts working after the page has arrived in the browser.

Server-side development means writing programs that run on the web server, before the response leaves. Instead of finding a finished file, the server runs your program, and the program builds the page on the spot. It can show today's specials, greet a signed-in user by name, search a database of ten thousand products, or check a password, and then it sends the result. The visitor's browser receives only that result: ordinary HTML. It never sees your program.

That one fact explains almost everything about server-side code. The program runs on a machine you control, so it can do things browser code never may: read files, talk to a database, keep secrets such as passwords and payment keys, and decide what each visitor is allowed to see. Step through one request below.

  1. You click a link to menu.php?cat=drinks. Exactly as in Chapter 2, the browser looks up the server's address and sends an HTTP GET request. Nothing about the request says "PHP": it is just a path and a query string.

  2. The web server software (usually Apache or nginx) receives the request. For a .html or .css file it would simply send the file. This file ends in .php, so the server is configured to hand the request to PHP instead.

  3. The PHP engine opens menu.php and reads it from top to bottom. Plain HTML is copied straight to the output; code between <?php and ?> is run. PHP also unpacks the request for your code: cat=drinks becomes $_GET['cat'].

  4. If the page needs stored data, the script asks a database for it ("every item in the drinks category") and gets rows back. You will connect PHP to a database in Chapter 14; in this chapter the data lives in arrays.

  5. The script finishes. Everything it printed, which is now plain HTML, goes back to the web server, which wraps it in a response: a status line such as 200 OK and headers such as Content-Type: text/html (12.8).

  6. The browser receives HTML and renders it like any other page, then fetches the CSS and images it links to. The PHP program has already finished and forgotten everything; the next request runs it again from the first line.

Three ways to build a dynamic site

Server-side code and the front-end JavaScript from Chapters 10 and 11 work together in a few standard arrangements. Knowing which one you are looking at tells you where each piece of logic belongs.

What it is. The server builds every page as finished HTML (this chapter's approach). Clicking a link or submitting a form loads a whole new page from the server.

When you meet it. WordPress sites, news sites, online stores, government forms, and most of the web's older pages. It is simple, works without JavaScript, and search engines read it easily.

Watch out. Every click is a full round trip to the server, so very interactive screens (a drag-and-drop planner, a chat) feel slow if built this way alone. Sprinkle in JavaScript for those parts.

What it is. The server sends only data, usually JSON (12.8), and JavaScript in the browser builds the page from it, as you did with fetch() in Chapter 10 and React in Chapter 11. The server-side program is then called an API.

When you meet it. Single-page applications such as Gmail or Trello, and mobile apps, which talk to the same API as the website.

Watch out. The server still does every check that matters. The JavaScript can hide a button, but only the API can refuse a request.

What it is. Most pages are plain HTML files (fast, cheap, cacheable), and only the few jobs that need a server, such as a contact form or a sign-up, are handled by small scripts or hosted services.

When you meet it. Portfolios, small business sites, documentation. Your course project could grow this way: static pages on a static host, plus one PHP script on a PHP host to receive its form.

Watch out. The form's action must point at a server that can run the script. A form on a static host cannot process itself.

A short history of PHP

PHP began in 1994 as a handful of tools Rasmus Lerdorf wrote to track visits to his online résumé; he called them "Personal Home Page Tools". It grew into a full language because it solved the web's most common problem, "put this data into this HTML", more simply than anything else at the time. Today the name stands for PHP: Hypertext Preprocessor (a joke acronym that contains itself), and modern PHP is fast, typed when you want it to be, and very different from the PHP of twenty years ago. If you read old tutorials, expect old habits that this chapter steers you away from.

Where PHP runs

To run PHP you need two pieces: something that speaks HTTP (a web server), and the PHP engine that runs your scripts. Pick a setup to see what it is, when you meet it, and how to start it.

What it is. PHP comes with a tiny web server of its own, made for development. One command in a terminal turns the current folder into a website at http://localhost:8000, running every .php file it serves.

When you meet it. When you practise on your own computer. It is the fastest way to try this chapter's examples for real: install PHP (from php.net, Homebrew on a Mac, or a package manager on Linux), then run the command in the folder that holds your files.

Watch out. It handles one request at a time and is not built for real traffic, so never use it to host a public site. Keep the terminal window open; closing it stops the server.

What it is. The classic production recipe: Linux (the operating system), Apache (the web server), MySQL or MariaDB (the database) and PHP. Variants swap a letter: LEMP uses nginx ("engine-x"), and WAMP or MAMP run on Windows or macOS.

When you meet it. On most shared web hosts and many company servers. Apache either runs PHP inside itself (a module) or passes each request to PHP-FPM, a separate pool of PHP workers. Either way, your code does not change.

Watch out. Your code runs as the web server's user on a machine connected to the internet, so treat every request as possibly hostile: validate input (12.7) and never show detailed error messages on a live site.

What it is. Free installers that bundle Apache, MySQL (or MariaDB) and PHP with a control panel, so you can run a full LAMP-style stack on your laptop with a few clicks. XAMPP runs on Windows, macOS and Linux; MAMP is popular on macOS.

When you meet it. In courses and tutorials that use a database (Chapter 14), and when you want your laptop to behave like a real host. Your files go in a special folder (htdocs for XAMPP) and are served at http://localhost/.

Watch out. Pages must be opened through http://localhost/…, not by double-clicking the file. Opening file:///…/index.php skips the server, so the browser shows your raw PHP instead of running it.

What it is. A company runs the server for you. Shared hosting plans include PHP and a database; you upload files (with SFTP or Git) and they are live at your domain.

When you meet it. When a site has to be public: a portfolio with a working contact form, a club site with sign-ups, a WordPress blog.

Watch out. Check the PHP version your host runs (this chapter uses PHP 8 features) and keep it updated. Old, unsupported PHP versions stop receiving security fixes.

PHP Language Fundamentals

PHP looks a lot like the JavaScript you already know: statements end with semicolons, blocks sit inside curly braces, and if, for and while work almost the same way. The differences are small but they bite, so this section concentrates on them. The biggest one is visible on every line: every variable name starts with a dollar sign.

Try it. This playground is a free sandbox with no checks: change the values, add lines, make mistakes on purpose and read what PHP says. The page re-runs as you type.

PHP tags, statements and echo

PHP only runs code between its tags. Everything outside them is sent to the browser exactly as written, which is why a .php file can be mostly HTML with a few PHP "islands". Inside the tags, each statement ends with a semicolon. The closing tag ?> also ends a statement, so the last semicolon before it is optional (but writing it anyway is a good habit).

Variables

A variable is created the moment you assign to it; there is no let, const or var. The name is a dollar sign followed by a letter or underscore, then any mix of letters, digits and underscores. Variable names are case-sensitive ($Total and $total are two different variables), although keywords and function names are not (ECHO works, but please do not). PHP is dynamically typed: a variable has no fixed type, and the value it holds decides its type.

Data types

PHP has eight types. Four hold a single value (scalar types), two hold collections, and one means "nothing". You will use all of them in this chapter. var_dump() is your best friend while learning: it prints a value's type and its value, so var_dump(10 / 4) prints float(2.5).

Working with numbers

Numbers behave mostly as you would expect, with a few PHP-specific tools. Pick a tab.

What it is. The operators + - * / % **, plus intdiv() for whole-number division. Parentheses work as in math class: (2 + 3) * 4 is 20.

When you meet it. Totals, taxes, averages, page counts: any calculation on a server.

Watch out. Dividing by zero is not Infinity as in JavaScript: PHP 8 throws a DivisionByZeroError and stops, so check a divisor that comes from input.

What it is. round($n, $places) rounds (halves go away from zero), floor rounds down, ceil rounds up, and number_format($n, $decimals) rounds and returns a string with thousands separators, ready to print.

When you meet it. Every time a price or a statistic is shown to a person.

Watch out. number_format returns a string, so do all your arithmetic first and format only when printing. Doing math on '1,234.50' fails.

What it is. Computers store decimal numbers in binary, so many of them (like 0.1) are stored very slightly wrong. echo rounds to 14 significant digits and usually hides this; var_dump shows the true value.

When you meet it. When comparing money calculations with ==, or when a total ends in ...0000001.

Watch out. Never compare floats for exact equality. Round both sides first, or store money in whole cents as ints.

What it is. A cast converts a value to a type: (int), (float), (string), (bool), (array). The functions intval(), floatval() and strval() do the same.

When you meet it. With input, which always arrives as text: (int) $_GET['page'] turns '3' into 3.

Watch out. Casts never complain. (int) 'abc' is quietly 0 and (int) '12 apples' is 12. To reject bad input instead of guessing, validate it with filter_var (12.7) or is_numeric().

Strings

Strings are where PHP differs most from JavaScript. There are two kinds of quotes and they behave differently, and strings are joined with a dot, not a plus sign. Pick a tab to see each way of writing a string.

What it is. 'text' is a literal string: PHP uses the characters exactly as typed. A dollar sign is just a dollar sign, and \n is a backslash and the letter n. The only escapes are \' (a quote) and \\ (a backslash).

When you meet it. For any fixed text with no variables in it: HTML snippets, array keys, messages. Many teams use single quotes by default because what you see is exactly what you get.

Watch out. Variables are not filled in, which is the most common beginner surprise in PHP.

What it is. "text" is an interpolated string: PHP replaces variables inside it with their values and understands escape sequences such as \n (newline), \t (tab), \" and \$.

When you meet it. When a message mixes text and variables: "Hello, $name" is easier to read than a chain of dots. For array items and object properties, wrap the expression in curly braces: "{$order['qty']} items".

Watch out. PHP grabs the longest variable name it can, so "$sizecm" looks for a variable called $sizecm. Write "{$size}cm" instead. To print a real dollar sign, escape it: "\$5".

What it is. The dot operator . joins two strings into one, and .= adds to the end of a string variable. In JavaScript the + sign did both jobs; in PHP + only ever does arithmetic.

When you meet it. Constantly, especially when building HTML a piece at a time inside a loop.

Watch out. "5" + "5" is the number 10, while "5" . "5" is the string "55": the opposite of JavaScript. Using + on text that is not a number, such as 'Total: ' + 5, stops the script with TypeError: Unsupported operand types.

What it is. A way to write long, multi-line strings without quotes. A heredoc starts with <<< and a label, ends with the same label on its own line, and fills in variables like double quotes. A nowdoc puts the label in single quotes and, like single quotes, fills in nothing.

When you meet it. For blocks of HTML or email text with a few variables in them.

Watch out. The closing label must be the only thing on its line (a semicolon may follow it). Indentation in front of the closing label is removed from every line.

Program Control

    
A script that runs every line exactly once, top to bottom, cannot do much. Program control statements change that: conditionals choose which lines run, and loops run lines many times. PHP's versions look almost exactly like the JavaScript ones from Chapter 8, so this section moves quickly through the familiar parts and slows down for the three things that are different: what counts as true, the match expression, and a second way of writing blocks that keeps HTML templates readable.

Functions

    
A function is a named block of code you can run whenever you need it, with different inputs each time. You have already used dozens of PHP's built-in functions: date(), number_format(), strtoupper(). PHP ships with thousands of them, all documented at php.net, where typing a function name into the search box takes you to its page. In this section you write your own user-defined functions, so a rule such as "how a price is displayed" lives in exactly one place.

    
    
Function names follow the same rules as variable names, without the dollar sign, and unlike variables they are not case-sensitive: formatPrice() and FORMATPRICE() call the same function. A function defined at the top level of a file can be called above the line where it is written, because PHP reads all of them before running the first statement. Defining two functions with the same name is a fatal error.


    
Parameters, defaults and return values

    
Parameters are the variables listed in the parentheses; the values passed in a call are the arguments. Give a parameter a default value with = and the argument becomes optional. return ends the function and hands one value back; a function with no return gives back null. To return several values, return an array and unpack it.

When you meet it. For settings that are usually the same: a currency symbol, a number of decimal places, a page size.

        
Watch out. Parameters with defaults must come after the ones without. Skipping a middle argument used to be impossible; named arguments (next tab) fix that.

        
      

      

        
What it is. A PHP 8 feature: pass an argument by writing the parameter's name and a colon before it. Named arguments can come in any order and let you skip optional parameters.

        
When you meet it. With functions that have several optional parameters, where htmlspecialchars($s, double_encode: false) is clearer than a list of positional values.

        
Watch out. Renaming a parameter now breaks callers that used its name. In this course's playground, named arguments work for your own functions but not for PHP's built-in ones.

When you meet it. Almost every function you write should return its result rather than echo it. A function that returns can be used anywhere: inside a string, in a condition, in another function call.

Type declarations

    
PHP lets you declare what type each parameter must be, and what type the function returns. If a caller passes something that cannot be used as that type, PHP stops with a TypeError that names the function, the argument and the line of the call. Declarations catch mistakes early and document what a function expects.

    
    
By default PHP works in coercive mode: if a value can be converted sensibly, it is. The string "5" passed to an int parameter arrives as the int 5, which is handy because form input is always a string. Add declare(strict_types=1); as the very first statement of a file and PHP switches to strict mode for calls made in that file: types must match exactly (the only exception is that an int is accepted where a float is expected). Arrays

    
Server-side code spends most of its time on collections: the items in a cart, the rows from a database, the fields of a submitted form. PHP has one collection type for all of these, the array, and it is more flexible than JavaScript's. A PHP array is an ordered map: a list of key and value pairs that remembers the order you added them in. When the keys are 0, 1, 2… it works like a JavaScript array; when the keys are names, it works like a JavaScript object. It can even be both at once.


    
Indexed arrays

    
An indexed array has whole-number keys that PHP assigns for you, starting at 0. Create one with square brackets (or the older array() syntax), read an element with its key in brackets, and add to the end with empty brackets.

    

    
Associative arrays

    
An associative array uses keys you choose, usually strings, written with the double arrow =>. It describes one thing by its named parts, the way a JavaScript object does. You will meet associative arrays everywhere on the server: $_GET, $_POST and $_SERVER are all associative arrays (12.7), and a database row arrives as one too.

    
    
Keys can only be ints or strings, and PHP tidies them up as they go in. Most of the time you will never notice, but it explains some surprising results:

Looping over arrays

    
There are several ways to walk an array, and each fits a different job. Pick a tab.

    

      

        
What it is. foreach ($array as $value) runs once per element, in order, handing you a copy of each value.

        
When you meet it. Most of the time: printing a list, adding up a total, checking each item.

        
Watch out. The loop works on a copy of the array, so adding elements inside the loop does not make it run longer, and changing $value does not change the array.

        
      

      

        
What it is. foreach ($array as $key => $value) also gives you each key. With an associative array the key is the name; with an indexed array it is the position.

        
When you meet it. Printing labels and values (Name: Ana), building <option value="key"> lists, numbering rows.

        
Watch out. The names $key and $value are your choice; pick ones that say what they hold, such as $drink => $price.

        
      

      

        
What it is. A loop inside a loop, one level per level of the data: the outer loop walks the rows, the inner loop walks each row's values.

        
When you meet it. Turning a list of rows into an HTML table, or a menu of categories into headings with items under each.

        
Watch out. Use different variable names at each level, or the inner loop overwrites the outer one's variables.

        
      

      

        
What it is. A counting loop from 0 to count($array) - 1, reading $array[$i].

        
When you meet it. When you need the position for arithmetic, such as "every other row" or "compare each element with the next one".

        
Watch out. It only works for indexed arrays with no gaps. After an unset() or with string keys, use foreach.

Static members and class constants

    
Sometimes data belongs to the class as a whole rather than to each object: a count of how many books exist, or a tax rate every book shares. Mark a property or method static, or declare a const, and it lives on the class. Reach it with the double colon :: (PHP calls it the scope resolution operator): ClassName::member from outside, self::member from inside.

    

    
Inheritance

    
A class can extend another. The new subclass (child) gets every public and protected property and method of its parent, and can add more or override a method by defining one with the same name. parent::method() calls the parent's version, which is how a child constructor sets up the parent's part of the object.

    
    
That last loop shows polymorphism: the same call, $item->label(), does the right thing for each kind of object. Two more tools build on inheritance. An abstract class cannot be created with new; it exists to be extended, and its abstract methods must be written by every child. An interface is a list of methods a class promises to have (class Drink implements Sellable). You will use both once your programs grow, and frameworks use them everywhere.


    

      

        
What it is. A class marked abstract is an unfinished blueprint. It cannot be created with new, and its abstract methods have no body: every non-abstract child must write them.

        
When you meet it. When several classes share most of their code but each must supply one piece, such as how a shape works out its area.

        
Watch out. A child that forgets an abstract method is a fatal error the moment the class is declared, which is the point: the mistake shows up immediately, not when a customer finds it.

        
      

      

        
What it is. An interface lists methods without any code. A class that implements it promises to provide them all. A class can extend only one parent but implement many interfaces.

        
When you meet it. When unrelated classes must work in the same place: a shop can print a receipt for anything that implements HasPrice, whether it is a drink, a gift card or a gym membership.

        
Watch out. Interface methods must be public, and the implementing class must match their parameters and return types.

        
      

      

        
What it is. In real projects each class gets its own file named after it (Book.php holds class Book), files are grouped into folders, and a namespace such as App\Models keeps names from clashing.

        
When you meet it. In every framework. A tool called Composer, PHP's package manager (like npm for JavaScript), loads each class file automatically the first time the class is used, so you never write long lists of require lines.

        
Watch out. This page keeps everything in one file so you can see it all at once. That is fine for learning and for small scripts, and not how larger projects are organized.

Methods whose names start with two underscores are magic methods: you never call them yourself; PHP calls them when something particular happens to an object. You have used one already, __construct. Three more are worth knowing now.

When you meet it. For objects with an obvious text form: a price, a person's name, a date.

How each kind of control arrives

    
Every control sends its name and its current value, but a few send nothing at all in some states. Knowing which is which saves a lot of "Undefined array key" warnings. Pick a control.

    

      

        
What it is. Typing controls always send their name, with whatever is in the box, even when it is empty.

        
When you meet it. Names, emails, comments, quantities.

        
Watch out. An empty box sends '', not nothing, so isset() is true even though the visitor typed nothing. Use trim($v) === '' to test for "empty". A type="number" field still arrives as a string such as '3'.

        
      

      

        
What it is. A ticked checkbox sends its value (or 'on' if it has none). An unticked checkbox sends nothing: its name is simply missing.

        
When you meet it. "Subscribe to the newsletter", "I agree to the terms".

        
Watch out. Because an unticked box is missing, test it with isset(); reading it directly gives a warning when it is unticked.

        
      

      

        
What it is. Several checkboxes sharing a name that ends in []. PHP collects the ticked ones into an array.

        
When you meet it. Toppings, interests, days of the week: any "choose all that apply" question.

        
Watch out. If nothing is ticked, the name is missing entirely, so default to an empty array. Then check every value against the allowed list, because a visitor can send values your form never offered.

        
      

      

        
What it is. A radio group or a drop-down sends the value of the one choice that is selected, under the group's name.

        
When you meet it. Sizes, shipping options, a country, a rating.

        
Watch out. A radio group with nothing selected sends nothing. And a visitor can edit the page and send size=XXL, so always check the value is one you offered with in_array(…, true).

        
      

      

        
What it is. <input type="hidden" name="order_id" value="A17"> sends a value the visitor does not see on the page.

        
When you meet it. To carry an ID through a form, such as which product a review is for.

        
Watch out. "Hidden" only means "not displayed". Anyone can see it in View Source and change it in DevTools, so never put a price, a permission or anything secret in a hidden field. Look prices up on the server from the ID.

Escaping output: stopping cross-site scripting

    
Validation decides whether to accept input. Forget it, and a visitor who types HTML (or a script) into your form gets it inserted into your page, for every visitor who views it. That attack is cross-site scripting (XSS), the same danger you met with innerHTML in Chapter 9, now on the server.

Post/Redirect/Get

    
There is one more trap with POST. After a successful order, the browser is showing the response to a POST request. If the customer presses Refresh, the browser repeats that last request, POST data and all, and the order is placed twice. The fix is a pattern called Post/Redirect/Get (PRG): after handling a successful POST, the script does not print a page. It sends a redirect (12.8 explains the header), and the browser follows it with a fresh, harmless GET.


    

      

        
      

      
    
        
  1. The customer submits the order form. The browser sends a POST request with the form data in its body.
    2. 
        
  2. The script validates the data and saves the order, exactly once. Instead of printing a thank-you page, it calls header('Location: order.php?done=1') and exit. The response is a 302 redirect with no page in it.
    3. 
        
  3. The browser follows the redirect on its own, with a brand-new GET request. The customer never sees the 302; the address bar simply changes.
    4. 
        
  4. The script sees ?done=1 in $_GET and shows the thank-you message. The page on screen is now the result of a GET.
    5. 
        
  5. If the customer presses Refresh, the browser repeats the last request, which is now the harmless GET. No second order, and no "Confirm Form Resubmission" dialog. If validation had failed in step 2, the script would instead show the form again with its errors, right away, with no redirect.

Working with the HTTP Header

    
Chapter 2 showed that every HTTP response has three parts: a status line (such as HTTP/1.1 200 OK), a block of headers (name and value lines such as Content-Type: text/html), and then, after one blank line, the body. So far your scripts have only written the body. PHP filled in the rest with sensible defaults: status 200 and Content-Type: text/html; charset=UTF-8. This section takes control of the rest, which is how a PHP script redirects, reports "not found", serves JSON or a download, and sets cookies.

    

    
The header() function, and the one rule

    
header('Name: value') adds a header to the response (or replaces one with the same name). The rule you must never forget comes from the shape of the response itself: headers go before the body. The moment your script outputs anything (one character of HTML, a space before <?php, an echo, even a warning message), PHP has to send the status line and headers so that the body can begin. After that it is too late, and header() fails with a warning you will see many times in your career:

    
    
The message even tells you where the guilty output started. The cures: do all your logic (and every header() call) at the top of the file, before any HTML; leave the closing ?> off files that are pure PHP so no stray newline slips out; and, as a safety net, output buffering with ob_start(), which holds output in memory until the script ends so headers can still be added. A redirect tells the browser "what you want is over there". Send a Location header and PHP automatically sets the status to 302 Found; the browser then requests the new address on its own. Always follow the header with exit: header() only adds a header, it does not stop your script, and code that keeps running after a redirect (still printing a secret page, still saving data) is a classic security bug.

Three more header jobs

    

      

        
What it is. Content-Disposition: attachment; filename="…" tells the browser to save the body as a file instead of showing it. With a matching Content-Type, a script can generate a spreadsheet, a calendar entry or a receipt on the fly.

        
When you meet it. "Export to CSV" buttons, downloadable invoices, reports.

        
Watch out. Nothing else may be printed: any stray HTML or warning ends up inside the downloaded file.

        
      

      

        
What it is. Cache-Control says whether a browser (or a server in between) may keep a copy of the response, and for how long. max-age=3600 allows one hour; no-store forbids keeping it at all.

        
When you meet it. Pages that rarely change can be cached to make a site much faster; pages with private or live data (an account page, a cart) should not be.

        
Watch out. Cache too aggressively and visitors see yesterday's prices. A related status, 304 Not Modified, lets a server answer "you already have the latest version" with no body at all.

        
      

      

        
What it is. Headers that switch on browser protections: X-Frame-Options: DENY stops other sites from showing your page inside a frame (to trick people into clicking), and Content-Security-Policy limits where scripts may load from, a strong second line of defense against XSS.

        
When you meet it. On every professional site, usually set once for the whole site by the web server or framework.

        
Watch out. A strict policy can block scripts your own page needs, so add one carefully and test every page.

        
      

    


    
Cookies

    
HTTP has no memory: every request arrives as if from a stranger. A cookie is a small named value the server asks the browser to store and send back with every later request to the same site. That is how a site remembers your theme, your cart, or that you are signed in. Cookies travel in headers: setcookie() adds a Set-Cookie header to the response, so like header() it must be called before any output. On the next request the browser sends the cookie back and PHP puts it in $_COOKIE.

    
    
Cookies are input too The visitor's browser stores cookies, so the visitor can read and change them. Never put a password or a price in a cookie, validate a cookie's value like any other input, and use httponly and secure (HTTPS only) for anything that identifies a user. Sessions, a later topic, keep the real data on the server and store only a random ID in the cookie.
