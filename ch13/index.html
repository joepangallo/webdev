Introducing Node.js

Node.js (usually just "Node") is a program that runs JavaScript outside the browser. Until 2009, JavaScript lived only inside web pages. Then Ryan Dahl took the JavaScript engine from Google Chrome, called V8, and wrapped it in a program that can read files, open network connections and listen for HTTP requests. The result was a way to write the server half of a website in the same language as the browser half.

That is the big idea of this chapter. In Chapter 12 the browser spoke JavaScript and the server spoke PHP: two languages, two sets of rules, two ways of writing a loop. With Node, one developer (or one team) can write the whole application in JavaScript, share code such as validation rules between both sides, and send data back and forth as JSON, which is JavaScript's own object notation. A setup where JavaScript runs in the browser and on the server is often called full-stack JavaScript.

Same language, different world

Node runs the same JavaScript you learned in Chapters 8 to 10: variables, functions, arrays, objects, classes, promises. What changes is the world around your code. In a browser, your script lives inside a web page, so it gets document, window and the DOM. On a server there is no page and no screen, so none of those exist. Instead Node gives you things a web page must never have, such as the power to read and write any file the server can reach.

What it is. JavaScript inside a web page, running on the visitor's own computer or phone, inside the browser's security sandbox.

When you meet it. Every page you built in Chapters 8 to 11: reacting to clicks, changing the DOM, calling fetch() to load data.

Watch out. Anyone can open DevTools and read (and change) browser JavaScript. Never put a password, a secret API key or a price check that matters only in browser code.

What it is. JavaScript run by the node program on a server (or on your own computer while you develop). There is no page and no visitor sitting in front of it.

When you meet it. Web servers and APIs (this chapter), command-line tools (npm itself is written in JavaScript), and the build tools from Chapter 11 such as Vite.

Watch out. document and window do not exist here. Code such as document.querySelector('h1') stops with ReferenceError: document is not defined.

What it is. The JavaScript language itself, plus a growing set of web-standard tools that Node copied from browsers so the same code works in both places.

When you meet it. Constantly: console.log(), setTimeout(), JSON, Math, promises, async/await, the URL class, and (since Node 18) even fetch().

Watch out. console.log() prints in different places: in a browser it goes to the DevTools console, in Node it goes to the terminal that started the program. Students often look for server messages in the browser and find nothing.

Sort these into the right box. Some exist only in the browser, some only in Node, and some in both.

One thread, never waiting: the event loop

A busy website handles hundreds of requests at once, and most of the time spent on a request is waiting: for a database to answer, for a file to load, for another service to reply. Traditional servers such as Apache with PHP give every request its own thread (a separate line of work inside the computer). While a thread waits for the database, it sits there doing nothing, but it still holds memory. With enough visitors, the server runs out of threads, and new visitors wait in line.

Node takes a different approach. Your JavaScript runs on one single thread, and that thread never sits and waits. When your code asks for something slow, Node hands the waiting to the operating system (through libuv) and moves straight on to the next request. When the slow thing finishes, a callback (or a resolved promise) is put in a queue, and the event loop runs it as soon as the thread is free. This style is called non-blocking, or asynchronous I/O ("I/O" means input and output: files, networks, databases). Step through one request below.

  1. A browser sends GET /books. Node's HTTP server receives it and puts a "request" event in line for the main thread.

  2. The main thread runs your route handler: plain JavaScript, a few microseconds of work, such as reading req.params.

  3. Your handler asks the database for rows. Instead of waiting, Node hands the job to libuv and the operating system, and your function returns.

  4. For the next 200 ms the database works and libuv waits. The main thread is free, so it serves dozens of other requests in the meantime. This is the whole trick.

  5. The rows arrive. libuv puts your callback (or the resolved promise) in the queue, and the event loop hands it to the main thread as soon as the thread finishes what it is doing.

  6. Your callback runs: it turns the rows into JSON and calls res.json(rows). Again only microseconds of work.

  7. The response travels back to the browser. One thread handled this request without ever sitting idle.

The one rule of Node: never block the thread Node is fast only while the main thread stays free. A function ending in Sync (such as fs.readFileSync()) or a long calculation (for example a loop over ten million items) blocks the thread: while it runs, every other visitor waits, as the third mode shows. Use the asynchronous versions (fs.promises.readFile(), a database library's promise-based methods) inside request handlers. Using readFileSync once at startup, before any visitor arrives, is fine.

Three ways Node tells you a slow job is done

Because Node never waits, every slow function needs some way to say "I'm finished, here is the result" later. Over the years Node has used three styles, and you will meet all three in tutorials and documentation. They do the same job; the newest one simply reads the most like ordinary top-to-bottom code.

What it is. Node's original style. You pass a function as the last argument, and Node calls it when the job finishes. Its first parameter is always an error (or null when all went well); the result comes second.

When you meet it. Older code, many tutorials, and Node's own documentation for modules like fs.

Watch out. Always check the error first. And several slow jobs in a row lead to callbacks inside callbacks inside callbacks, a shape so common it has a name: "callback hell".

What it is. The promise objects from Chapter 10. Every fs function has a promise version in fs.promises (or require('fs/promises')) that returns a promise instead of taking a callback.

When you meet it. Code that chains several steps with .then(), or runs jobs side by side with Promise.all().

Watch out. End every chain with .catch(). A rejected promise nobody catches makes modern Node print an error and stop the whole process.

What it is. The same promises, written with async and await (Chapter 10) so that the code reads top to bottom, with an ordinary try/catch for errors.

When you meet it. Almost all new Node code, including the Express handlers in this chapter: app.get('/', async (req, res) => { … }).

Watch out. await pauses only this function, never the whole server: while it waits, the event loop serves other requests. That is exactly why it is safe, and readFileSync is not.

Pick a program, guess the order of the output, then step through it and watch the call stack (the code running right now), the jobs waiting in Node, and the two queues the event loop empties.               First Steps with Node

              To use Node for real, you install it once from nodejs.org. Pick the version labeled LTS ("long-term support"): it is the stable one that companies use. The installer adds two commands to your computer: node, which runs JavaScript files, and npm, which installs packages. You type both into a terminal (Terminal on macOS, PowerShell or Windows Terminal on Windows, or the terminal panel built into VS Code).

              Lines that start with $ are what you type (do not type the $ itself; it stands for the prompt). The other lines are what the computer answers. If you see "command not found", the installer did not finish, or the terminal was already open before you installed: close it and open a new one.

              Three ways to run JavaScript with Node

              What it is. Type node on its own and you get the REPL: Read, Evaluate, Print, Loop. It reads one line of JavaScript, runs it, prints the result, and waits for the next line. It is Node's version of the browser's DevTools console.

              When you meet it. When you want to test one idea quickly: how a string method behaves, what new Date() gives, whether a regex matches.

              Watch out. Nothing typed in the REPL is saved. To leave, type .exit or press Ctrl+C twice.

              What it is. Save JavaScript in a file, such as hello.js, and run it with node hello.js. Node runs the file from top to bottom, then quits when nothing is left to do.

              When you meet it. Small tools: renaming files, converting data, sending a report. The first playground in 13.1 was a script like this.

              Watch out. Run the command from the folder that holds the file. cd ("change directory") moves the terminal into a folder, for example cd Desktop/my-api.

              What it is. A script that calls listen() does not quit: it keeps running, waiting for HTTP requests, until you stop it with Ctrl+C. That is a web server.

              When you meet it. For the rest of this chapter. You start it with node server.js (or npm start) and visit http://localhost:3000 in a browser.

                  Modules: require or import?
                  
    
                  A module is one file of code that shares some of its contents with other files. Node has two systems for this, and you will see both in tutorials. The older one, CommonJS, uses require() and module.exports. The newer one, ES modules, uses the same import and export you met in Chapter 10. New projects increasingly use ES modules; the playgrounds in this chapter accept both.
                  
    
                  
      
                  
        
                  What it is. Node's original module system. require('name') loads a module and returns whatever that module put in module.exports.
                  
        
                  When you meet it. In most existing Node code, most Stack Overflow answers, and any project whose package.json does not say "type": "module".
                  
        
                  Watch out. Your own files need a path that starts with ./ (require('./books')). Without it, Node looks for a package called books in node_modules and fails with "Cannot find module".
                  
        
        
      
                  
      
                  
        
                  What it is. The standard module system of JavaScript itself, the same one browsers use with <script type="module">.
                  
        
                  When you meet it. When package.json contains "type": "module", or a file ends in .mjs. Vite, React projects and many newer packages use it.
                  
        
                  Watch out. Your own files need the full name including .js: import { count } from './books.js'. And __dirname does not exist in ES modules; use import.meta.dirname (Node 20.11 and later) instead.

                  Paths: __dirname and the path module
                  
    
                  Servers read files constantly: templates, data, uploads. A path such as 'data/books.json' is relative, which means "relative to the folder the terminal was in when you typed node", not the folder your file lives in. Start the same server from a different folder and it suddenly cannot find its own files. The fix is to build paths from __dirname (the folder of the current file) with the path module.
                  
    
                  
      
                  
        
                  What it is. Joins pieces of a path with the right separator for the operating system (/ on macOS and Linux, \ on Windows), and tidies up .. and doubled slashes.
                  
        
                  When you meet it. Every time a server opens a file of its own.
                  
        
                  Watch out. Do not glue paths with +: __dirname + 'data' forgets the slash and gives /appdata.
                  
        
      
                  
      
                  
        
                  What they are. Small functions that pull a path apart or build one: path.extname() (the extension), path.basename() (the file name), path.dirname() (the folder), and path.resolve() (an absolute path).
                  
        
                  When you meet them. Deciding a file's type from its extension, building download names, checking an upload.
                  
        
                  Watch out. Never join a path with something a visitor typed without checking it: a "file name" of ../../secret.txt climbs out of your folder. express.static already guards against this for you.
                  
        
      
                  
      
                  
        
                  What it is. __dirname does not exist in ES modules. Node 20.11 and later offer import.meta.dirname instead (and import.meta.filename).
                  
        
                  When you meet it. In projects whose package.json has "type": "module".
                  
        
                  Watch out. Older tutorials build it by hand with fileURLToPath(import.meta.url); on a current Node version, the one-liner is enough.

                  Creating an API in Node
                  
    
                  The http server in 13.2 already needed an if for every path, and it could not yet read form data, serve files, or tell GET from POST without more ifs. Real servers have dozens of paths, so almost everyone uses a framework on top of http. The most popular one by far is Express: small, flexible, and installed with npm install express.
                  
    
                  This section builds an API (application programming interface): a server whose answers are data, usually JSON, instead of web pages. A React app (Chapter 11), a phone app, or another server calls the API with fetch() and decides for itself how to display the data. One API can serve all of them.
                  
    
    
                  Compare that with the http version. Express reads the method and path for you (app.get('/api/books', …) runs only for GET /api/books), and res.json() converts, labels and sends the data in one call. Express also adds helpful extras to req and res, listed below.
                  

    
                  Routes: method + path + handler
                  
    
                  A route connects one HTTP method and one path to a handler function. Express checks routes in the order you wrote them and runs the first one that matches. If none matches, Express answers by itself with a 404 page that says Cannot GET /the/path.

                    Reading the rest of the request: headers, cookies and the client
                    
    
                    Besides the path, the query and the body, every request carries headers (Chapter 2): what the browser accepts, what language the visitor prefers, which cookies it holds, and sometimes a login token. Express makes each of them easy to read.
                    
    
                    
      
                    
        
                    What it is. req.get('Name') reads one request header, ignoring upper or lower case. req.headers holds them all, with lower-case names.
                    
        
                    When you meet it. API keys and login tokens (Authorization), the preferred language (Accept-Language), what the client accepts (Accept).
                    
        
                    Watch out. Headers are sent by the client, so a client can send anything. Use them as hints or as tokens you verify, never as proof on their own.
                    
        
      
                    
      
                    
        
                    What it is. Small named values the server asks the browser to store and send back with every later request. res.cookie() sets one; the cookie-parser middleware fills req.cookies.
                    
        
                    When you meet it. Remembering a logged-in session, a theme choice, a shopping cart id.
                    
        
                    Watch out. Mark login cookies httpOnly (JavaScript in the page cannot read them, which blunts XSS), secure (HTTPS only) and sameSite.
                    
        
      
                    
      
                    
        
                    What it is. req.ip (the client's address), req.hostname, req.protocol and req.originalUrl describe where the request came from and what it asked for.
                    
        
                    When you meet it. Logging, rate limiting ("at most 100 requests a minute from one address"), building absolute links.
                    
        
                    Watch out. Behind a host's proxy, req.ip is the proxy's address unless you set app.set('trust proxy', 1); only do that when your host tells you a proxy is in front.

                        Organizing routes with express.Router
                        
    
                        One file with fifty routes is hard to read. Express lets you split routes into small groups called routers, each in its own file, and mount each group at a path prefix. Inside the router, paths are written without the prefix.
                        
    
                        
      
                        
        
                        What it is. A mini app that holds only routes (and middleware) for one resource.
                        
        
                        When you meet it. Every Express project bigger than a demo: routes/books.js, routes/users.js, routes/orders.js.
                        
        
                        Watch out. The paths inside start from the mount point, so router.get('/:id') here answers /api/books/:id.
                        
        
      
                        
      
                        
        
                        What it is. The main file, now short: settings, global middleware, and one line per group of routes.
                        
        
                        When you meet it. As the entry point ("main" in package.json).
                        
        
                        Watch out. Mount routers after the middleware they rely on, such as express.json().
                        
        
      
                        
    
                        

    
                        When something goes wrong: error-handling middleware
                        
    
                        If a handler throws an error (or, in Express 5, an async handler's promise rejects), Express skips every normal middleware and route and jumps to the first error handler: middleware with four parameters, (err, req, res, next). Without one, Express sends its own plain 500 page. With one, you choose what the client sees, and you can log the details for yourself.
                        
    
    
                        Express 4 versus Express 5 Many tutorials were written for Express 4, where a rejected promise in an async handler was not caught (the request just hung), so they wrap every handler in try/catch or a helper. Express 5, which npm install express gives you today, catches it. Two other changes trip people up: req.body is undefined (not {}) until a body parser runs, and wildcard routes are written '/*splat' instead of '*'.
                        

    
                        Serving files with express.static
                        
    
                        An Express server can also hand out ordinary files, the job a plain web host did for your project site. Put your HTML, CSS, images and browser JavaScript in a folder (usually called public) and add one line. A request for /css/site.css is answered with the file public/css/site.css, and / gets public/index.html. Your API routes keep working beside it, so one server can deliver the front end and the data.
                        
    

    
                        CORS: when a page on another site calls your API
                        
    
                        Browsers protect visitors with the same-origin policy: JavaScript on a page from one origin (scheme + host + port, such as http://localhost:5173) may not read responses from a different origin (such as your API at http://localhost:3000) unless that server says it is allowed. The permission is an HTTP response header, Access-Control-Allow-Origin, and the system is called CORS (Cross-Origin Resource Sharing). This is the error you will meet the first time a React app (port 5173) calls your Express API (port 3000).

The URL names a resource (a noun such as /api/books); the method says what to do with it (the verb).

                        Reading the request body: express.json()
                        
    
                        POST, PUT and PATCH requests carry data in their body, usually as JSON with the header Content-Type: application/json. Express does not read bodies unless you ask: add app.use(express.json()) once, near the top, and every route gets the parsed object in req.body.                         Validation: never trust the client
                        
    
                        Anyone can send your API anything: a missing field, a number where text belongs, a 50,000-character title, or a hand-made request from curl that skips your front end's form checks entirely. The front end's validation (Chapter 5 and Chapter 9) is a convenience for honest users; the server's validation is the one that protects your data. Check every field you use, and answer 400 with messages specific enough to fix the request.
                        
    
    
                        Copy only the fields you expect Never save req.body as it is (books.push(req.body)). A client could add "id": 1 to overwrite another record, or "isAdmin": true to a user. Build the new object from the fields you checked. Libraries such as Zod and express-validator make long lists of rules shorter, but the idea stays the same.

                        Bigger lists: filtering, sorting and pages
                        
    
                        A real collection might hold thousands of records, and nobody wants all of them in one response. APIs let the client ask for a slice with query strings: which items (filter), in what order (sort), and how many at a time (pagination). The path stays the same; only the query changes, so GET /api/books?genre=classic&sort=year&page=2&limit=10 still means "books".
                        
    
    
                        Version your API Once other people's apps call your API, changing a response's shape breaks them. Many APIs put a version in the path, /api/v1/books, and when a breaking change is needed they add /api/v2/books beside it, keeping v1 alive until its users have moved over. An Express router makes this one line: app.use('/api/v1', v1Router).

                        Working with Web Sockets
                        
    
                        Everything so far followed HTTP's one rule: the client asks, the server answers, and then the conversation is over. The server can never speak first. That works for loading pages and data, but not for a chat app, a multiplayer game, a live sports score or a shared document, where the server learns something new and must tell the browsers immediately.
                        
    
                        Before WebSockets, sites faked it. With polling, the browser asks "anything new?" every few seconds, and the answer is usually "no". With long polling, the browser asks and the server holds the request open until it has news (or a timeout), then the browser asks again. A WebSocket replaces both: one connection that stays open, through which either side may send a message at any moment. Compare the three over the same minute.

                        How a WebSocket starts: the upgrade handshake
                        
    
                        A WebSocket begins life as an ordinary HTTP request with two special headers asking to upgrade the connection. If the server agrees, it answers 101 Switching Protocols, and from then on the same TCP connection carries small WebSocket messages (called frames) in both directions instead of HTTP. The URL uses ws:// (or the encrypted wss://, which you should always use on a live site).
                        
    
                        
      
                        
        
                        
          
        
                        
      
                        
      
                          
        
                        1. The browser runs new WebSocket('ws://localhost:8080/chat'), which sends an HTTP GET with Connection: Upgrade and Upgrade: websocket headers.
                          2. 
        
                        2. The server agrees: 101 Switching Protocols. HTTP's job is done. In the browser, the socket's open event fires; on the server, connection fires.
                          3. 
        
                        3. The connection now stays open, for minutes or hours. Neither side has to ask permission to talk.
                          4. 
        
                        4. The browser calls socket.send('Hi everyone!'). The server's message event fires, a few milliseconds later, with no new request and no headers.
                          5. 
        
                        5. The server sends a message whenever it wants: someone joined, a score changed, a price moved. The browser's message event fires. This is what plain HTTP cannot do.
                          6. 
        
                        6. Either side calls close(). Both get a close event with a code (1000 means a normal close; 1006 means the connection was lost).
                          7.

                          View Engines
                          
    
                          The APIs in 13.3 and 13.4 send data, and leave building the page to JavaScript in the browser (client-side rendering, the React way from Chapter 11). There is an older, simpler and still very common way: the server builds the finished HTML page itself and sends that, just as PHP did in Chapter 12. This is server-side rendering (SSR). In Express, the tool that turns data into HTML is a view engine, also called a template engine.
                          
    
                          A template is an HTML file with holes in it. The holes are marked with special tags: "put the book's title here", "repeat this <li> for every book", "show this paragraph only if the list is empty". The engine fills the holes with your data and returns plain HTML, which Express sends to the browser. The browser never sees the template, only the result.
                          
    
    
    
                          
      
                          
        
                          
          
        
                          
      
                          
      
                            
        
                          1. The route handler gathers the data for this page (from an array here, from a database in real life) and calls res.render('books', { heading, books }).
                            2. 
        
                          2. Express finds the template: the views folder, plus the name, plus the engine's extension: views/books.ejs.
                            3. 
        
                          3. The engine runs the template: the <% %> code (the if and the loop) and every <%= %> output tag, using the data object as its variables.
                            4. 
        
                          4. Out comes ordinary HTML, with no EJS tags left in it.
                            5. 
        
                          5. Express sends it with Content-Type: text/html. The browser draws it at once: no JavaScript needed, and search engines see the full content.
                            6. 
      
                          
    
                          


    
                          The five EJS tags
                          
    
                          EJS has only a handful of tags, and each one does one job. Pick a tag to see exactly what it does.
                          
    
                          
      
                          
        
                          What it is. Runs the JavaScript expression inside and prints its value, with HTML characters escaped (< becomes &lt;).
                          
        
                          When you use it. Almost every time you print data: titles, names, numbers, anything a user typed.
                          
        
                          Watch out. It prints expressions only: <%= if (x) %> is an error. Put statements in the code tag.
                          
        
      
                          
      
                          
        
                          What it is. Prints the value exactly as it is, HTML and all.
                          
        
                          When you use it. To include partials, and for HTML that your own code produced and trusts.

                          What it is. Runs JavaScript without printing anything: if, loops, variables.
                          
        
                          When you use it. Repeating or hiding parts of the page.
                          
        
                          Watch out. A block opened in one tag must be closed in a later one: every { needs its }, often in a tag of its own like <% } %>.
                          
        
      
                          
      
                          
        
                          What it is. A comment that never reaches the browser.
                          
        
                          When you use it. Notes for yourself and your team inside a template.
                          
        
                          Watch out. An HTML comment <!-- --> IS sent to every visitor and shows in View Source; an EJS comment is not.
                          
        
      
                          
      
                          
        
                          What it is. Ending a tag with -%> removes the line break right after it, so loops do not leave blank lines in the HTML.
                          
        
                          When you use it. When the generated HTML must be tidy (emails, plain text), or simply to keep View Source neat.

                          Escaping: <%= %> versus <%- %>
                          
    
                          Templates often print text that visitors typed: a name, a review, a comment. If that text contains HTML and the engine prints it as is, a visitor can inject their own tags into your page, including scripts. That is cross-site scripting (XSS), the same attack as innerHTML in Chapter 9. Every engine's normal output tag escapes the text, turning < into &lt; so it shows as a character instead of becoming a tag. Type a review below, try the attack examples, and compare the two tags.
                          
    
                          
      
                          
      
                          
      
                          
        
                          Template: <p><%= review %></p> (escaped)
                          
        
                          Template: <p><%- review %></p> (raw)
                          
      
                          
      
                          
    
                          
    
                          Use the raw tag only for HTML you wrote <%- %> exists for HTML that comes from your own code, such as <%- include('partials/footer') %>. Never pass anything a visitor typed through it. The preview frames above are sandboxed, so nothing actually runs here; on a real site the raw version would run the attacker's code for every visitor who opened the page.

                          Serverless Approaches
                          
    
                          Every server in this chapter so far has the same chores attached: rent a computer (a virtual private server, or VPS), keep its operating system patched, keep Node running, restart it when it crashes, and add more computers when traffic grows. And you pay for it 24 hours a day, even at 4 a.m. when nobody visits.
                          
    
                          Serverless computing hands those chores to a cloud company. There are still servers, of course; you just never see or manage them. You upload individual functions, and the platform runs a copy of a function each time a request (or another event) arrives, creates more copies when traffic jumps, removes them all when traffic stops, and charges you per request and per millisecond of running time. This model is called Function as a Service (FaaS). Well-known platforms include AWS Lambda, Netlify Functions, Vercel Functions, Cloudflare Workers, Google Cloud Run functions and Azure Functions.

                          Cold starts, warm starts
                          
    
                          When a function has not run for a while, the platform has nothing loaded, so the next request must wait while it starts a fresh copy and loads your code: a cold start, typically a few hundred milliseconds (more for big functions). Requests that arrive while a copy is still loaded get a warm start and answer almost instantly. Platforms also run copies side by side: if 50 requests arrive at once, up to 50 copies start, each handling one.

                            2. 
        
                          2. More requests arrive soon after. The copy is still loaded, so each one only pays for its own few milliseconds of work.
                            3. 
        
                          3. Nobody visits for a while (often 5 to 15 minutes). The platform shuts the copy down. Cost from now on: zero.
                            4. 
        
                          4. A sudden burst of three requests at once: the platform starts three copies side by side, each with its own cold start. No crowd can overwhelm a single server, because there is no single server.

                          What a function looks like
                          
    
                          A serverless function is one exported function. There is no express() and no listen(): the platform does the listening and calls your function with the request. Each platform has its own small conventions, but they fall into two families. The newer one uses the same Request and Response classes as fetch() in the browser.
                          
    
                          
      
                          
        
                          What it is. A default export that receives a standard Request and returns a standard Response, exactly the objects fetch() uses in the browser.
                          
        
                          When you meet it. Netlify Functions (files in netlify/functions/), Vercel Functions (files in api/), and Deno and Bun servers.
                          
        
                          Watch out. The URL is a full address, so read the query string with new URL(req.url).searchParams.get('name'), and the body with await req.json().
                          
        
      
                          
      
                          
        
                          What it is. An exported function called handler that receives an event object describing the request and returns a plain object with statusCode, headers and a body string.
                          
        
                          When you meet it. AWS Lambda (the oldest and largest FaaS platform) and Netlify's older function format.
                          
        
                          Watch out. The body must be a string: wrap objects in JSON.stringify(). And queryStringParameters is null, not {}, when there is no query string.
                          
        
      
                          
      
                          
        
                          What it is. A default export object with a fetch method. Workers run in Cloudflare's data centers in hundreds of cities, close to each visitor, and start in under 5 ms because they use V8 directly rather than a full Node.
                          
        
                          When you meet it. Sites that need very fast responses worldwide, redirects, small APIs, and "edge" logic in front of other servers.
                          
        
                          Watch out. Not every Node module is available on the edge: there is no ordinary file system, so data lives in Cloudflare's own storage services.
                          
        
      
                          
    
                          
    
                          
      
                          
        Strengths and weaknesses of serverless functions
        
                          Serverless is great when…Think twice when…
                          
        
          
                          Traffic is spiky or unpredictable (it scales instantly)Traffic is high and steady all day (a rented server is often cheaper)
                          
          
                          The site is mostly static, with a few API endpoints (a contact form, a payment)You need open connections such as WebSockets (functions end after each request)
                          
          
                          You want zero server maintenanceEvery millisecond matters and cold starts would hurt
                          
          
                          The project is small or new (often free at low traffic)Work runs for minutes (functions have time limits, often 10 to 30 seconds)
                          
                                  
      
                          
    
                          
    
                          The JAMstack pattern A very common modern setup combines this chapter's ideas: a static front end (HTML, CSS and JavaScript, maybe built with React) on a CDN, a handful of serverless functions for the parts that need a server (sending email, taking payments, hiding an API key), and a BaaS such as Supabase or Firebase for the database and logins. Your course project could grow this way: it is already static on GitHub Pages, and a single function on Netlify or Vercel could add a working contact form.
                          


    
                          A classic use: hiding an API key
                          
    
                          Chapter 10 warned that any API key in browser JavaScript is public: anyone can open DevTools and copy it. A tiny serverless function fixes that. The browser calls your function; the function, running on the platform's server, adds the secret key (stored as an environment variable in the platform's settings) and calls the real API. The key never reaches the visitor. This is called a proxy.

                          Variables do not survive In an Express server, an array of books lives in memory as long as the server runs. In a function, it does not: the next request may land on a brand-new copy with an empty array, and many copies may run at once, each with its own array. A counter such as let visits = 0 gives a different wrong answer on every copy. Serverless functions keep data in a database or a storage service, always.
                          

    
                          Backend as a Service, briefly
                          
    
                          Sometimes you need no server code at all. A BaaS such as Supabase or Firebase gives your front end a hosted database, user sign-up and login, and file storage, through a JavaScript library you call straight from the browser. Instead of writing an Express route, you write rules on the service saying who may read or change which rows.
                          
    



    
                          Not only web requests: what else can start a function
                          
    
                          "Serverless" functions answer HTTP requests, but that is only one kind of trigger. Platforms can run the same kind of function on a schedule, when a file is uploaded, or when data changes. This "something happened, run this code" model is called event-driven, the same idea as an event listener in the browser (Chapter 9), on a much larger scale.
                          
    
                          
      
                          
        
                          What it is. A function the platform runs at set times, described with a cron expression (five fields: minute, hour, day of month, month, day of week).
                          
        
                          When you meet it. Nightly backups, a daily summary email, clearing out old records every hour.
                          
        
                          Watch out. Schedules usually run in UTC, not your local time: 0 13 * * * is 1 p.m. UTC, which is 9 a.m. in Florida during daylight saving time.
                          
        
      
                          
      
                          
        
                          What it is. A function that a storage service (such as Amazon S3) calls whenever a new file lands in a folder.
                          
        
                          When you meet it. Making thumbnails of uploaded photos, scanning uploads, converting documents.
                          
        
                          Watch out. If the function writes its result back into the same folder, it triggers itself again, forever. Write to a different folder.
                          
        
      
                          
      
                          
        
                          What it is. A function a database or BaaS runs when a record is created, changed or deleted.
                          
        
                          When you meet it. Sending a welcome email when a user signs up, updating a counter when a review is added.
                          
        
                          Watch out. Triggers run separately from the request that changed the data, so the visitor's page does not wait for them, and errors in them do not reach the visitor. Log them.

                          When to choose it. Express APIs, server-rendered sites, and anything with WebSockets.

Free plans often put the app to sleep when idle, so the first visit after a quiet spell is slow (a cold start, again).

                          Watch out. Secrets go in the platform's "Environment variables" settings page, never in the repository. And remember that variables do not survive between requests.
