Internet Protocols

The internet is a network of networks. Your home Wi-Fi, your phone carrier, a campus network and a data center full of servers are all separate networks, run by different organizations with different hardware. They can still trade data because every device on them follows the same protocols: agreed rules for how a message is formatted, addressed, sent and acknowledged.

Keep two words apart. The internet is the global infrastructure that moves data; it grew out of ARPANET, a US research network that first linked computers in 1969. The World Wide Web is one service that runs on top of it: pages connected by links and delivered with HTTP, created by Tim Berners-Lee at CERN between 1989 and 1991. Email, video calls and online games also use the internet without being "the web."

Packet switching

A call on the old telephone network reserved a dedicated circuit for its entire length, even during silences. The internet works differently. It uses packet switching: your data is chopped into small packets, each stamped with where it came from, where it's going, and its place in the message. Routers forward every packet on its own, picking the best next hop at that moment. Millions of conversations share the same cables, and if a path is jammed or broken, packets flow around it.

    Three things just happened that your programs never have to worry about: packets took different routes, they arrived out of order, and (with loss switched on) one never arrived at all. The receiver used the sequence numbers to rebuild the message and got the missing piece sent again. That repair work belongs to one protocol, TCP, which is just one layer of a larger stack.

    The four layers of TCP/IP

    Networking is split into layers. Each layer solves one problem and relies on the layer below it, so Wi-Fi engineers never think about web pages and web developers rarely think about radio signals. The internet's family of protocols is called TCP/IP, after its two most famous members, and it's usually described with four layers:

    LayerIts jobExamplesUnit of data
    4 · ApplicationThe conversation between programs: what is actually being saidHTTP, HTTPS, DNS, SMTP, IMAP, SSH, FTPmessage
    3 · TransportDelivers data to the right program, optionally with guaranteed, in-order deliveryTCP, UDP (and QUIC, which runs on UDP)segment (TCP), datagram (UDP)
    2 · InternetAddresses packets and routes them from network to networkIPv4, IPv6, ICMPpacket
    1 · LinkMoves bits across one physical connection to the next deviceEthernet, Wi-Fi, fiber, cellularframe

    Sending data means passing it down the stack. Each layer wraps what it receives in its own header, the way a letter goes into an envelope, the envelope into a mail sack, and the sack onto a truck. This is called encapsulation. The receiver passes the data back up, and each layer removes only its own header.

    Jump to a layer

    The internet layer: IP addresses

    The Internet Protocol (IP) gives every connected device an address and lets routers forward packets toward it. Two versions run side by side today:

    • IPv4 (1981) addresses are 32 bits, written as four numbers from 0 to 255 separated by dots, such as 192.168.1.23. That allows about 4.3 billion addresses, fewer than the number of devices online. The central pool of unused IPv4 blocks ran out in 2011, and the regional registries ran dry over the following decade.
    • IPv6 addresses are 128 bits, written as eight groups of four hexadecimal digits separated by colons. A run of all-zero groups can be shortened to :: once, so 2001:0db8:0000:0000:0000:0000:0000:0001 becomes 2001:db8::1. There are so many IPv6 addresses that running out isn't a realistic worry.

    Some ranges have special jobs. Addresses starting 192.168., 10., or 172.16. through 172.31. are private: they work only inside a local network, and your router shares one public address among all your devices using network address translation (NAT). 127.0.0.1 is the loopback address, which always means "this computer." The addresses in this chapter's examples come from blocks reserved for documentation, so they never point at anyone's real server.

    IPv4 232 = 4,294,967,296 addresses: about 4.3 billion, fewer than one per person on Earth.

    IPv6 2128 = 340,282,366,920,938,463,463,374,607,431,768,211,456 addresses: about 3.4 × 1038.

    That's 296 (roughly 79 octillion) times the size of the entire IPv4 address space.

    The transport layer: TCP, UDP and ports

    An IP address gets data to the right computer. A port number (0 to 65535) gets it to the right program on that computer. A web server listens on port 443 for HTTPS or port 80 for plain HTTP, while your browser borrows a temporary high-numbered port for its end of the conversation. An address plus a port, like 203.0.113.80:443, names one endpoint of a connection.

    Two transport protocols carry almost everything:

    • TCP (Transmission Control Protocol) sets up a connection first, numbers every byte, acknowledges what arrives, resends what's lost, and hands data to the program in order. The web, email and file transfers rely on it.
    • UDP (User Datagram Protocol) fires off independent datagrams with no setup and no guarantees. It's lighter and quicker, which suits DNS lookups, voice and video calls, and games, where a late packet is useless anyway. The newest HTTP, HTTP/3, runs on QUIC, a protocol that builds its own reliability and encryption on top of UDP.

    Before TCP carries any data, the two sides agree on starting sequence numbers in a three-way handshake. Step through it:

    1. SYN. Your browser wants to talk to port 443 on the server. It picks a random starting sequence number (1000 here) and sends a segment with the SYN ("synchronize") flag set.

    2. SYN-ACK. The server replies with both flags set. It acknowledges the browser's number by saying which byte it expects next (1001), and it sends its own random starting number (5000).

    3. ACK. The browser acknowledges the server's number (expecting 5001). Both sides now agree on the numbering, so the connection is open. Notice that one full round trip passed before any real data moved; on a slow network you can feel that delay.

    4. Data. For HTTPS, a TLS handshake comes next (one more round trip with TLS 1.3) to agree on encryption keys and check the server's certificate. Then the HTTP request travels as numbered segments, and the server acknowledges what it receives.

    5. Response. The page comes back the same way. Any segment that isn't acknowledged in time gets sent again. When both sides are finished, they close the connection with FIN segments. UDP skips all of this: no handshake, no acknowledgments, no resends.

    The application layer

    At the top of the stack live the protocols that programs actually speak. HTTP and HTTPS carry the web. DNS looks up names (Section 2.2). SMTP moves email between mail servers, IMAP and POP3 let your mail app read it, SSH gives you a secure remote command line, and FTP is an older file-transfer protocol that SFTP (which runs over SSH) has largely replaced. Each service has a well-known port so clients know where to knock.

    Domain Name System

    Routers work with IP addresses, but people remember names. The Domain Name System (DNS) is the internet's directory: it turns a name like www.example.com into an address like 203.0.113.80. No single computer holds the whole directory. The work is split across a hierarchy of servers run by thousands of organizations, and answers are cached all along the way, so most lookups finish in a few milliseconds.

    Reading a domain name

    Read domain names right to left, from most general to most specific. Each dot-separated part is a label.

    • The invisible root sits at the far right. A name written with a final dot, like www.example.com., is a fully qualified domain name; browsers let you leave the dot off.
    • The top-level domain (TLD) is the last label: com, org, uk, dev.
    • The second-level domain is the label just left of it. In example.com that's example, the part somebody registered.
    • Anything further left is a subdomain the owner creates freely: www, shop, mail, api.

    TLDs come in a few flavors. Generic TLDs (gTLDs) include the originals .com, .org, .net and hundreds of newer ones like .app and .shop. Sponsored TLDs such as .edu, .gov and .mil are limited to qualifying organizations. Two-letter country-code TLDs (ccTLDs) such as .uk, .de and .jp belong to countries and territories, and some add their own second level, which is why British companies register names like example.co.uk. Finally, .arpa is an infrastructure TLD used for reverse lookups from address to name.

    Who hands out names?

    The Internet Corporation for Assigned Names and Numbers (ICANN) coordinates the whole namespace. Each TLD is operated by a registry that keeps the master list of names under it; Verisign, for example, runs .com and .net. You never deal with the registry directly. You rent a name, for one to ten years at a time, from a registrar: a company accredited to sell names in that TLD, which passes your registration on to the registry. Public registration details can be looked up with RDAP, the protocol that officially replaced the older WHOIS service for generic TLDs in January 2025. Personal details are usually redacted for privacy.

    How a name gets resolved

    When your browser needs an address, it doesn't search the internet. It asks a recursive resolver to find the answer for it; that resolver is run by your internet provider, your school or employer, or a public service such as 1.1.1.1 or 8.8.8.8. If the resolver hasn't seen the name recently, it works its way down the hierarchy, and each server along the way either answers or refers it to a server that knows more. Step through a lookup of www.example.com with every cache empty:

    1. You type www.example.com. The browser first checks its own DNS cache. It has never looked up this name, so that's a miss.

    2. The browser asks the operating system's stub resolver, which checks the OS cache and the local hosts file. Still nothing.

    3. The OS sends the question to the recursive resolver configured for your network, normally over UDP port 53 (or an encrypted channel such as DNS over HTTPS). The resolver's cache is empty too.

    4. The resolver asks a root server. The root doesn't know the address, but it knows who runs .com, so it answers with a referral: the names and addresses of the .com TLD servers.

    5. The resolver asks a .com TLD server, which refers it to the name servers for example.com: the NS records that the domain's owner set up through their registrar.

    6. The resolver asks example.com's authoritative server, which finally answers: www.example.com has an A record of 203.0.113.80, with a TTL of 3600 seconds. (The address is illustrative.)

    7. The resolver caches the answer for up to 3600 seconds and passes it back to the OS, which caches it too and hands it to the browser. Anyone else using this resolver in the next hour gets the answer instantly.

    8. With an IP address in hand, the browser opens a TCP connection to 203.0.113.80 on port 443 and sends its HTTP request. The whole lookup took a few dozen milliseconds, and the next one will take almost none.

    That full walk is rare in practice. There are only 13 named root server identities (a.root-servers.net through m.root-servers.net), but each one is really a fleet of machines around the world sharing one address, so the nearest copy answers. And resolvers cache referrals as well as answers, so they seldom need to ask a root server at all.

    Every DNS answer carries a TTL (time to live), in seconds, chosen by the domain's owner. Resolvers, operating systems and browsers may reuse a cached answer until its TTL runs out. Use the lab to see what caching buys you, and what it costs when a site moves.

    Uniform Resource Locators

    A URL (Uniform Resource Locator) is a complete set of directions to one resource on the internet: which protocol to use, which server to contact, and which thing on that server you want. Every link, image, stylesheet, script and form on the web points somewhere with a URL, so reading them fluently pays off every day you write HTML.

      Encoding special characters

      URLs may only contain a limited set of ASCII characters. Anything else must be percent-encoded: each byte is written as % plus two hexadecimal digits.       Hypertext Transfer Protocol

      HTTP is the application-layer protocol of the web. It's a request–response conversation: the client (usually a browser) sends a request, the server sends back exactly one response, and that exchange is done. Loading a single page usually takes dozens of these exchanges: one for the HTML, then one for each stylesheet, script, image and font it refers to.

      In HTTP/1.1 the messages are plain text, so you can read them directly:

      Both messages share one shape: a start line (the request line, or the status line), then headers written as Name: value, then a blank line, then an optional body. The request line holds a method, a path and the protocol version. The status line holds the version, a three-digit status code and a short reason phrase.

      Request methods

      MethodAsks the server to…Typical use
      GETSend a copy of a resource. No body. Safe to repeat.Clicking links, loading images, search forms
      POSTAccept data in the body and act on it. Repeating it may repeat the action.Logins, sign-ups, checkout, posting a comment
      PUTReplace a resource with the body. Repeating it has the same effect.Saving an edited record in an API
      PATCHChange part of a resource.Updating one field of a record

      Plain HTML can only send GET (links, and forms by default) and POST (<form method="post">). The other methods come from JavaScript or other programs talking to APIs.

      Status codes

      Every response begins with a status code, and its first digit tells you the category: 1xx informational, 2xx success, 3xx redirection (look elsewhere, or use your cached copy), 4xx client error (the request was wrong), and 5xx server error (the server failed). You'll meet 200, 301, 304, 404 and 500 constantly.

      Headers
      
    
      Headers carry the metadata of the conversation: who's asking, what formats are acceptable, how big the body is, how long a response may be cached, and much more. The browser writes most request headers for you; the server's software writes most response headers. Here are the ones you'll see most often in DevTools:
      

    
      
      
    
      

    
      HTTP is stateless (and cookies fix that)
      
    
      An HTTP server treats every request as brand new. By itself it doesn't remember that you logged in a second ago or what's in your cart. That statelessness keeps servers simple and easy to scale, but web apps need memory, so they add it with cookies. The server includes a Set-Cookie header in a response; the browser stores that little name–value pair and sends it back in a Cookie header with every later request to the same site. The server looks up the session ID in the cookie and knows who you are. You watched exactly this happen in the lab with POST /login followed by GET /members.
      

    
      HTTPS
      
    
      HTTPS is ordinary HTTP sent through an encrypted TLS connection (usually on port 443). TLS does two jobs: it encrypts everything, including the path, headers, cookies and body, so nobody on the network can read or change it; and it checks the server's certificate, issued by a trusted certificate authority, so you know you're really talking to example.com. Browsers now label plain-HTTP pages "Not secure," and many modern features only work over HTTPS. Free certificates mean there's no reason to publish a site without it.

      Web Browsers
      
    
      A web browser is an HTTP client with a lot of machinery attached: a networking layer that manages connections and caches, a rendering engine that turns HTML and CSS into pixels, a JavaScript engine that runs scripts, plus security features, developer tools and extensions. Its core job sounds simple: fetch the resources for a page and draw them as quickly as possible.
      

    
      Fetching a page
      
    
      The browser requests the HTML document first. As it reads the HTML, it discovers other resources (stylesheets in <link> elements, scripts, images, and fonts named inside the CSS) and requests each one. How many requests can travel at once depends on the protocol. With HTTP/1.1, browsers open up to six connections per host, and each connection carries one request at a time, so extra requests wait in line. HTTP/2 and HTTP/3 multiplex many requests over a single connection. On top of that, the browser cache keeps copies of files, so a repeat visit can skip the network for anything that hasn't expired.

      Browser engines
      
    
      There are dozens of browsers but only three major rendering engines. Google's Blink (a 2013 fork of WebKit) powers Chrome, Microsoft Edge (since 2020), Opera, Brave, Vivaldi and Samsung Internet. Apple's WebKit powers Safari, and on iPhones and iPads Apple has long required every browser, even Chrome, to use WebKit under the hood, with exceptions allowed only recently and only in some regions. Mozilla's Gecko powers Firefox. Each engine pairs with its own JavaScript engine. Because so many browsers share engines, testing your pages in Chrome, Safari and Firefox covers nearly every visitor.
      

    
      
      
    
      

    
      Browsers also give you tools you'll lean on all semester. DevTools (F12) lets you inspect the DOM and CSS, watch network traffic, and run JavaScript in a console. Extensions add features such as ad blocking, password managers and accessibility checkers, using web technologies themselves.
      

    
      
      
    
      
  
      

  
  
      
    
      Web Servers
      
    
      A web server is two things at once: a computer that's always on and connected, and the software on it that listens on ports 80 and 443 and answers HTTP requests. Most production web servers are virtual machines or containers in a data center. Busy sites also put a content delivery network (CDN) in front: a worldwide network of servers that keep copies of files close to users, so a visitor in Tokyo isn't waiting on a server in Virginia for every image.
      

    
      Static and dynamic requests
      
    
      For a static resource, the server's job is easy: map the URL path to a file on disk and send its bytes. Every visitor gets identical content, which is fast and easy to cache. For a dynamic resource, the server runs a program that builds the response on the spot, often after querying a database, so each visitor can get a different page (their cart, their feed, today's prices).       6. MySQL sends back the matching row, and the script drops the name and price into an HTML template, producing a brand-new page.
        7. 
        
      7. PHP hands the finished HTML to nginx, which sends it as an ordinary 200 OK response. The browser can't tell whether a page came from a file or was generated a millisecond ago.
        8. 
      
      
    
      

    
      The server stack
      
    
      A server that runs dynamic sites needs four layers of software, together called its stack:
      
    
      
      
      Operating system
      Mostly Linux (free, stable, and dominant on servers); also Windows Server.
      
      
      Web server software
      Nginx and Apache are the most common; IIS on Windows; Node.js can serve HTTP itself.
      
      
      Database
      MySQL/MariaDB, PostgreSQL, SQL Server, or document stores like MongoDB.
      
      
      Server-side language
      PHP, JavaScript (Node.js), Python, C# (ASP.NET), Ruby, Java.

      Where your site lives: hosting
      
    
      Unless you run a data center, you'll rent space on someone else's servers. The main options, from cheapest and simplest to most flexible:
      
    
        
      
      • Static hosting (GitHub Pages, Netlify, Cloudflare Pages and similar) serves plain files from a CDN, often for free. Perfect for HTML/CSS/JS sites like your course project.
        • 
      
      • Shared hosting puts many customers' sites on one server with a control panel and PHP/MySQL ready to go. Cheap, but you share resources and can't install your own software.
        • 
      
      • A virtual private server (VPS) gives you your own virtual machine with full administrator (root) access, at a modest monthly price.
        • 
      
      • A dedicated server is a whole physical machine that's yours alone: maximum control and isolation, maximum cost.
        • 
      
      • Cloud platforms (AWS, Microsoft Azure, Google Cloud) rent computing by the hour or even by the request ("serverless"), scaling up and down with traffic.
        • 
    
      

    
      
      
    
      

    
      Your own computer as a server: localhost
      
    
      During development you'll run web servers on your own machine. The name localhost and the loopback addresses 127.0.0.1 (IPv4) and ::1 (IPv6) always mean "this computer," so requests to them never leave your machine. Several servers can run at once because each listens on its own port; that's why development URLs look like http://localhost:5500/.       Chapter 2 Review
      
    
      Everything in this chapter fits into one story: what happens between typing an address and seeing a page.
      
    
      
      
      2.1 Protocols
      Data travels as packets through layers: application (HTTP), transport (TCP/UDP and ports), internet (IP addresses), link (Wi-Fi, Ethernet).
      
      
      2.2 DNS
      A resolver walks root → TLD → authoritative server to turn a name into an address, then caches the answer for its TTL.
      
      
      2.3 URLs
      Scheme, host, port, path, query, fragment. Relative URLs resolve against the current page; special characters are percent-encoded.
      
      
      2.4 HTTP
      Stateless request and response: a method and path in, a status code, headers and body out. Cookies add state; TLS adds security.
      
      
      2.5 Browsers
      Fetch resources over several connections or one multiplexed one, then DOM + CSSOM → render tree → layout → paint → composite.
      
      
      2.6 Servers
      Software on an always-on machine that serves static files or runs code with a database (LAMP, MERN…), hosted somewhere or on localhost.
