HTML 1: Introduction

HTML is the skeleton of every web page. In this chapter you'll learn where it came from, how its syntax works, and how to write markup that says what your content means, so browsers, screen readers and search engines all understand it.

What Is HTML and Where Did It Come From?

HTML stands for HyperText Markup Language. Every web page you have ever visited is written in it, and each word in the name tells you something about it:

HyperText

Text that links to other text. Select a link and you jump to another document, on the same computer or across the world. Those links are what make it a web.

Markup

Labels wrapped around content that say what each piece is. Editors once marked up printed drafts by hand ("make this a headline"). HTML does the same job with tags like <h1>.

Language

A fixed vocabulary of elements and rules for combining them. HTML isn't a programming language: it has no variables, loops or logic. It describes content.

HTML never works alone. A modern page has three layers: HTML gives content its structure and meaning, CSS controls how it looks, and JavaScript makes it respond to the user. Switch the layers off one at a time and watch what's left.

A short history of HTML

HTML was invented to share physics papers and grew into the language of the entire web. Along the way it went through standards bodies, browser wars and one big fork in the road: should HTML become strict, or stay forgiving? Explore the milestones.

Select a milestone, or focus the timeline and use the ← → arrow keys.

    Strict XHTML vs forgiving HTML

    Around 2000 the W3C bet the web's future on XHTML: the same elements as HTML, but written under the strict rules of XML. Element names had to be lowercase, every element had to be closed (even empty ones, written <br />), and every attribute value had to be quoted. A page served as true XHTML that broke a single rule showed the user an error message instead of the page.

    Browser makers pushed back. Real pages are full of small mistakes, and users blame the browser, not the author. So HTML5 took the opposite approach: the standard spells out exactly how a browser must recover from every kind of error, so broken markup produces the same page in every browser.     Forgiving doesn't mean correct. The browser's repair is a guess, and it may not match what you meant (look at where the <i> ended up in the overlapping example). That is why you still check your work.

    Who writes the rules?

    W3C

    The World Wide Web Consortium, founded by Tim Berners-Lee in 1994. It published HTML 3.2 through HTML5 and XHTML, and still develops CSS, accessibility guidelines (WCAG) and many other web standards.

    WHATWG

    The Web Hypertext Application Technology Working Group, formed in 2004 by Apple, Mozilla and Opera (Google and Microsoft later joined its steering group). Since 2019 its HTML Living Standard is the one official HTML specification.

    "HTML5" is still the everyday name for modern HTML, but there is no HTML6 coming. The Living Standard is updated continuously, and browsers ship new features (like the <dialog> and <search> elements) as they're ready.

    Validate as you go Because browsers quietly repair your mistakes, you need a tool that shows them. The W3C's free Nu Html Checker checks a page against the Living Standard: paste your code, upload a file, or enter a URL. Fix errors from the top down, since one early mistake (like an unclosed element) often causes several messages further down.

    HTML Syntax

    An HTML document is built from elements. Most elements have three parts: an opening tag, some content, and a closing tag. A tag is the element's name inside angle brackets, and the closing tag adds a forward slash. Extra information goes in attributes, written as name="value" pairs inside the opening tag.

    Void elements

    A few elements can't contain anything, so they have no closing tag. These are void (or empty) elements. An image, for example, is completely described by its attributes. The ones you'll meet most: <br>, <hr>, <img>, <input>, <meta> and <link> (the full list adds area, base, col, embed, source, track and wbr).

    XHTML required a slash on them: <br />. HTML still allows that slash but ignores it. On a non-void element it's a trap: <div /> is just an opening <div>, and it still needs a </div>.

    Nesting

    Elements can contain other elements, which is called nesting. The rule is simple: close elements in the reverse order you opened them, like nested boxes. The last box you opened is the first one you close. When one element sits inside another, the outer one is its parent and the inner one is its child. That family tree is exactly what the browser builds when it reads your page (you'll explore it in 3.4).

    Type or paste some HTML into the checker. It keeps a stack of open elements the same way a parser does, and flags overlapping tags, missing closing tags, stray closing tags and closed void elements. Select an issue to jump to its line.

      Boolean attributes

      Most attributes need a value, but a few, such as checked, disabled, required and hidden, are boolean: just being there means "true."       Whitespace and comments

      Browsers collapse whitespace: any run of spaces, tabs and line breaks in your text displays as a single space. That lets you indent your code neatly without changing the page, but it also means pressing Enter in your editor doesn't start a new line on screen. Use <p> for paragraphs, <br> for a line break inside one (a poem, a street address), and CSS for spacing. Only <pre> (preformatted text) keeps whitespace exactly as typed.

      Semantic Markup
      
    
      Semantic means "relating to meaning." Semantic markup chooses each element for what the content is, not for how it should look. A heading gets <h2> because it's a heading, not because you want big bold text. A group of site links gets <nav> because it's navigation. How any of it looks is CSS's job.
      
    
      This split between structure (HTML) and presentation (CSS) is the most important idea in this chapter. Early HTML mixed the two with tags like <font> and <center>. Those tags are now obsolete.
      
    
      
      
      
    
      
    
      Here's the catch: with CSS, both versions can look identical. The difference is invisible to a sighted user with a mouse, and huge for everyone and everything else that reads your page. A screen reader, for example, lets a blind user jump straight from heading to heading or from landmark to landmark, but only if the markup has headings and landmarks.         Why it's worth the effort
        
    
        
      
        
        
        Screen readers, voice control software and keyboard users depend on real headings, landmarks, lists, links and buttons. You just saw the difference: the div-soup page gives a screen reader user nothing to navigate by. Accessibility is also a legal requirement for many organizations, for example under the Americans with Disabilities Act in the United States and the European Accessibility Act in the EU.
        
      
        
      
        
        
        Search engines read your markup to work out what a page is about. A clear <title>, one <h1>, a sensible heading outline and descriptive link text help them index your page and summarize it in results.
        
      
        
      
        
        
        Semantic markup is easier to read and change. <nav> tells the next developer (or you, three months from now) exactly what a block is, while <div class="d3"> tells them nothing. CSS can also target meaningful elements directly instead of relying on a pile of classes.
        
      
        
      
        
        
        When presentation lives in one shared CSS file instead of being repeated on every element, pages are smaller and a redesign means editing a stylesheet, not every page. Well-structured content is also easy for other software to reuse: reader modes, translation tools, smart speakers and feed readers all rely on it.
        
      
        
    
        

    
        Importance and emphasis: strong, em, b and i
        
    
        Browsers show <strong> and <b> in bold, and <em> and <i> in italics, so they're easy to mix up. Choose by meaning, not by looks:
        
    
          
      
        • <strong> marks importance, seriousness or urgency: Warning: the oven is hot.
          • 
      
        • <em> marks stress that changes the meaning of a sentence. Compare "I never said she ate it" with "I never said she ate it."
          • 
      
        • <b> draws attention without adding importance: keywords in a summary, a product name in a review.
          • 
      
        • <i> marks a different voice or mood: a technical term, a foreign phrase like carpe diem, a ship's name, a character's thoughts.

          2.

          3. 
        
        3. Lines 3 and 8, <head>. The head holds metadata: information about the page. Nothing in it appears in the page area itself.
          4.

          5.

          6. 
        
        6. Line 6, <title>. The page's name, shown in the browser tab, bookmarks, history and search results. It's required, and every page on your site should have its own.
          7. 
        
        7. Line 7, <link>. Connects an external resource, here a stylesheet (Chapter 4). It's a void element.
          8. 
        
        8. Lines 9 and 12, <body>. Everything the visitor sees goes in the body: text, images, links, forms. A page has exactly one.
          9. 
        
        9. Lines 10 and 11, the content. Your content lives inside the body, structured with the elements you'll meet in 3.5 and 3.6.

        The DOCTYPE and quirks mode
        
    
        In the late 1990s browsers were full of bugs, and pages were written to work around them. When browsers finally started following the standards, those old pages would have broken. The fix was the DOCTYPE switch: pages that start with a DOCTYPE get standards mode, and pages without one get quirks mode, which imitates the old bugs. You can check which mode a page is in with document.compatMode.           The DOM: your document as a tree
          
    
          When the browser reads your HTML, it builds the Document Object Model (DOM): a tree of objects, one for each element, each piece of text and each comment. The document is the root. <html> is its element child, and <head> and <body> are the children of <html>, which makes them siblings. Family words describe every relationship: parent, child, sibling, ancestor and descendant. CSS selectors and JavaScript both work by walking this tree, so it pays to get comfortable with it now.

            Quick Tour of HTML Elements
            
    
            HTML has more than 100 elements, but a couple of dozen do most of the work. This tour covers the ones you'll use on nearly every page: headings, paragraphs and divisions, links, inline text elements, images, character entities and lists.
            

    
            Headings
            
    
            HTML has six heading levels, <h1> through <h6>. Together they form the outline of your page, like a book's table of contents: <h1> is the page title, <h2>s are its main sections, <h3>s are subsections of those, and so on. Three rules keep an outline healthy:
            
    
              
      
            • Use one <h1> for the page's main title.
              • 
      
            • Don't skip levels on the way down. The subsections of an <h2> are <h3>s, not <h4>s. Jumping back up (from <h4> to <h2>) is fine.
              • 
      
            • Never choose a level for its size. If you want smaller text, that's a job for CSS.
              •

            Outline
                
      
                
    
                
    
                What about the HTML5 "outline algorithm"? Older tutorials say every <section> or <article> can restart at <h1>. Browsers and screen readers never implemented that idea, and it was removed from the HTML standard in 2022. Use heading levels that match the real structure of the page.
                

    
                Paragraphs, divisions and spans
                
    
                <p> marks a paragraph. <div> (division) is a generic container with no meaning at all: use it to group things for styling or layout when no semantic element fits. <span> is its inline twin, wrapping a few words so CSS can reach them.
                
    
                That brings up a key distinction. Block-level elements such as p, div, headings and lists start on a new line and stretch across their container. Inline elements such as a, span, strong and em flow along inside a line of text.                 Links
                
    
                The anchor element <a> makes a link, and its href attribute says where it goes. The destination can take several forms:
                
    
                
      
                
        
                KindExample hrefGoes to
                
        
          
                Absolute URLhttps://www.w3.org/A full address with the protocol. Use it for other websites.

Screen reader users often pull up a list of all links on a page, and a list of "click here, click here, click here" tells them nothing.
                

    
                Relative paths
                
    
                A relative path is a set of directions starting from the folder the current file is in:
                
    
                  
      
                • about.html (or ./about.html): a file in the same folder.
                  • 
      
                • images/logo.png: go down into the images folder.
                  • 
      
                • ../index.html: go up one folder. .. means "the parent folder."
                  • 
      
                • ../../css/style.css: up two folders, then down into css.
                  • 
    
                
    
                Always use forward slashes, and match upper and lower case exactly. Most web servers treat Logo.png and logo.png as different files, even if your laptop doesn't.

                  Images
                  
    
                  The <img> element embeds an image. It's a void element with two required attributes: src, the path or URL of the image file, and alt, a text alternative.
                  
    
    
                    
      
                  • alt is read aloud by screen readers, shown when the image fails to load, and used by search engines. Describe what the image communicates in its context, in a sentence or less.
                    • 
      
                  • If an image is purely decorative, keep the attribute but leave it empty: alt="". Screen readers then skip it. Leaving alt out entirely is different, and worse: many screen readers read the file name instead.
                    • 
      
                  • width and height (in pixels, no unit) let the browser reserve space before the file arrives, so the page doesn't jump around as images load.
                    • 
      
                  • loading="lazy" tells the browser not to download an image until it's about to scroll into view.
                    • 
    
                  
    
                  Pick the format for the job: JPEG for photos, PNG for graphics that need sharp edges or transparency, SVG for logos and icons (it's vector-based, so it stays crisp at any size), GIF for simple animations, and WebP or AVIF, modern formats that produce smaller files and work in all current browsers.

                    Character entities
                    
    
                    Some characters are special in HTML: < starts a tag and & starts an entity. To show them as ordinary text, you write a character entity: an ampersand, a name or number, and a semicolon. &lt; displays <, and &amp; displays &.
                    
    
                    Every character also has numeric forms: &#169; (decimal) and &#xA9; (hexadecimal) both display ©, just like &copy;. Because your pages declare UTF-8, you can type most symbols (é, ©, —, emoji) directly. In practice you only need entities for <, &, quotation marks inside attribute values, and invisible characters such as the non-breaking space &nbsp;, which keeps two words on the same line, as in 10&nbsp;km.

                    Lists
                    
    
                    HTML has three kinds of list:
                    
    
                      
      
                    • Unordered <ul>: items whose order doesn't matter, like ingredients, features or a navigation menu. Bullets by default.
                      • 
      
                    • Ordered <ol>: items whose sequence matters, like steps or rankings. Numbered by default. The start, reversed and type attributes control the numbering.
                      • 
      
                    • Description <dl>: groups of terms (<dt>) and descriptions (<dd>), like a glossary or FAQ.
                      • 
    
                    
    
                    List items (<li>) are the only elements that belong directly inside <ul> and <ol>. To nest a list, put the whole inner list inside an <li>, not between two items.

                    HTML5 Semantic Structure Elements
                    
    
                    Before HTML5, page layouts were built almost entirely from <div>s with ids and classes like header, nav, content and footer. When HTML5's editors studied real pages, the same names kept turning up, so they made the most common ones into real elements. Now the markup itself says which part of the page is which, and every browser and screen reader understands it.
                    
    
                    
      
      
    
                    

    
                    The structure elements
                    
    
                    
      
                    <header>
                    Introductory content: a logo and site name, a heading, maybe navigation. A page can have several, since an article can have its own header too.
                    page-level: banner landmark
                    
      
                    <nav>
                    A major block of navigation links, like the main menu or a table of contents. Not every group of links needs one.
                    navigation landmark
                    
      
                    <main>
                    The dominant, unique content of the page. Only one visible <main> per page, placed in <body> (or a plain <div>), never inside article, aside, header, footer, nav or section.
                    main landmark
                    
      
                    <article>
                    A self-contained piece that makes sense on its own: a blog post, a news story, a product card, a user comment.
                    
      
                    <section>
                    A thematic group of content, normally with a heading: a chapter, the "Contact" part of a page. Not a generic wrapper.
                    
      
                    <aside>
                    Content tangentially related to what's around it: a sidebar, a pull quote, related links, an ad.
                    complementary landmark
                    
      
                    <footer>
                    Closing information for the page or for an article: author, copyright, related links, contact details.
                    page-level: contentinfo landmark
                    
      
                    <figure>
                    Self-contained content the text refers to, such as an image, chart or code listing, with an optional <figcaption>.

                      article, section, aside or div?
                      
    
                      These four cause the most confusion. The short version: <article> is self-contained, <section> is a themed part of something bigger, <aside> is tangential, and <div> means nothing at all. When you're not sure, answer the questions in order:
                      

    
                      
      
                      
        
      
                      
      
                        
      
                        
      
    
                        

    
                        figure, details and time
                        
    
                        
      
                        
        
                        <figure> wraps self-contained content that the main text refers to: an image, a diagram, a chart, a code listing or a quotation. <figcaption>, as its first or last child, gives it a caption. A good test: if you moved the figure to an appendix, the text would still make sense.
                        
        
                        
          
          
        
                        
      
                        
      
                        
        
                        <details> creates a disclosure widget that opens and closes with no JavaScript. The <summary> is the clickable label. When it opens, the browser adds the open attribute; when it closes, the browser removes it. Try it and watch the markup:
                        
        
                        
          
                        
            
                        What's on the Margherita?
                        Tomato, fresh mozzarella, basil and olive oil.
                        
            
                        
          
                        
          
                        
            
                        Give several <details> the same name and they act as an accordion: opening one closes the others (supported in all major browsers since 2024).
                        
            
                        Do you deliver?
                        Yes, within 3 miles.
                        
            
                        Are there vegan options?
                        Every pizza can be made with vegan cheese.
                        
            
                        Can I book a table?
                        Tables for 6 or more can be booked online.
