CSS 1: Selectors and Basic Styling

HTML gives a page its structure; CSS decides how it looks. In this chapter you will write rules, aim them with selectors, predict which rule wins a conflict, size boxes to the exact pixel, and set text that is comfortable to read.

What Is CSS?

CSS (Cascading Style Sheets) is the language that controls how HTML is presented: colors, fonts, spacing, sizes, borders and layout. HTML says what something is (a heading, a list, a link). CSS says how it looks.

Keeping those two jobs apart is called separating content from presentation. It pays off fast:

  • One file styles every page. A redesign means editing one stylesheet, not 200 HTML files.
  • Faster pages. The browser downloads the stylesheet once, caches it, and reuses it on every page.
  • One page, many devices. The same HTML can look right on a phone, a wide monitor, or a printed sheet.
  • Cleaner HTML. Markup that only describes meaning is easier for screen readers, search engines, and you to understand.

Versions: from CSS1 to modules

CSS has grown in stages. Knowing the history explains a phrase you will hear constantly ("CSS3") and why there is no single "CSS4" to download.

  1. 1996CSS1. Fonts, colors, text, margins, borders.
  2. 1998CSS2. Positioning, media types (screen vs print), more selectors.
  3. 2011CSS 2.1. A cleaned-up CSS2 that became the stable foundation every browser agreed on.
  4. 2011 →"CSS3" modules. After 2.1, CSS was split into separate modules (Selectors, Color, Backgrounds and Borders, Flexbox, Grid, and dozens more), each moving at its own pace.
  5. TodayLevels, not versions. Modules have level numbers (Selectors Level 4, Color Level 4...). The working group publishes a yearly "snapshot" of what is stable, and browsers ship features one at a time.

CSS Syntax

A stylesheet is a list of rules. Each rule has two parts: a selector that picks which elements to style, and a declaration block in curly braces that says what to change. Inside the block, each declaration is a property, a colon, a value, and a semicolon.

h1, .title {
  color: #1F4FD1;
  font-size: 2rem;
}

A few syntax facts that save hours of debugging:

  • Whitespace and line breaks do not matter. h1{color:navy} works, but one declaration per line is far easier to read.
  • The semicolon separates declarations. It is optional after the last one, but always add it so the next line you add does not break.
  • Comments are written /* like this */. (// is not a CSS comment.)
  • Grouping: separate selectors with commas (h1, h2, h3 { }) to give them the same declarations.
  • Browsers skip what they do not understand, silently. A typo does not show an error; that declaration (or sometimes the whole rule) just disappears. That is why a tiny slip can make "nothing happen."

Color values

Every color on a screen is a mix of red, green and blue light. CSS lets you write that mix in several notations. Most of them can describe exactly the same colors; each one is simply easier for a particular job. Named colors (tomato, navy) are easy to read. Hex (#1f4fd1) packs red, green and blue into two hex digits each (00 to ff). rgb() uses numbers from 0 to 255, and hsl() describes hue (an angle on the color wheel), saturation and lightness, which makes it easy to create lighter or darker shades of one color. Add an alpha value for transparency: rgb(31 79 209 / 50%) or #1f4fd180.

The examples below all use the Riverside Hiking Club's brand green, #2f6f4e, written each way.

What it is. Nearly 150 English color names, such as red, tomato, navy and rebeccapurple, plus two useful keywords: transparent (fully see-through) and currentColor (whatever this element's text color is).

When to use it. While learning and for quick experiments, when you just want to see something change. In a finished stylesheet, white, black and transparent are perfectly normal. currentColor is handy for a border or icon that should always match the text around it.

Watch out. A brand's colors almost never match a name exactly, so real designs use hex or hsl(). The names are not consistent either: darkgray (#a9a9a9) is actually lighter than gray (#808080). And gray text on a white background has a contrast of only 3.9 : 1, below the 4.5 : 1 that body text needs. Names are one word with no spaces: darkgreen, not dark green.

What it is. A # followed by three pairs of hexadecimal (base 16) digits: one pair each for red, green and blue. Hex digits run from 0 to 9 and then a to f (which stand for 10 to 15), so a pair can go from 00 (none of that light) to ff (the full amount, 255). To turn a pair into a normal number, multiply the first digit by 16 and add the second.

Worked example. #2f6f4e: 2f = 2 × 16 + 15 = 47 red, 6f = 6 × 16 + 15 = 111 green, 4e = 4 × 16 + 14 = 78 blue. More green than anything else, and all three fairly low, so it is a dark forest green. It is the same color as rgb(47 111 78). A three-digit hex is shorthand that doubles each digit: #f60 means #ff6600, a bright orange. It only works when both digits of every pair are the same.

When to use it. It is the most common notation in real stylesheets, because design tools, color pickers and brand guides hand you hex codes. Copy the code exactly and the color matches everywhere.

Watch out. Hex is hard to adjust by eye: which digits would you change to make #2f6f4e slightly lighter? (hsl() makes that easy.) Do not forget the #: without it the value is invalid and the browser drops the declaration. Upper and lower case mean the same thing (#2F6F4E = #2f6f4e). An eight-digit hex adds transparency; see the Alpha tab.

What it is. The same three amounts of red, green and blue as hex, written as ordinary numbers from 0 to 255. rgb(0 0 0) is black (no light at all), rgb(255 255 255) is white (every light at full), and any three equal numbers make a gray.

When to use it. When a color picker or an image editor gives you RGB numbers, and when you need transparency: add a slash and an alpha value, rgb(47 111 78 / 50%). Because the numbers are plain decimals, it is also the easiest notation for seeing how much of each light is in a color.

Watch out. A "slightly lighter green" means raising all three numbers by the right amounts, which is guesswork; hsl() does that with one number. There are two ways to write it: the modern rgb(47 111 78) with spaces, and the older rgb(47, 111, 78) with commas. Both work, but do not mix them: rgb(47, 111 78) is invalid and silently dropped.

What it is. A color described the way people talk about color. Hue is an angle on the color wheel, from 0 to 360: 0 is red, 60 yellow, 120 green, 180 cyan, 240 blue, 300 magenta. Saturation runs from 0% (gray) to 100% (full, vivid color). Lightness runs from 0% (black) through 50% (the pure color) to 100% (white).

When to use it. Whenever you need a family of shades from one color: keep the hue and saturation, change only the lightness. The club's green is about hsl(150 40% 31%). Lower the lightness to 22% and you have a darker green for a button's hover state; raise it to 94% and you have a pale tint for a background. With hex you would have to recalculate all six digits each time.

Watch out. The same lightness does not look equally bright in every hue. hsl(60 100% 50%) (yellow) is so bright that white text on it has a contrast of just 1.07 : 1, while hsl(240 100% 50%) (blue) is dark enough to reach 8.6 : 1. So check the contrast of every shade you make; the Color lab below measures it for you.

What it is. A fourth value that sets how opaque (solid) the color is: 1 or 100% is solid, 0 is invisible, and anything in between lets the background show through. The modern syntax puts it after a slash: rgb(0 0 0 / 60%) or hsl(150 40% 30% / 0.5). Hex adds a fourth pair: #2f6f4e80.

Worked example. In #2f6f4e1a, the last pair 1a = 1 × 16 + 10 = 26, and 26 ÷ 255 ≈ 0.10: the brand green at 10% strength, a faint tint of whatever is behind it. 80 = 128, which is about 50%.

When to use it. A dark, see-through panel behind white text on top of a photo; a faint tinted background when the pointer is over a table row; soft shadows (the card in the px units tab uses rgb(0 0 0 / 0.1)).

Watch out. A see-through color looks different depending on what is behind it, so check contrast against the real background, not against white. Alpha on a color is also not the same as the opacity property: opacity: 0.5 fades the whole element, text and children included, while an alpha background fades only the background and leaves the text solid.

Which notation should I pick?
  • A color from a design file or brand guide: hex, copied exactly. Example: color: #2f6f4e;
  • Several shades of one color (hover, tint, border): hsl(), changing only the lightness. Example: background-color: hsl(150 40% 22%);
  • Something see-through (an overlay, a tint, a shadow): rgb() or hsl() with / alpha. Example: background-color: rgb(0 0 0 / 60%);
  • Plain white, black or invisible: the names. Example: color: white;
  • Whatever you pick: check the contrast. Body text needs at least 4.5 : 1, large text 3 : 1. Try your colors in the lab below.

Units: px, em, rem, %, vw, vh, ch

Every length in CSS (a width, a font size, some padding) is a number plus a unit: 16px, 1.5rem, 50%. Leave the unit off and the browser ignores the whole declaration. The one exception is 0, because zero pixels and zero percent are the same thing.

Units come in two families:

  • Absolute units are a fixed size. px is the only one you will use on screen. 20px is 20px on every page, in every box, on every device.
  • Relative units are a fraction of something else: the text size, the parent's width, or the browser window. When that something changes, the length changes with it. That is what lets one stylesheet look right on a phone and on a wide monitor, and lets the page grow when a visitor turns up their browser's text size.

What it measures. A fixed length. One CSS pixel is about 1/96 of an inch seen at arm's length. It is not a dot on the screen: a high-resolution phone draws each CSS pixel with two or three physical dots, so 1px looks about the same size on every device.

When to use it. For details that should never grow or shrink with the text: hairline borders, outlines, the offset and blur of a shadow, the rounding on a small corner.

When not to. Font sizes. Many people set their browser's default text size larger so they can read comfortably. Text in rem or em grows with that setting; text in px ignores it.

What it measures. A multiple of the element's own font size. If a button's text is 20px, then 1em is 20px and 0.5em is 10px. On the font-size property itself, em uses the parent's font size, because the element's own size is the thing being set.

When to use it. For spacing that should stay in proportion to the text beside it: padding inside buttons, badges and tags, or the gap between an icon and its label. Make the text bigger and the padding grows with it, so a large button keeps the same shape as a small one.

When not to. Font sizes on elements that nest inside each other. em multiplies at every level: font-size: 1.2em inside 1.2em inside 1.2em ends up 1.2 × 1.2 × 1.2 = 1.728 times the size. The explorer below shows this happening. Use rem for font sizes instead.

What it measures. "Root em": a multiple of the font size on the <html> element, the root of the page. Browsers set that to 16px by default, so 1rem = 16px, 1.5rem = 24px and 0.875rem = 14px. Unlike em, it means the same thing everywhere on the page, however deeply an element is nested.

When to use it. Font sizes (the body text, h1 to h3) and spacing that should be consistent across the whole page, such as the space between sections. Because everything is based on the browser's text-size setting, a visitor who turns it up gets a larger page that keeps its proportions.

Converting from a design in px. Divide by 16: 24px is 1.5rem, 12px is 0.75rem, 40px is 2.5rem.

What it measures. A percentage of something that belongs to the parent. For width, it is the parent's content width: width: 50% inside a 600px-wide parent is 300px, and the same rule gives 180px inside a 360px phone column. Other properties measure against other things: font-size: 150% is 1.5 × the parent's font size, and padding and margin in % are based on the parent's width, even for top and bottom.

When to use it. For sizes that should adapt to whatever box they are in: a form field that fills its form, an image that must never be wider than its column, two boxes that share a row.

When not to. Heights, usually. height: 50% only works when the parent has a height set explicitly; most parents are as tall as their content, so the percentage has nothing to measure against and is ignored.

What they measure. The viewport, the visible area of the browser window. 1vw is 1% of its width and 1vh is 1% of its height. They ignore the parent entirely: in a 1280px-wide window, 50vw is 640px no matter where the element sits.

When to use them. For layouts tied to the screen itself: a welcome banner that fills the whole window (min-height: 100vh), or a big headline that shrinks on phones and grows on wide monitors.

Watch out. On phones the address bar slides in and out, so 100vh can be a little taller than what is visible; the newer unit 100dvh ("dynamic") follows the visible height. width: 100vw includes the scrollbar on desktop computers and makes the page scroll sideways, so use width: 100% for full-width boxes. Never set body text in vw alone: it becomes tiny on phones and ignores the visitor's text-size setting.

What it measures. The width of the "0" (zero) character in the element's current font. Most letters are a little narrower than a zero, so 60ch holds a few more than 60 characters of ordinary text. It changes with the font and the font size, which is exactly what you want when sizing a box to fit text.

When to use it. To keep lines of text a comfortable length. Lines of roughly 45 to 75 characters are the easiest to read; much longer, and your eye loses its place jumping back to the start of the next line. It is also handy for inputs that hold a known number of characters, such as a ZIP code.

Which unit should I pick?
  • Text size: rem. Example: font-size: 1.125rem;
  • Padding inside a button, badge or tag: em, so it grows with the text. Example: padding: 0.5em 1em;
  • Space between sections and paragraphs: rem. Example: margin-bottom: 2rem;
  • Borders and shadows: px. Example: border: 1px solid gray;
  • A width that should fit its container: %. Example: width: 100%;
  • A readable column of text: ch. Example: max-width: 65ch;
  • A section as tall as the screen: vh. Example: min-height: 100vh;

Location of Styles

You can put CSS in three places. All three feed into the same cascade, but they are not equally useful.

An inline style lives in a style attribute on one element. It affects only that element.

Use sparingly Inline styles mix presentation back into your HTML, cannot be reused, and beat every normal rule in your stylesheets, which makes them hard to override later. They are handy for quick tests and for values set by JavaScript.

When to use it. Almost never in a finished site. It is fine for a quick test ("does red work here?"), and you will see it in HTML emails, where many email programs ignore stylesheets, and in values that a script sets while the page runs.

Watch out. Ten paragraphs styled this way means ten places to edit when the color changes. Because an inline style beats your stylesheet, a rule in styles.css cannot change it later without !important. And a style attribute cannot describe states or parts: there is no way to write :hover or ::before inside it.

An embedded style sheet (also called internal) sits in a <style> element, normally in the <head>. It affects only this one page.

Good for single-page experiments, demos, and styles that truly belong to one page only.

When to use it. A page with a look that no other page shares, a quick experiment, or a demo you want to keep in one file. This lesson page does both: it links the course's shared stylesheet, and keeps the few styles that only its own widgets need in a <style> element.

Watch out. The moment a second page needs the same styles, you are tempted to copy the <style> block, and now two copies must be kept in step. When two pages share styles, move them into an external file. Keep the <style> element in the <head> so the styles are ready before the content is drawn.

An external style sheet is a separate .css file. Every page that links to it gets its styles.

Best practice One file for the whole site: consistent design, one place to edit, and the browser caches it so later pages load faster. This is what your project will use.

When to use it. For every real site, even a small one: add the same <link> to every page and they all share one look.

Watch out. If the href path is wrong, nothing warns you: the browser quietly fails to download the file and the page appears unstyled, like the "No CSS" view in 4.1. The Console or Network panel in DevTools shows the failed request. A page inside a subfolder needs a path that climbs out first, such as href="../css/styles.css". And if an edit does not seem to show up, the browser may be using its cached copy: reload with Ctrl+Shift+R (Cmd+Shift+R on a Mac).

A stylesheet can pull in another stylesheet with @import. It must come before every other rule in the file.

Prefer <link> The browser cannot discover an imported file until it has downloaded and read the file that imports it, so downloads happen one after another instead of in parallel. Several <link> elements are usually faster. Imported rules count as if they were written where the @import sits: before the rest of the importing file.

When to use it. Rarely, in plain CSS. You will meet it in older sites and in the instructions of some font services. It is common in preprocessors such as Sass (4.8), which combine the files into one before the browser ever sees them, so the slowdown does not apply.

Watch out. An @import placed after any normal rule is ignored, silently. Its path is measured from the CSS file that contains it, not from the HTML page.

When the same element gets conflicting values from different places, which one wins? The short version for now (4.5 has the full story):

  1. An inline style beats any normal rule in a stylesheet.
  2. Between stylesheets, a more specific selector wins (for example, an id beats a tag name).
  3. If the selectors are equally specific, the rule that appears later wins. "Later" means later in the page's order of <link> and <style> elements, so an external sheet linked after a <style> element beats it. Embedded styles do not automatically beat external ones; they usually just come later.

Selectors

A selector is a pattern that matches elements in the page. The better your selectors, the less extra markup you need: instead of adding a class to every link in the navigation, you can write nav a and reach them all.

Selectors come in a handful of kinds. Some match elements by what they are (their tag, class, id or attributes), some by where they are (inside something, or next to something), and some by what state they are in (hovered, first in a list). What it matches. A bare tag name such as p, h2 or a matches every element of that type on the page, wherever it is. The universal selector * matches every element of every type.

When to use it. For site-wide defaults, the rules you write first at the top of a stylesheet: the font and text color on body, the size of every h1, the spacing of every paragraph, the color of every link. Use * almost only for the box-sizing reset you will meet in 4.6.

Watch out. An element selector hits every element of that type, including ones you forgot about: a p rule also restyles the paragraphs in the footer and inside every card. When a style belongs to one area, use a class or a descendant selector instead. Element selectors score only 0-0-1 for specificity, which is exactly right for defaults: any class can override them. Be careful with * and inherited properties: * { color: navy; } sets the color on every element directly, so a child can no longer inherit a different color from its parent.

What it matches. A dot and a name, such as .featured, matches every element whose class attribute contains that name, whatever its tag. An element can carry several classes separated by spaces (class="trip featured") and matches a selector for any one of them. Join selectors with no space to require both: p.note is a <p> that has the class note, and .trip.featured is an element with both classes.

When to use it. Most of the time. Classes are the everyday styling tool: put a class on the elements that should share a look and write one rule for it. A class can be reused on any number of elements of any type, and its specificity (0-1-0) is strong enough to override element defaults while staying easy to override with another class.

Watch out. The dot belongs only in the CSS: write class="featured" in the HTML and .featured in the stylesheet. Class names are case-sensitive, so .Featured does not match class="featured". Name a class after what the thing is (.trip-card, .warning), not how it looks (.green-box), so the name still makes sense after a redesign. And mind the space: p.note and p .note mean different things.

What it matches. # and a name matches the one element with that id. An id must be unique: no two elements on a page may share it.

When to use it. Ids have important jobs outside CSS: they are the targets of in-page links (<a href="#signup"> jumps to id="signup"), they connect a <label for="…"> to its input, and JavaScript uses them to find elements. For styling, you rarely need them.

Watch out. An id selector scores 1-0-0, which beats any number of classes. That sounds useful until you want to change one small thing about that element: every later override now needs an id too. Style with a class, even for a one-off, and keep ids for links, labels and scripts. The # goes in the CSS and in link addresses, never in the id attribute itself, and using the same id twice is invalid HTML.

What it matches. A comma-separated selector list matches everything that any of its selectors matches. h1, h2, h3 { … } is shorthand for writing the same declarations in three separate rules.

When to use it. Whenever different selectors should share the same declarations: one font and color for all the headings, the same look for real buttons and links styled as buttons. The value then lives in one place, so a later change is one edit instead of three.

Watch out. A comma and a space are completely different: h2, p means "every h2 and every p", while h2 p means "a p inside an h2". Each selector in the list keeps its own specificity. And if one selector in the list is invalid, whether from a typo or a stray trailing comma, the browser throws away the whole rule, not just the broken part.

What they match. A space between two selectors (nav a) is the descendant combinator: it matches an a anywhere inside a nav, at any depth, whether child, grandchild or deeper. A > (.menu > li) is the child combinator: the second element must be a direct child of the first, exactly one level down.

When to use them. Use a descendant selector to style things by where they sit, without putting a class on each one: links in the navigation look different from links in the article, paragraphs inside a card get smaller text. Use the child combinator when the same structure nests inside itself and you only want the outer level, such as the top-level items of a menu but not the items of a sub-menu inside it.

Watch out. Descendant selectors reach further than you expect: .menu li also styles every li of any list nested inside the menu. Child selectors break just as easily the other way: nav > a matches nothing when the links sit inside a <ul>, because then their parent is an li, not the nav. And every part adds specificity: nav a scores 0-0-2, so a later a { color: … } rule (0-0-1) will not change the menu links. Two parts is usually enough; long chains are hard to override.

What they match. Siblings are elements with the same parent. h3 + p (the adjacent sibling combinator) matches a p that comes immediately after an h3, with no other element in between. .cancelled ~ p (the general sibling combinator) matches every p that comes anywhere after a .cancelled element under the same parent. Both only look forward, never at earlier siblings, and never inside other elements.

When to use them. + is handy for "the thing right after": the first line after a heading, or a divider between list items with li + li (every item that has an item before it, so the first one gets no line). ~ is needed less often; it styles "everything after this point" within the same parent.

Watch out. + needs the two elements side by side: put an <img> between the heading and the paragraph and the rule stops matching. (Text and comments in between do not count; only elements do.) And ~ matches all later siblings, including ones far below, so it can reach further than you meant.

What it matches. Square brackets match elements by their attributes. [title] matches any element that has a title attribute. [type="email"] matches when the value is exactly email. Three operators match part of the value: ^= starts with, $= ends with, *= contains.

When to use it. When the HTML already says what something is, so you do not need to add a class: style form fields by type (input[type="checkbox"]), mark links to other sites (a[href^="https"]), or highlight links that download a PDF (a[href$=".pdf"]). An attribute selector scores 0-1-0, the same as a class.

Watch out. Values are compared as text, character by character, and usually case matters: [href$=".pdf"] misses href="MAP.PDF" (add i before the bracket, [href$=".pdf" i], to ignore case). Put quotes around the value; they are required when it contains a dot, a space or starts with a digit, and never wrong. [class="note"] only matches when the whole attribute is exactly note, so class="note urgent" fails: use .note for classes. And a[href^="https"] also catches full addresses that point to your own site.

Which selector should I pick?
  • Site-wide defaults (body text, headings, links): an element selector. Example: p { line-height: 1.6; }
  • Anything you are styling on purpose: a class. Example: .trip-card { padding: 1rem; }
  • The same look for several things: a selector list. Example: h1, h2, h3 { color: #2f6f4e; }
  • Everything of one kind inside one area, without adding classes: a descendant selector. Example: nav a { color: white; }
  • Only the outer level of something nested: the child combinator. Example: .menu > li
  • Lines or space between repeated items: the adjacent sibling combinator. Example: li + li { border-top: 1px solid #c8d3cc; }
  • Form fields by type, links by address: an attribute selector. Example: input[type="email"]
  • Ids: for link targets, labels and scripts. Style the same element with a class instead.

What they match. :hover matches an element while the mouse pointer is over it. :active matches while it is being pressed: the mouse button is down, or a finger is on the screen. Links have two more states: :link (an address not visited yet) and :visited (an address already in the browser's history).

When to use them. To give feedback: a link changes color under the pointer, a button darkens when hovered and looks pushed in while clicked, a table row lights up so the eye can follow it across.

Watch out. Phones and tablets have no hover: a finger either taps or does not. So hover may only add feedback; never hide something people need (a menu, a price, the only copy of some instructions) until the pointer is over it. Give keyboard users the same feedback with :focus-visible (next tab). For links, write the four states in the order :link, :visited, :hover, :active (remember "LoVe HAte"). They all have the same specificity, so the later rule wins: a :hover color written before :visited would lose to it, and visited links would never change on hover. For privacy, :visited may only change colors.

What it matches. An element has focus when it will receive the keyboard: the text box you are typing in, or the link or button you reached by pressing Tab. :focus matches whenever an element has focus, however it got it. :focus-visible matches only when the browser decides a visible marker is needed: always for text fields, and for links and buttons when the visitor is using the keyboard, but not after a mouse click.

When to use it. To design a focus ring that fits your site instead of the browser's default one. :focus-visible is the usual choice for links and buttons: keyboard users always see where they are, and mouse users do not get a ring after every click.

Watch out. Never remove the focus outline (outline: none) without putting something at least as visible in its place. People who navigate with a keyboard, including many people with motor disabilities, rely on it to know where they are on the page; without it they are lost. Try it now: press Tab a few times on this page and watch the ring move from link to link.

What they match. These match an element by its position among its siblings. :first-child and :last-child match the first and last. :nth-child() takes a pattern: odd (1st, 3rd, 5th...), even (2nd, 4th, 6th...), a single number such as 3 (only the third), or a formula such as 3n (every third: 3, 6, 9...). Counting starts at 1, not 0.

When to use them. For repeated items where every piece of HTML looks the same: zebra stripes on table rows, removing the extra space under the last item of a list, a special look for the first card. You get the effect without adding a class to every other row by hand, and it stays correct when rows are added or removed.

Watch out. p:first-child means "a p that is the first child of its parent", not "the first p". If an <h2> comes first, p:first-child matches nothing at all. When you mean "the first p among its siblings", use p:first-of-type. Likewise, :nth-child() counts every sibling element, whatever its tag.

What it matches. :not(X) matches elements that do not match X. li:not(:last-child) is every list item except the last; input:not([type="checkbox"]) is every input except checkboxes.

When to use it. When "all of these except one kind" is shorter than listing the ones you want: a divider under every item but the last, one width for every text-like field but not for checkboxes and radio buttons.

Watch out. On its own it reaches everywhere: :not(p) matches <html>, <body> and every other element that is not a paragraph. Always attach it to something, as in li:not(…). It is as specific as its argument: :not(.done) scores 0-1-0, and :not(#main) scores 1-0-0.

What they are. Two extra boxes the browser can generate inside an element: ::before becomes its first child and ::after its last. They only appear when you give them a content property, even an empty one (content: "";), and you style them like any other element.

When to use them. For decoration that does not belong in the HTML: an arrow after "Read more" links, a small colored bar in front of each section heading, the check marks you switched on in the lab above.

Watch out. Generated content is not really part of the page's text. It cannot be selected or copied, and screen readers are inconsistent: some read it aloud, some skip it. So anything a reader must know, such as a price, a warning, "(required)" or "opens in a new tab", belongs in the HTML. Also, ::before and ::after generally do not work on elements that cannot hold content, such as <img>, <input> and <br>.

What they are. ::first-letter is the first letter of a block of text, and ::first-line is its first line as drawn on screen. Neither exists in the HTML: the browser works them out as it lays out the page.

When to use them. Magazine-style touches: a large, colored first letter (a "drop cap") at the start of a story, or the first line of an article in small capitals to draw the reader in.

Watch out. The first line depends on the width of the window, so a phone and a monitor show different words in that style (switch on the ::first-line rule in the lab above and resize the window to see it). Both only work on block elements such as <p>, not on inline ones such as <span> or <a>. And only some properties apply: fonts, colors, backgrounds and text spacing work; things like width do not.

What it is. The hint text inside an empty form field, taken from its placeholder attribute. It disappears as soon as the visitor starts typing.

When to use it. To match the hint text to your design, or to make the browser's very light default gray a little easier to read.

Watch out. A placeholder is not a label. It vanishes while the person types, so they can forget what the field was for, and some screen readers do not announce it. Always keep a real <label>. Make the hint dark enough to read (aim for 4.5 : 1 like other text) but styled differently from typed text, for example in italics, so nobody mistakes it for an answer already filled in.

Which one should I pick?
  • Feedback when the pointer is over something: :hover, always paired with :focus-visible for keyboard users. Example: a:hover, a:focus-visible { … }
  • A clear focus ring: :focus-visible. Example: outline: 3px solid #2f6f4e;
  • Zebra stripes on a table: :nth-child(). Example: tr:nth-child(even)
  • Something on every item except the last: :not(). Example: li:not(:last-child)
  • A decorative icon, arrow or bar: ::before or ::after. Never for information the reader needs.
  • A drop cap: ::first-letter. Example: p::first-letter { font-size: 2em; }
  • Hint text in form fields: ::placeholder, with a real <label> as well.

The Cascade: How Styles Interact

Almost every element receives declarations from several places at once: the browser's built-in stylesheet, your stylesheets, maybe an inline style. When two declarations try to set the same property on the same element, the cascade picks exactly one winner. Three ideas cover almost every case: inheritance, specificity, and location (order).

Inheritance

Some properties flow from a parent to its children automatically. They are mostly about text: color, font-family, font-size, font-weight, font-style, line-height, letter-spacing, text-align, list-style. That is why setting font-family once on body changes the whole page.

Box properties do not inherit: border, margin, padding, background, width, height. Imagine if they did: a border on <main> would put a border around every paragraph inside it.

Inherited values are the weakest of all. Any rule that targets the element itself beats them, including the browser's own rules. That explains two classic surprises you can see below: links keep their blue color, and buttons keep their own font.

Specificity

When two rules set the same property on the same element, the one with the more specific selector wins. The browser scores each selector as three numbers, often written A-B-C:

The universal selector * and combinators (space, >, +, ~) add nothing. An inline style beats every selector, which is why it is sometimes drawn as a fourth column in front: 1-0-0-0.

Three functional pseudo-classes have special rules: :not(), :is() and :has() count as their most specific argument, and :where() always counts zero, which makes it handy for easy-to-override defaults.

The Box Model

Every element is drawn as a rectangle, a box, built from four layers. From the inside out:

Content: the text or image itself. width and height set its size (by default).
Padding: space between the content and the border. The element's background shows here.
Border: the line around the padding: border: 2px solid gray;
Margin: transparent space outside the border that pushes other boxes away.

These are the same colors your browser's DevTools use when you inspect an element, so what you learn here transfers directly. Margin and padding have four sides, and their shorthands go clockwise from the top: margin: 10px 20px 30px 40px means top 10, right 20, bottom 30, left 40. Two values mean top/bottom then left/right; margin: 0 auto centers a block that has a width.

Block, inline and inline-block

Every element also has a display type that decides how its box behaves in the flow of the page:

  • block (div, p, h1, ul, section...): starts on a new line, stretches to fill the available width, and respects width, height and all margins.

CSS Text Styling

Most of a web page is text, so typography does more for a design than almost anything else. CSS splits the job into font properties (which typeface, how big, how heavy) and text properties (alignment, spacing, decoration, case).

Font stacks and generic families

font-family takes a list called a font stack. The browser walks it from left to right and uses the first font that exists on the visitor's device, so the stack should end with a generic family that always exists: serif, sans-serif, monospace, cursive, fantasy, or system-ui (the operating system's own interface font). Put quotes around names that contain spaces.

Three rules apply to every stack you write:

  • Quote font names that contain spaces: "Segoe UI", "Times New Roman". Single-word names such as Georgia need no quotes.
  • Never quote the generic family. sans-serif is a keyword; "sans-serif" in quotes asks for a font that is literally named sans-serif, which does not exist, so your safety net silently disappears.
  • A stack only chooses among fonts already on the device. Naming a font does not download it. To send a font with your page, you need a web font (later in this section).

What it is. Letters with small finishing strokes, the serifs, at the ends of their lines, as in most printed books and newspapers. Georgia and Times New Roman are serif fonts.

When to use it. Headings that should feel traditional or editorial, such as the club's newsletter, or long articles meant for reading. A popular combination is serif headings with sans-serif body text.

Watch out. Delicate serif fonts can look thin and spindly at small sizes on low-resolution screens; Georgia was designed for screens and holds up well. Two font families per site is plenty; more starts to look messy.

What it is. Fonts in which every character, from a narrow i to a wide W, takes up exactly the same width, like an old typewriter.

When to use it. Code (browsers already use it for <code>, <pre> and <kbd>), and anything whose characters should line up in columns, such as a plain-text schedule.

Watch out. It is tiring to read in long paragraphs, so keep it for code. Most browsers also give text whose only font is the bare keyword monospace a smaller default size (13px instead of 16px). Setting the size in rem, as below, avoids that surprise.

What it is. Whatever font the visitor's operating system uses for its own menus and buttons: Segoe UI on Windows, San Francisco on iPhones and Macs, Roboto on Android.

When to use it. Forms, dashboards and other app-like pages that should feel like part of the device. It costs no download and every visitor already knows the font well.

Watch out. It looks different on every system, on purpose, so check that your design works with all of them. Very old browsers do not know the keyword, which is why the stack still ends with sans-serif.

What they are. cursive asks for some handwriting or script font; fantasy asks for some decorative display font. The device chooses which one. cursive often turns out to be Comic Sans MS on Windows and Apple Chancery on a Mac, and fantasy can be anything from Impact to Papyrus.

When to use them. Almost never on their own. If a design needs a particular handwriting font, load it as a web font and put cursive at the end of the stack only as the last fallback.

Watch out. Because you cannot know what visitors will see, the result may look nothing like your design, and script fonts are hard to read beyond a few words. Never use them for body text.

Which stack should I pick?
  • Body text of a content site: a sans-serif stack. Example: font-family: "Segoe UI", Roboto, Helvetica, Arial, sans-serif;
  • Headings with a classic feel: a serif stack. Example: font-family: Georgia, "Times New Roman", serif;
  • Code: a monospace stack. Example: font-family: Consolas, Menlo, "Courier New", monospace;
  • Forms and app-like pages: font-family: system-ui, sans-serif;
  • Anything decorative: a web font, with a generic family as the last fallback.

Size, weight, style and spacing

Set font-size in rem so text respects the reader's browser settings. font-weight runs from 100 to 900 (normal is 400, bold is 700), but a font only looks different at the weights it actually has. Give line-height as a plain number like 1.5: it multiplies each element's own font size, so it scales correctly for headings and small print alike. Then the text properties: text-align, text-decoration, text-transform, text-indent, letter-spacing, word-spacing and text-shadow.

All of these except text-decoration are inherited, so a declaration on body reaches every piece of text on the page, and you only override it where something should differ.

What it does. Sets how big the text is. It also sets what 1em means on that element, so padding in em and a unitless line-height follow along.

When to use it. To build a clear scale. Body text at 1rem (16px, the browser default) or a little larger for reading-heavy pages (1.125rem = 18px); headings stepping up from there (h3 1.25rem, h2 1.5rem, h1 2 to 2.5rem); small print no smaller than 0.875rem (14px).

Watch out. Use rem, not px, so the text grows when a visitor turns up their browser's text size. Body text below 16px is hard for many people to read. And choose heading tags for structure (the page title is an h1, sections are h2), then size them with CSS; never pick h4 just because it looks the right size.

What they do. font-weight sets how thick the strokes are, from 100 (thin) to 900 (black); normal is 400 and bold is 700. font-style switches between normal (upright) and italic.

When to use them. Weight builds a visual hierarchy: headings at 700, labels and buttons at 600, body text at 400. font-style: italic suits captions and photo credits; font-style: normal undoes the browser's italics on elements such as <cite>, <address> and <em> when your design marks them another way.

Watch out. A font can only show the weights it actually has. Many system fonts have just 400 and 700, so 600 may look exactly like bold; if a font has no bold at all, the browser fakes one by thickening the letters ("faux bold"), which looks smudged. Thin weights (100 to 300) are hard to read at small sizes. And for meaning, use HTML: <strong> for importance, <em> for emphasis. These properties only change the look.

When to use it. Almost always on body: browsers default to about 1.2, which is cramped for paragraphs. Body text reads best around 1.4 to 1.6. Headings need less, around 1.1 to 1.3, because large text with wide gaps falls apart when it wraps onto a second line.

Watch out. Write it as a plain number with no unit. A plain number is inherited as a multiplier, so every element multiplies its own font size: 16px text gets 24px lines, a 36px heading gets 54px. With a unit, the finished length is inherited instead: body { line-height: 24px; } gives a 36px heading 24px lines, and when it wraps, the lines overlap. 1.5em has the same problem, because it is converted to 24px on body first.

What they do. text-align places each line of text inside its box: left, right, center, or justify (stretched so both edges are straight). text-indent moves only the first line of a block in from the left.

When to use them. left (the default in English) for paragraphs and most text. center for short items: a banner headline, a button label, a one-line footer. right for columns of numbers in a table, so the digits line up. text-indent is rare on the web: books indent paragraphs, but web pages usually separate them with space instead.

Watch out. text-align moves the text inside the box, not the box. To center a whole box that has a width, use margin: 0 auto (4.6). Centered paragraphs are hard to read because every line starts in a different place. Justified text leaves uneven gaps between words, which get worse in narrow columns such as a phone screen.

What it does. Draws lines on text: underline, line-through, overline, or none to remove them. Related properties fine-tune the underline: text-decoration-color, text-decoration-style (solid, dotted, wavy...), text-decoration-thickness and text-underline-offset.

When to use it. Mostly for links: removing the underline in a navigation bar, or restyling it in running text so it fits the design. line-through suits an old price, a cancelled date or a crossed-off item.

Watch out. Links inside paragraphs need something besides color to stand out, and the underline is what readers expect; many people cannot tell the difference between two colors. Removing underlines is fine where everything is obviously a link, as in a menu bar. And never underline text that is not a link: people will try to click it.

What it does. Changes the capitalization you see without changing the HTML: uppercase, lowercase, capitalize (the first letter of every word), or none.

When to use it. For small labels, buttons, navigation items and table headings in capitals. The HTML keeps normal writing ("Difficulty"), so if the design changes you edit one CSS line instead of retyping every label.

Watch out. Text in all capitals is slower to read, so keep it to a few words, never whole paragraphs. capitalize is not real title case: it raises every word, including the small ones, so "a walk in the woods" becomes "A Walk In The Woods". Capital letters look cramped, so pair uppercase with a little letter-spacing.

What they do. letter-spacing adds space between every pair of characters (a negative value removes some). word-spacing adds space between words.

When to use them. A little positive letter-spacing for uppercase labels and small capitals (about 0.05em to 0.1em); a tiny negative value for very large headings, whose letters can look too far apart. word-spacing is rarely needed.

Watch out. Use em, so the spacing grows with the text: 0.1em is 1.6px on 16px text and 4px on 40px text, while a fixed 2px that looks right on a label looks wrong on a heading. Do not space out lowercase body text: words start to fall apart into single letters and reading slows down.

What it does. Draws a shadow behind the letters. The value is sideways offset, downward offset, blur, and color: 1px 2px 4px rgb(0 0 0 / 50%) is 1px right, 2px down, softened over 4px, in black at 50%.

When to use it. A subtle lift for white text on top of a photo, or a soft glow on a big display heading.

Watch out. Keep it subtle: a hard or large shadow makes letters look blurry or doubled. A shadow alone does not make text readable over a busy photo; put a see-through dark panel behind the text (the alpha colors from 4.2) and check the contrast.

Which property do I reach for?
  • Text bigger or smaller: font-size in rem. Example: h2 { font-size: 1.5rem; }
  • Heavier or lighter: font-weight (and <strong> in the HTML when it means "important"). Example: font-weight: 700;
  • Lines feel cramped: line-height as a plain number. Example: body { line-height: 1.5; }
  • Center a heading: text-align: center; To center a box, use margin: 0 auto; instead.
  • Remove or restyle a link underline: text-decoration, keeping underlines on links inside paragraphs.
  • A label in capitals: text-transform: uppercase; with letter-spacing: 0.05em;
  • White text over a photo: a dark see-through background for contrast, plus a soft text-shadow if you like.

Readability

Comfortable body text follows a few rules of thumb: a measure (line length) of about 45 to 75 characters, a line-height around 1.4 to 1.6, a size of at least 16px, strong contrast, and left alignment for long passages (justified text leaves uneven gaps between words). Long lines make your eyes lose their place; short ones chop up the reading.

CSS Frameworks and Variables

As a stylesheet grows, the same values repeat everywhere: the brand color thirty times, the same spacing on every card. Two tools help. Custom properties (CSS variables) are built into CSS. Frameworks are stylesheets other people wrote that you build on.

Custom properties

A custom property is a name that starts with two dashes. You define it inside a rule, usually :root (the <html> element) so the whole page can use it, and read it with var():

  • Change once, update everywhere. Edit --brand and every rule that uses it follows.
  • They inherit and cascade. Redefine a variable on an element and it changes for that element and its descendants only.
  • Fallbacks: var(--name, fallback) uses the fallback when the variable is not defined.
  • They are live. Media queries, JavaScript and DevTools can change them while the page runs. Names are case-sensitive: --Brand and --brand are different.

A CSS framework is a ready-made stylesheet (sometimes with JavaScript) that gives you consistent defaults, a layout grid, and pre-styled components. There are two main philosophies:

Preprocessors

A preprocessor such as Sass lets you write an extended language (.scss files with variables, nesting, mixins and partial files) that a build tool compiles into ordinary CSS. The browser never sees Sass. Plain CSS has since caught up on the two most popular features: custom properties and nesting (supported in all major browsers since 2023), so small projects often need no preprocessor. The difference in variables matters: a Sass $brand is replaced with its value at build time, while a CSS --brand still exists in the browser and can change live.
