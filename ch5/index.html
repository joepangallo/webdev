HTML 2: Tables and Forms

Tables present information and forms collect it. In this chapter you will build both, style them, make them work for people using keyboards and screen readers, and check what users type before it ever reaches a server.

HTML Tables

A table holds tabular data: information that makes sense along two axes. Each row is one record (a day, a product, a student) and each column is one kind of fact about it (a time, a price, a score). Timetables, price lists, gradebooks and sports standings are all tables. A quick test: if the content would make sense pasted into a spreadsheet, it belongs in a <table>.

You build a table one row at a time. A <tr> (table row) holds the cells for that row. Each cell is either a <td> (table data) or a <th> (table header), which labels a row or a column. Notice what is missing: there is no column element. Columns appear because every row has the same number of cells.

Browsers show <th> text bold and centered, but the look is only a default. What matters is meaning: a header cell tells browsers, search engines and screen readers "I describe the other cells in my column (or row)". The scope attribute says which one. You will see why that matters in 5.5.

Spanning rows and columns

Sometimes one cell should stretch across several slots. colspan="2" makes a cell two columns wide and rowspan="3" makes it three rows tall. The big cell takes over the slots it covers, so you must delete the cells it replaced. Forget that and the leftover cells get pushed out past the right edge of the table. Everyone makes that mistake at least once.

The parts of a table

Beyond rows and cells, HTML gives tables a few grouping elements. They barely change the default look, but they give CSS something to target, let browsers repeat headers on printed pages, and help assistive technology understand the structure. Pick an element to see where it lives, in the table and in the code.


      

    


    
The invisible <tbody> If you put rows straight inside <table>, the browser quietly wraps them in a <tbody>. Inspect any simple table in DevTools and you will find it. This matters for CSS: the selector table > tr matches nothing, because no row is a direct child of the table.


    
Knowing where each part goes is half the job. The other half is knowing which parts a particular table needs. A three-row price list and a gradebook with a totals row need different pieces. Pick a part to see what it is for, when to use it, when to leave it out, and a commented example.

    

      

        
What it is. The table's title, written as the first child of <table>. Because it lives inside the table, it stays attached to it: screen readers announce it as soon as a user reaches the table, before any cell, so they know what the numbers are about before they start moving through them.

        
When to use it. On every data table. Write what you would otherwise put in a heading above the table, and be specific about what and when: "Campus parking permits, 2026-27" tells the reader far more than "Prices".

        
Watch out. It must come first, before any row or group. A heading or bold paragraph placed above the table looks the same on screen, but nothing connects it to the table, so a screen reader user who jumps straight to the table never hears it. If you want the title below the table, keep the caption first in the code and move it with the CSS caption-side: bottom.

        
      

      

        
What they are. Three containers that group rows by their job. <thead> holds the row (or rows) of column headings, <tbody> holds the data rows, and <tfoot> holds summary rows such as a total or an average. They change almost nothing on screen by themselves.

        
When to use them. Use <thead> whenever the table has a header row, which is almost always, and write <tbody> around the data rows whenever you have a <thead>, so the structure is clear to you and to CSS. Add <tfoot> only when there is a summary row: the total of an invoice, the class average under a gradebook. You may use several <tbody> elements to split long data into groups, such as one per semester.

        
Why bother. They give CSS clean targets (thead th for the header style, tbody tr:nth-child(even) for stripes that skip the header), they let a sticky header work (5.2), and when a long table is printed, browsers can repeat the <thead> at the top of every page.

        
Watch out. Write them in the order thead, tbody, tfoot. Some old tutorials put <tfoot> before the body; that is outdated. And <tfoot> is for rows that summarize the columns, not for a note about where the data came from: put a source note in a paragraph below the table.

        
      

      

        
What it is. <th> is a header cell: a cell that labels other cells. The scope attribute says which ones. scope="col" means "I label every cell below me in my column", and scope="row" means "I label every cell to my right in my row". Two more values exist for headers over a group: colgroup (a header above several columns) and rowgroup (a header for a group of rows, such as the first row of a <tbody>).

        
When to use it. For every cell that names something: the headings across the top, and the first cell of each row when that cell names the row (a day, a product, a student). In a timetable both exist: the days across the top are column headers and the times down the side are row headers.

        
When not to. Do not use <th> just to get bold, centered text; use CSS for that. And do not do the reverse, a <td> styled bold to look like a header: it looks right, but a screen reader has no idea it is a label, so the cells under it are read without context. 5.5 lets you hear the difference.

        
Watch out. In a very simple table, browsers can often guess what a header labels. Adding scope removes the guessing and costs nothing, so make it a habit. Tables with two levels of headings need the headers attribute instead, covered in 5.5.

        
      

      

        
What they are. Attributes that make one cell cover several slots. colspan="2" makes a cell two columns wide; rowspan="2" makes it two rows tall. The cells it covers must be deleted from the code.

        
When to use them. When one label or one value truly belongs to several slots: a heading that sits over a group of columns ("North campus" over "Opens" and "Closes"), a booking that lasts two hours in a schedule, an event that uses two rooms at once, or the "Total" label in a footer row that stretches across the label columns.

        
When not to. To merge cells just because they happen to hold the same text, or to arrange things visually. Every span makes a table harder to read cell by cell with a screen reader, and harder to sort or edit later. If each slot really has its own value, repeat the value.

        
Watch out. After adding a span, count the columns in every row. A row that is too long pushes cells past the right edge; the builder above does this bookkeeping for you.

        
      

      

        
What they are. The only way to talk about a whole column at once. A <colgroup> goes right after the caption, and each <col> inside it stands for one column (or several, with span). They hold no content; they exist so CSS can reach the column.

        
When to use them. To give a whole column a background (highlighting the column a reader should compare), a border, or a fixed width, without adding a class to every cell in it.

        
Watch out. Only four properties work on columns: background, border (with collapsed borders), width and visibility. Text color, alignment and fonts do nothing on a <col>, because the text lives in the cells. To right-align a column of numbers, style the cells instead, for example with a class like td.num.

Tables are for data, not layout

    
Before CSS could position things, developers built entire pages from invisible tables: one cell for the header, one for the sidebar, one for the content. That technique is long dead, for good reasons. A layout table makes a screen reader announce "table, 3 rows, 2 columns" around your navigation, it refuses to rearrange itself on a phone, and it buries your content in markup. Today you lay out pages with CSS Flexbox and Grid, and you save <table> for real data.

Styling Tables

    
An unstyled table is hard to read: no lines, cramped cells, and a small gap around every cell. A handful of CSS properties fix almost everything. Most are box-model properties you already know; a few only apply to tables.

    
    
      
  • border-collapse: collapse merges the borders of neighboring cells into single lines. The default, separate, draws a box around every cell with border-spacing between the boxes.
    • 
      
  • padding on th and td gives the data room to breathe.
    • 
      
  • tbody tr:nth-child(even) shades every other row ("zebra stripes"), which helps your eye track across a wide row. tbody tr:hover highlights the row under the pointer.
    • 
      
  • Numbers read best right-aligned with font-variant-numeric: tabular-nums, which gives every digit the same width so ones, tens and hundreds line up.
    • 
      
  • caption-side: bottom moves the caption under the table.
    • 
    

    
Older tutorials use attributes such as border="1", cellpadding, cellspacing and bgcolor. They are obsolete in HTML5. Do all presentation in CSS.

Wide and long tables

    
A table cannot shrink narrower than its content, so on a phone a wide table pushes the whole page sideways. The robust fix is to wrap it in a container that scrolls on its own. For long tables, position: sticky on the header cells keeps the column labels in view while the rows scroll.

    
    
Why won't my header stick? A sticky element sticks inside its nearest scrolling ancestor. Wrapping a table in overflow: auto makes that wrapper the scroller, so the header only sticks if the wrapper itself scrolls vertically. Give it a max-height, as above.

Introducing Forms

    
Every page you have built so far talks to the user. A form lets the user talk back: search a catalog, log in, order a pizza, sign up for a class. HTML's job is to draw the controls and say where the answers should go. A program on the web server (written in PHP, JavaScript on Node.js, Python, C# or similar) receives the answers and acts on them. You will write that server side in later courses; this chapter is about the browser side.

    
Every form starts with a <form> element and two key attributes:

    
    
      
  • action: the URL of the server program that receives the data. Leave it out and the form submits to the current page's own URL.
    • 
      
  • method: how to send the data, either get (the default) or post.
    • 
    

    
    
When the user submits, the browser collects a name=value pair from each control that has a name attribute. The name is the key the server uses to find the value, much like a variable name. A control without a name is never sent, no matter what the user typed into it. The pairs are URL-encoded (a space becomes +, @ becomes %40, and an & inside a value becomes %26) and joined with &. What it does. The browser adds a ? and the name=value pairs to the end of the action URL, then requests that address, exactly as if you had clicked a link to it. The results page therefore has its own address.

        
When to use it. For forms that only look something up and change nothing on the server: a site search box, filters on a product list (size, color, price range), a sort order, "page 2 of results", a "find a class" form. Because the answers live in the URL, the results can be bookmarked, texted to a friend, reloaded and reached again with Back. For these forms, that is exactly what you want.

        
When not to. Never for passwords or personal details: the URL is saved in the browser history, shown in the address bar (and in any screenshot or screen share), written to server logs, and copied whenever someone shares the link. And never for an action that changes something, such as deleting, buying or subscribing: browsers, link previews and search engine crawlers all assume a GET is safe to repeat, so they may send it again without asking.

What it does. The same name=value pairs travel in the body of the request, after the headers. The URL stays clean (/login), and nothing the user typed appears in the address bar, history or bookmarks.

        
When to use it. For anything private, and for anything that changes data on the server: logging in, creating an account, changing a password, placing an order, paying, posting a comment, sending a contact message, subscribing or unsubscribing. File uploads must use POST.

        
Watch out. POST needs a program on the server to receive it. A static host such as GitHub Pages only hands out files; it has no program to receive the data, so it rejects a POST with an error. If you refresh a page that was the result of a POST, the browser warns "Confirm Form Resubmission", because sending again could place the same order twice. Well-built sites avoid this by answering every POST with a redirect to an ordinary page.

    POST is not encryption A POST body is just as readable as a URL to anyone who can see the traffic.     Form Control Elements
    
    
    HTML has a control for nearly every kind of answer, and picking the right one does half your validation for free: a date picker cannot produce "February 31", and a group of radio buttons cannot produce two answers. Most controls are the same element, <input>, with a different type. On phones, the type also picks the keyboard: email adds an @ key and tel shows a number pad. If a browser does not know a type, it falls back to a plain text box, so newer types are safe to use.
    

    
    
      
    
        
    Text entry
    
        
    text, password, email, url, tel, search, plus <textarea> for several lines of text.
    
      
    
      
    
        
    Choices
    
        
    Radio buttons (exactly one of a few), checkboxes (any number), <select> (one of many, or several with multiple) and <datalist> (suggestions, but typing is still allowed).
    
      
    
      
    
        
    Buttons
    
        
    type="submit" sends the form, type="reset" restores the starting values, type="button" does nothing until JavaScript gives it a job. A <button> inside a form with no type is a submit button.
    
      
    
      
    
        
    Specialized
    
        
    number, range, date, time, datetime-local, month, week, color, file and hidden.
    
      
    
    
    

    
    For text fields, the value is whatever the user types. For radio buttons, checkboxes and select options, you set the value in the markup, and the visible text can differ from what is sent. Radio buttons form a group by sharing a name; checkboxes that share a name send one pair for each box that is checked.

    Watch out. "Complete" means it includes a scheme. www.example.com and example.com both fail with "Please enter a URL.", which confuses people who never type https://. Say so in a hint. The check also accepts any scheme, even ftp: or javascript:, so the server must confirm the address starts with https:// before it ever shows it as a link.

Put the closing tag right after the opening one, or the box starts with invisible spaces.     Buttons: submit, reset or button?
    
    
    A button's type decides what happens when it is pressed. Getting it wrong is one of the most common form bugs, so decide on purpose every time.
    
    
    
      
    
        
    What it does. Runs the browser's validation and, if everything passes, sends the form. A <button> inside a form with no type is a submit button. Pressing Enter in a one-line text field also submits the form, as if the submit button had been pressed.
    
        
    When to use it. Once per form, at the end, named for what it does: "Create account", "Search", "Place order". A specific label tells people what will happen before they commit.
    
        
    Watch out. "Submit" is vague. If a form needs two actions, such as "Save draft" and "Publish", give each submit button the same name and a different value; only the pair of the button that was pressed is sent, so the server knows which one it was.

    When to use it. Almost never. Usability studies keep finding that people press it by accident, often mistaking it for the submit button, and lose everything they typed with no undo.
    
        
    If you must. Make it look clearly secondary, place it away from the submit button, and label it plainly. Recognize it in other people's code; rarely write it in yours.
    
        
      
    
      
    
        
    What it does. Nothing, until JavaScript gives it a job. It never submits or resets the form.
    
        
    When to use it. For actions that should happen on the page without sending the form: a "Show password" toggle, "Add another guest", opening a help panel, a "Calculate total" button that updates a number on the page.
    
        
    Watch out. Inside a form, forgetting type="button" turns it into a submit button, so pressing "Show password" suddenly sends the half-finished form. Always write the type.
    
        
      
    
      
    
        
    Two ways to write a button. <input type="submit" value="Search"> takes its text from the value attribute and can hold nothing else. <button type="submit">Search</button> holds content between its tags, so it can include an icon or a bold word, and it is easier to style.
    
        
    Which to use. Prefer <button> in new code. You will still see <input type="submit"> in older pages; it works the same way.

    Table and Form Accessibility
    
    
    Millions of people browse with a screen reader, a keyboard alone, voice control, a switch device or heavy zoom. Tables and forms are where their experience most often breaks, because the meaning of a table or a form lives in relationships: this label belongs to that field, this header describes that column. A sighted mouse user infers those relationships from the layout. Everyone else needs them written into the markup.
    
    
    The good news: plain, correct HTML does nearly all the work. Accessibility is mostly about using the elements from this chapter the way they were designed.
    

    
    WCAG and the four principles
    
    
    The Web Content Accessibility Guidelines (WCAG), published by the W3C, are the standard that laws, schools and companies point to. The current version is WCAG 2.2. Each guideline has testable success criteria at three levels: A (the minimum), AA (the usual target) and AAA (the strictest). They are organized under four principles, remembered as POUR.
    
    
    
      
    
    

    
    Accessible forms
    
    
    Assistive technology does not read your pixels. It reads the browser's accessibility tree, where every control has a role (text field, checkbox, button), an accessible name (what it is called) and a state (checked, required, invalid). The name is the part developers most often forget, and it comes from your markup:
    
    
      
      
    • Label every control with <label>. Explicit: the label's for matches the input's id. Implicit: the input sits inside the label. Explicit labels keep working even when the label and field end up apart in the markup. Bonus: clicking a label focuses or toggles its control, which turns a tiny checkbox into a big target.
      • 
      
    • A placeholder is not a label. It vanishes as soon as you type, it is usually pale gray, and screen reader support for it as a name is inconsistent.
      • 
      
    • Group related controls with <fieldset> and name the group with <legend>. Without it, a screen reader user hears "Yes, radio button" with no idea what the question was.
      • 
      
    • Connect hints and errors to their field with aria-describedby, so they are read along with it.
      • 
      
    • Help autofill with autocomplete values such as name, email, tel, postal-code and new-password. WCAG criterion 1.3.5 (Identify Input Purpose) asks for this on fields about the user.
      • 
      
    • Keep the keyboard order logical. Tab follows the source order, so write the markup in reading order and never use positive tabindex values.
      •

      Which autocomplete value?
      
    
      The autocomplete attribute tells the browser what a field is for. With that, it can fill in the user's saved name, address or card in one tap, and a password manager knows which box gets which password. That saves everyone time and typos, and for people who find typing slow or painful, or who struggle to remember details, it can decide whether they finish the form at all. That is why WCAG asks for it.
      
    
      When to use it. On every field that asks about the user themselves: name, email, phone, address, birthday, username, password, payment details. The value must be spelled exactly as listed; a made-up value such as zipcode is ignored.
      
    
      When not to. On fields about someone or something else. A "Friend's email" field marked email would be filled with the user's own address. Leave autocomplete off those, or set autocomplete="off" (browsers may still offer suggestions, especially on login forms, to keep password managers working).

        Styling and Designing Forms
        
    
        Design decides whether people finish your form. Every extra field, vague label and tiny tap target costs you users. The best practices are simple and well tested:
        
    
          
      
        • One column. Stack fields in a single column in a logical order. Side-by-side fields make the eye zig-zag, and people skip fields they don't notice.
          • 
      
        • Labels above fields. Top-aligned labels are the fastest to scan and they fit on phones. Labels beside fields (lined up with CSS Grid) can work for short forms on wide screens.
          • 
      
        • Ask only for what you need, and mark the exceptions in words: if most fields are required, label the few optional ones "(optional)". Never rely on a red asterisk alone.
          • 
      
        • Size fields to their answers. A ZIP code box should look short and a street address box long, so people can tell what goes where.
          • 
      
        • Make targets big enough. WCAG 2.2 asks for pointer targets of at least 24×24 CSS pixels (criterion 2.5.8). Around 44×44 is comfortable for thumbs.
          • 
      
        • Keep focus visible and name buttons by what they do: "Create account" beats "Submit". Skip the Reset button; people mostly hit it by accident and lose their work.
          • 
    
        

    
        CSS for form controls
        
    
        Form controls arrive with their own quirky browser styles. For example, they do not inherit the page's font, which is why unstyled inputs often look small and out of place. A short set of rules gets them under control:
        
    
    
        A few pseudo-classes target control states: :focus-visible (focused, and the browser decided the focus should show, as it always does for keyboard users), :checked, :disabled, :required and :optional, :invalid and :user-invalid, plus the ::placeholder pseudo-element.
        
    
        Each one matches a control only while it is in a certain state, so your styles switch on and off by themselves as the user works through the form. No JavaScript is needed.

        What it matches. Controls with the disabled attribute. A disabled control cannot be focused, clicked or changed, and its value is not sent with the form.
        
        
        When to use it. To make a control that does not apply right now look unavailable, such as a "Company name" field that only matters for business accounts.
        
        
        Watch out. Keyboard users cannot even focus a disabled control, so they cannot find out why it is off. A disabled submit button with no explanation is a classic frustration: it is usually better to leave the button enabled and explain what is missing when it is pressed. The cursor change only helps mouse users.
        
        
      
        
      
        
        
        What they match. :required matches fields that have the required attribute; :optional matches the fields that do not.
        
        
        When to use them. For a subtle visual difference between the two, such as a slightly heavier border on required fields.
        
        
        Watch out. Styling alone does not tell anyone which fields are required: screen readers do not announce a border, and many people would not notice it. Say it in words, in the label, as the design advice at the top of this section explains: "(optional)" on the few optional fields.
        
        
      
        
      
        
        
        What they match. Both match a field that currently breaks one of its rules (required, type, pattern, min and so on). The difference is timing. :invalid matches from the moment the page loads, so an empty required field is "invalid" before the user has even reached it. :user-invalid matches only after the user has changed the field and moved on, or has tried to submit. The opposites, :valid and :user-valid, work the same way.
        
        
        When to use them. Use :user-invalid for error borders and icons, so people are not greeted by a form full of red. :user-valid can add a quiet "looks good" mark after a correct answer.
        
        
        Watch out. Red alone is not an error message. Pair the style with text that says what is wrong and how to fix it (5.7), because people who cannot see the color, and screen reader users, get nothing from a border.
        
        
      
        
      
        
        
        What it matches. The placeholder text shown inside an empty field. It has two colons because it is a pseudo-element, a part of the field, not a state.
        
        
        When to use it. When a field shows an example of the format, such as "e.g. 33101", to make that text readable. Browsers often draw it too pale.
        
        
        Watch out. A placeholder is never a replacement for a label (5.5). Make it readable but clearly lighter than real input, so nobody mistakes the example for an answer they already typed.
        
        
      
        
    
        

    
        
      Which selector should I pick?
      
          
        
        • A focus ring: :focus-visible. Example: input:focus-visible { outline: 3px solid #1f4fd1; }
          • 
        
        • Error styling: :user-invalid, never plain :invalid. Example: input:user-invalid { border-color: #c62828; }
          • 
        
        • Highlighting the chosen option: :checked with +. Example: input:checked + span { font-weight: bold; }
          • 
        
        • Unavailable controls: :disabled. Example: :disabled { opacity: 0.6; }
          • 
        
        • Readable example text: ::placeholder. Example: input::placeholder { color: #5f6b7a; }
          • 
      
        
    
        
    
        :invalid or :user-invalid? :invalid matches immediately, so every empty required field glows red before the user has typed a thing. :user-invalid waits until the user has changed the field or tried to submit. It works in all current major browsers, so prefer it for error styling. Try both in the lab.

        Validating User Input
        
    
        People make mistakes: typos, skipped fields, dates in the wrong format. Some "users" are bots or attackers sending junk on purpose. Validation checks input against rules before you rely on it. It has two separate goals: helping honest users fix mistakes quickly, and protecting your application and its data.
        

    
        What to check
        
    
        
      
        
        Kinds of validation with examples and tools
        
        Kind of checkExampleTool
        
        
          
        RequiredAn email address must be enteredrequired
        
          
        Data typeAge is a number; website is a URLtype="number", type="url"
        
          
        FormatA ZIP code is 5 digits, optionally plus 4pattern
        
          
        LengthA password has at least 8 charactersminlength, maxlength
        
          
        RangeAge from 13 to 120; a date that isn't in the pastmin, max, step
        
          
        Comparison"Confirm password" matches "Password"JavaScript: setCustomValidity()
        
          
        Business ruleThe username isn't already takenServer code with a database lookup
        
                
      
        
    
        

    
        The first five kinds are built into HTML: add an attribute and the browser enforces it. Pick a kind to see when it applies, the exact markup, the message the browser shows when it fails, and why the server has to check it again anyway.
        
    
        
      
        
        
        What it checks. That the field is not empty. On a checkbox, required means that box must be checked; on a radio group, that one option must be picked; on a <select>, that the chosen option has a non-empty value.
        
        
        When to use it. On every field you truly cannot do without: the email you will send the receipt to, the password on a sign-up, the "I agree" box. Not on nice-to-have fields: every required field is another reason for someone to give up.
        
        
        
        What the user sees. In Chrome (each browser words it a little differently, always in the user's own language):
        
        
          
          
        • An empty text box: "Please fill out this field."
          • 
          
        • An unchecked required checkbox: "Please check this box if you want to proceed."
          • 
          
        • A select still on its prompt: "Please select an item in the list."
          • 
        
        
        
        In every case the validity flag is valueMissing.
        
        
        Why the server checks again. required only means "not empty", so a single space passes. And anyone can delete the attribute in DevTools or send the request without the field at all. The server must trim the value and treat blank or missing as an error.
        
      
        
      
        
        
        What it checks. That the value has the right shape for its type: email needs name@domain, url needs a full address with a scheme such as https://, and number accepts only numbers. Date, time and color pickers cannot produce a wrong shape in the first place.
        
        
        When to use it. Whenever a field holds an email address, a web address or a quantity. You get the matching phone keyboard as a bonus. Note that type="tel" checks nothing, because phone formats vary too much.
        
        
        
        What the user sees. In Chrome:
        
        
          
          
        • ana in the email box: "Please include an '@' in the email address. 'ana' is missing an '@'." (flag: typeMismatch)
          • 
          
        • example.com in the URL box: "Please enter a URL." (typeMismatch)
          • 
          
        • Something that is not a number in the number box: "Please enter a number." (badInput)
          • 
        
        
        
        Why the server checks again. The server receives plain text; it has no idea which type the field had in the browser, and a script can send anything. The shape check also cannot prove an email address exists (ana@gmial.com passes), which is why sites send a confirmation link.
        
      
        
      
        
        
        What it checks. That the whole value matches a pattern, a regular expression (the Patterns section below explains the syntax).
        
        
        When to use it. For values with one fixed, known shape: a ZIP code, a student ID, a course code, a username limited to certain characters.
        
        
        When not to. For values that come in many valid shapes. Names contain spaces, hyphens and apostrophes, and some people have only one name; addresses and international phone numbers vary endlessly. A strict pattern on those locks real people out.
        
        
        
        What the user sees. In Chrome: "Please match the requested format." That tells nobody what the format is, which is why the hint matters. (Some browsers add the text of a title attribute to the message, but a visible hint helps everyone, before they make the mistake.) The flag is patternMismatch.
        
        
        Watch out. An empty field skips the pattern, so add required if the field must be filled in. pattern does not work on type="number".
        
        
        Why the server checks again. The same pattern must run on the server, because a script can send zip=hello or a line of code straight to your URL.
        
      
        
      
        
        
        What it checks. The number of characters. minlength sets the fewest allowed; maxlength sets the most.
        
        
        When to use it. minlength for passwords (12 or more is a common modern minimum). maxlength when there is a real limit, such as a 20-character username or a 160-character bio that has to fit on a profile card.
        
        
        
        What the user sees. For a short password, Chrome says "Please lengthen this text to 12 characters or more (you are currently using 5 characters)." (flag: tooShort). maxlength shows no message at all: the field just stops accepting characters, so say the limit in the label.
        
        
        Watch out. minlength ignores an empty field (pair it with required) and only complains once the user has typed something.
        
        
        Why the server checks again. maxlength only limits typing in the browser. A script can send a bio of five million characters; the server must refuse anything longer than it can store.
        
      
        
      
        
        
        What it checks. That a number, date or time lies between min and max, and that it lands on an allowed step (whole numbers, quarters, every 15 minutes).
        
        
        When to use it. Age limits, quantities (1 to 8 tickets), dates that cannot be in the past, times within opening hours, prices in cents.
        
        
        
        What the user sees. In Chrome:
        
        
          
          
        • Below min: "Value must be greater than or equal to 1." (flag: rangeUnderflow)
          • 
          
        • Above max: "Value must be less than or equal to 8." (rangeOverflow)
          • 
          
        • A date before min: "Value must be 10/01/2026 or later.", with the date shown in the user's own style (rangeUnderflow)
          • 
          
        • 2.5 tickets, which misses the step: "Please enter a valid value. The two nearest valid values are 2 and 3." (stepMismatch)
          • 
        
        
        
        Watch out. Values in HTML are fixed. "No dates in the past" means a min that changes every day, so a real site writes today's date into the page with JavaScript or on the server.
        
        
        Why the server checks again. A script can send tickets=-3. If the server trusted it, a negative quantity could turn a charge into a refund.
        
      
        
      
        
        
        What it checks. One field against another: "Confirm password" matches "Password", an end date comes after the start date, a confirmation email matches the first one.
        
        
        When to use it. Only when the second field really prevents mistakes. "Confirm password" is common on sign-up forms; many sites now use a single password field with a "Show password" button instead.
        
        
        The tool. No HTML attribute can compare two fields. JavaScript does it with setCustomValidity(), covered below in "Custom rules with JavaScript", where you will build the password version yourself. Here is the date version:
        
        
        
        What the user sees. Exactly your message, in the browser's usual error bubble. The flag is customError.
        
        
        Why the server checks again. JavaScript can be turned off, and a request sent by a script never runs your page's code at all.
        
      
        
      
        
        
        What it checks. Rules that depend on data only the server has: the username is already taken, the email is already registered, the coupon code has expired, the class section is full, the item is out of stock.
        
        
        When to use it. Whenever the answer depends on your database. The browser cannot know, so there is no HTML attribute for it.
        
        
        What the user sees. The server checks after the form is sent and, if something fails, sends the form back with the user's answers still filled in and a message beside the problem field:
        
        
        
        Watch out. Some sites check while you type, with JavaScript asking the server in the background. That is a nice touch, but the server must still check again when the form arrives: two people could choose the same name in the same second.
        
      
        
    
        

    
        
      Which check do I need?
      
          
        
        • The field cannot be empty: required.
          • 
        
        • It is an email address, a web address or a number: the matching type.
          • 
        
        • It has one fixed format, such as a ZIP code or an ID: pattern, plus a hint that shows the format.
          • 
        
        • A password minimum or a character limit: minlength or maxlength.
          • 
        
        • A number, date or time within limits: min, max and step.
          • 
        
        • Two fields must agree: JavaScript's setCustomValidity().
          • 
        
        • It depends on your data (taken, full, expired): the server.
          • 
        
        • And every time: the server checks again.
          • 
      
        
    
        

    
        Built-in validation
        
    
        Add those attributes and the browser does the rest with no JavaScript: when the user submits, it blocks the request, focuses the first bad field and shows a message in the user's own language. Behind the scenes, every field has a validity property, a ValidityState object with one true/false flag per rule. Pick a preset (or set attributes yourself), type in the test field, and watch the flags change.

          Patterns
          
    
          The pattern attribute takes a regular expression, a mini-language for describing text. The browser treats it as if it were wrapped in ^(?: … )$, so the pattern must match the entire value, not just part of it. pattern works on text, search, tel, url, email and password fields, not on number fields.
          
    
          
      
          
        
          
        
          
      
          
      
          
      
          
        
          
        
          Results
            
      
            
      
            
    
            
    
            Escape the hyphen inside brackets Modern browsers compile pattern with JavaScript's v flag, which is stricter than older regex rules. Inside square brackets, write a literal hyphen as \- (as in [ .\-]). A pattern that fails to compile is silently ignored, so the field accepts anything. Test your patterns!
            

    
            Telling users what went wrong
            
    
              
      
            • Say what is wrong and how to fix it: "Enter a 5-digit ZIP code, like 33101", not "Invalid input".
              • 
      
            • Put the message next to its field, connect it with aria-describedby, set aria-invalid="true", and don't rely on color alone.
              • 
      
            • Check when the user leaves a field or submits, not on every keystroke. Being told your email is invalid after typing one letter is just annoying.
              • 
      
            • On submit, bring the user to the first problem (built-in validation does this) or show a summary that links to each field. Never erase what they typed.
              • 
    
            
    
            Better still, prevent errors: pick controls that cannot hold a bad value (a date input, a select, radio buttons), give hints before people type, use autocomplete so browsers fill known-good values, and accept flexible input you can clean up yourself, like spaces in a card number.
            

    
            Client side, server side, or both?
            
    
            Client-side validation (HTML attributes and JavaScript) runs in the browser, so feedback is instant. But the browser belongs to the user. Anyone can delete a required attribute in DevTools, turn off JavaScript, or skip the browser completely and send a request from a script. So the server must check everything again. Think of it this way: client-side validation is for convenience; server-side validation is for correctness and security. You always need the server side, and you almost always want both.
            
    
            
      
    
            
    
            
      
    
            

    
            Custom rules with JavaScript
            
    
            Some rules can't be written as attributes, such as "the two passwords must match". The Constraint Validation API lets JavaScript plug custom rules into the browser's built-in system. Call field.setCustomValidity('message') to mark a field invalid with your own message, and field.setCustomValidity('') to mark it valid again. The browser then blocks submission and shows your message exactly like its own.
