CSS 2: Layout

In Chapter 4 you styled boxes one at a time. This chapter is about arranging them: side by side, in rows and columns, stacked on a phone and spread out on a wide monitor. You will meet the older tools (floats and positioning), the modern ones (Flexbox and Grid), media queries for responsive design, shadows, gradients and animation, and the preprocessors many teams use to write their CSS.

Older Approaches to CSS Layout

Layout means deciding where every box on the page sits: the header across the top, the sidebar beside the article, the photo to the left of its caption. Flexbox and Grid, the modern layout tools, only became usable in every browser around 2017. Before that, developers built every layout from three older tools: normal flow, floats and positioning.

Those tools have not gone away. Floats are still the only way to wrap text around a photo, and positioning is still how you pin a badge to a corner or keep a header on screen while the page scrolls. Learning them first also explains why the modern tools were invented, and what problems they solved.

Normal flow: what happens before you write any layout CSS

Every element produces a box, and with no layout CSS at all the browser places those boxes using normal flow. There are two kinds of box in normal flow:

  • Block boxes stack on top of each other, from the top of the page down. Each one starts on a new line and stretches as wide as its parent. Paragraphs, headings, lists and <div>s are block boxes.
  • Inline boxes flow from left to right inside a line of text, exactly like words, and wrap onto the next line when they run out of room. Links, <span>, <strong> and <em> are inline boxes.

The display property switches a box between these behaviors. The green box below is a <span> in the middle of a sentence. Change its display and watch what happens to the width, the padding and the margin you gave it, and to the text around it.

    Floats

    Magazines have always wrapped text around photos. CSS copied the idea with the float property. float: left pushes a box to the left edge of its container, and the text that follows flows down its right side; float: right does the mirror image.     Positioning

    Normal flow decides where a box goes on its own. The position property lets you take over: you choose a positioning scheme, then move the box with the offset properties top, right, bottom and left. Each offset is a distance in from an edge: top: 20px puts the box's top edge 20px below a reference edge, and right: 0 lines its right edge up with a reference right edge.

    Stacking order and z-index

    Once boxes can overlap, something has to decide which one is drawn on top. By default, positioned elements are drawn above non-positioned ones, and among positioned elements, the one that comes later in the HTML wins. The z-index property overrides that: a higher number is drawn closer to the viewer. Two rules trip everyone up:

    • z-index only works on positioned elements (anything but static), and on flex and grid items.
    • A positioned element with a z-index other than auto creates a stacking context: a sealed group. Its children are stacked against each other inside the group, and the whole group is stacked as one unit with that z-index. A child with z-index: 9999 can never rise above something outside its group that is higher than the group.

    When to use it. For content that is not relevant right now: a closed menu, a form step you have not reached yet, an error message before there is an error.

    Watch out. You cannot animate to or from display: none smoothly the way you can with opacity; it switches instantly.

    What it is. The element is not drawn, but it keeps its space in the layout, so nothing moves. It cannot be clicked, and screen readers skip it.

    When to use it. When you need a spot to stay reserved, such as a "Saved!" message next to a button that appears and disappears without nudging the button around.

    Watch out. A child can override it with visibility: visible and reappear inside an invisible parent. That never happens with display: none.

    What it is. The element is fully transparent, but in every other way it is still there: it takes space, it can be clicked and focused, and screen readers read it.

    When to use it. As the start or end point of a fade, because opacity animates smoothly from 0 to 1. Values in between (opacity: 0.5) make something see-through.

    Watch out. An invisible element that still catches clicks is a trap: users click "nothing" and something happens. If something should stay hidden after a fade, also set visibility: hidden or pointer-events: none.

    What it is. Content that sticks out past the box's edges is cut off at the padding edge. The overflow property has five values: visible (the default: content spills out over whatever comes next), hidden (cut off), clip (cut off, and scrolling is impossible even from code), scroll (always shows scrollbars) and auto (scrollbars only when needed).

    When to use it. To crop: an image inside a box with rounded corners, a fixed-height card preview, a strip of photos where the edges should not show.

    Watch out. Cut-off text is lost to sighted users; never use it on content people need to read. It also clips shadows and dropdown menus that are meant to stick out, and it breaks position: sticky on descendants.

    What it is. If the content fits, nothing happens. If it does not, the box gets a scrollbar and the content scrolls inside it, while the rest of the page stays still.

    When to use it. Code samples with long lines, a wide table on a phone, a chat window or a list with a fixed height. It is also the gentle alternative to hidden: nothing is lost.

    Watch out. A scrolling box needs a size limit to scroll against: a height or max-height for vertical scrolling, or content wider than the box for horizontal. Prefer auto to scroll, which shows empty scrollbars even when nothing overflows.

    Which one should I pick?
    • Gone until it is needed (menus, messages, later steps): display: none.
    • Invisible, but the layout must not move: visibility: hidden.
    • Fading in or out: animate opacity, and end with visibility: hidden if it should stay hidden.
    • Content too big for its box, and people need it: overflow: auto.
    • Cropping decoration, such as a photo in a rounded card: overflow: hidden.

      Why the old layout tricks were replaced

      For about fifteen years, whole page layouts were built from tools that were never designed for the job. In the late 1990s, pages were cut up into invisible <table>s: one cell for the logo, one for the menu, one for the content. That mixed presentation into the HTML, confused screen readers ("table with 3 rows and 2 columns") and could not adapt to phones.

      Then came float grids: every column was a float with a percentage width, every row needed a clearfix, and frameworks such as Bootstrap 3 shipped hundreds of lines of float and clearfix rules. Floats could not make columns of equal height, could not center something vertically, and could not reorder content. Developers used position: absolute and negative margins to fake what they could not do.

      Flexbox (for rows and columns of items) and Grid (for whole two-dimensional layouts) were designed specifically to solve those problems, and they replaced the old tricks. The old tools are still the right choice for the small jobs they were made for.

      Flexbox Layout

      Flexbox (the Flexible Box Layout module) is a layout mode for arranging items in one direction: a row or a column. It decides how big each item is, how the leftover space is shared, and how the items line up. Tasks that took floats, clearfixes and negative margins, such as a navigation bar, equal-height cards or a box centered in the middle of the screen, take two or three lines of Flexbox.

      Flexbox always involves two roles:

      • The flex container is the parent. You switch it on with display: flex. Most Flexbox properties go here.
      • The flex items are the container's direct children, and only those. Grandchildren are laid out normally inside their own parent, unless that parent is a flex container too.

      Everything else in Flexbox is about two axes. The main axis is the direction the items are placed in: left to right for a row, top to bottom for a column. The cross axis runs at a right angle to it. The property names follow the axes: justify-content works along the main axis, and the align- properties work along the cross axis. Turn a row into a column and the axes turn with it, so justify-content: center switches from horizontal to vertical centering.

      • A row that becomes several rows on small screens: flex-wrap: wrap plus a flex-basis on the items.

      Sizing the items: grow, shrink and basis

      Flexbox sizes items in three steps. First, each item gets its starting size, the flex-basis (by default, auto: its width or its content). Then the browser compares the total with the container:

      • If there is space left over, it is shared out in proportion to each item's flex-grow. The default is 0: don't grow.
      • If there is not enough space, each item gives some up in proportion to its flex-shrink times its basis. The default is 1: everyone shrinks, big items more.

        Grid Layout

        Flexbox lays items out in one direction at a time. CSS Grid works in two: you draw rows and columns on the container first, then put each item into the cells you want. That makes it the natural tool for whole page layouts, photo galleries, dashboards, and anything where things must line up both across and down.

        Grid comes with its own vocabulary. Step through the diagram: every word below appears in property names, so it pays to learn them now.

        123 456 1234 123

        1. The grid container (outlined) is the element with display: grid. Its direct children, the six numbered boxes, are the grid items.

        2. Grid lines are the dividing lines, numbered from 1 at the start. Three columns need four column lines (1 to 4), and two rows need three row lines (1 to 3). You place items by these numbers.

        3. A track is the space between two neighboring lines: a column or a row. One column track (column 2) and one row track (row 2) are highlighted. grid-template-columns and grid-template-rows size the tracks.

        4. A cell is where one column track crosses one row track: the smallest space an item can fill. The highlighted cell is column 3, row 1.

        5. A grid area is any rectangle of cells. This one runs from column line 2 to column line 4 and from row line 1 to row line 3, so it covers four cells. In CSS: grid-column: 2 / 4; grid-row: 1 / 3;

        6. Gaps (also called gutters) are the spaces between tracks, set with gap. Nothing can be placed inside a gap. The lines run down the middle of the gaps.

        The implicit grid

        The tracks you define with grid-template-columns and grid-template-rows make up the explicit grid. When there are more items than explicit cells, or an item is placed beyond the last line, the browser doesn't give up: it adds extra tracks automatically. Those form the implicit grid (the track editor above labels them). Implicit tracks are sized by grid-auto-rows (and grid-auto-columns), which default to auto. That is why most galleries define only their columns and let the rows appear as needed.

        Grid or Flexbox?

        They are partners, not rivals. Flexbox is one-dimensional and works from the content out: you have some items, and Flexbox shares a row (or a column) between them, letting each line wrap on its own. Grid is two-dimensional and works from the layout in: you draw the tracks, then place items into them, and everything lines up across and down. A typical page uses both: Grid for the overall page and the card gallery, Flexbox for the navigation bar and for the contents of each card.

        Responsive Design

        Your page will be opened on a 5-inch phone, a tablet held sideways, a laptop and a 32-inch monitor, often by the same person on the same day. More than half of all web traffic now comes from phones. Building a separate site for each screen is impossible to maintain, so instead you build one page that rearranges itself to fit whatever screen it lands on. That is responsive web design, a term coined by Ethan Marcotte in 2010, and it rests on three ingredients:

        1. Fluid layouts: widths in %, fr and max-width instead of fixed pixels, so the layout stretches and squeezes.
        2. Flexible media: images and video that shrink to fit their container instead of spilling out of it.
        3. Media queries: CSS rules that apply only when a condition is true, such as "the screen is at least 600px wide", so the layout can change at chosen widths.

        Before any of that works on a phone, there is one line of HTML you must add.

        The viewport meta tag

        When the iPhone appeared in 2007, almost no website was built for a small screen. So mobile browsers pretend to be about 980px wide: they lay the page out for a desktop screen, then shrink the result to fit the phone. Old sites stayed usable (with a lot of zooming), but it ruins a responsive page: everything is tiny, and your media queries think they are on a desktop. This tag in the <head> tells the phone to stop pretending:

        width=device-width means "the layout is as wide as the screen" (390 CSS pixels on a typical phone) and initial-scale=1 means "start at 100% zoom". Every page you build from now on should have it. Never add user-scalable=no or maximum-scale=1: they stop people with low vision from zooming in.

                  CSS Preprocessors

                  Real stylesheets grow to thousands of lines. For most of CSS's history, the language had no variables (so the brand color was pasted in two hundred places), no way to nest related rules, no way to reuse a group of declarations, and no arithmetic. A CSS preprocessor fills those gaps with a language of its own, then compiles your file into ordinary CSS. The most popular is Sass, usually written in its SCSS syntax (files ending in .scss, which look like CSS with extras); Less and Stylus are older alternatives.

                  The key idea: browsers never see Sass. You write styles.scss; a compiler (the sass command, or a build tool such as Vite that runs it for you) turns it into styles.css; your HTML links to styles.css. Step through what the compiler does with a small file.

                  styles.scss (what you write) 
                  $brand: #1d7a55;
$space: 8px;

@mixin card-shadow {
  box-shadow: 0 2px 6px rgb(0 0 0 / 0.15);
}

.card {
  padding: $space * 2;
  @include card-shadow;
  h2 {
    color: $brand;
  }
  &:hover {
    border-color: $brand;
  }
}
                  styles.css (what the browser gets) 
                  .card {
  padding: 16px;
  box-shadow: 0 2px 6px rgb(0 0 0 / 0.15);
}
.card h2 {
  color: #1d7a55;
}
.card:hover {
  border-color: #1d7a55;
}

                  Saved as styles.css and linked from the HTML with <link rel="stylesheet" href="styles.css">

                  1. The compiler reads styles.scss from top to bottom. Lines starting with $ define variables, and @mixin defines a reusable group of declarations. Neither one produces any CSS by itself: they are notes for the compiler.

                  2. It replaces each variable with its value and does the math: $space * 2 becomes 8px * 2, which becomes 16px.

                  3. It expands each @include: the line is replaced by the declarations inside the mixin, as if you had typed them there.

                  4. It flattens the nesting. CSS (until recently) couldn't nest rules, so the h2 rule inside .card becomes a separate rule after it, with the selector .card h2.

                  5. & means "the parent selector, right here". &:hover glues the parent on with no space, giving .card:hover.

                  6. It writes styles.css. This is the only file the browser downloads; the .scss file stays on your computer. (Compilers can also write a source map, so DevTools can show which .scss line each CSS rule came from.)

                  What it is. A name that holds a value: $brand: #1d7a55;. Wherever you write $brand, the compiler pastes the value in. Change it in one place and every use changes in the next compile.

                  When to use it. For a design's building blocks: brand colors, the spacing scale, font stacks, breakpoints, corner radii.

                  Watch out. Sass variables exist only while compiling. In the finished CSS they are gone, so they can't change in a media query or from JavaScript. CSS custom properties can, which is why many projects now use custom properties even inside Sass.

                  What it is. Writing a rule inside another rule, so the inner selector only matches inside the outer one. & stands for the parent selector: &:hover, &.active, or even &-title to build the class name .card-title.

                  When to use it. To keep everything about one component together: the card, its heading, its button, its hover state.

                  Watch out. Deep nesting creates long, very specific selectors (.page .main .card .body p a) that are hard to override. A good rule: never more than three levels.

                  What it is. A named, reusable group of declarations, defined with @mixin and pasted in with @include. Mixins can take parameters, with default values, so one mixin can produce many variations.

                  When to use it. For patterns that repeat with small differences: a button style in different colors, a focus ring, a truncated single line of text.

                  Watch out. Every @include copies the declarations again, so a big mixin used fifty times makes a big CSS file. When the styles are identical everywhere, a shared class is lighter.

                  What it is. Splitting styles into many small files. A file whose name starts with an underscore, such as _buttons.scss, is a partial: it is not compiled on its own, only when another file loads it with @use. The compiler combines everything into one CSS file.

                  When to use it. On any project bigger than one page: one partial for variables, one per component, one for the layout. You find things faster and teammates edit different files.

                  Watch out. With @use, a partial's variables are reached through a namespace (the file name): colors.$brand. The older @import in Sass is deprecated.

                  What it is. Arithmetic on numbers with units ($space * 3), plus built-in functions, mostly for colors: lighten(), darken(), mix(). The compiler works out the result, so the browser gets a plain value.

                  When to use it. To derive values from one source: spacing as multiples of a base unit, a hover color a little darker than the brand color.

                  Watch out. Sass can only do the math while compiling, so it cannot mix units it can't convert, such as 100% - 2rem; the browser's calc() can, because it works it out on the page.

                  Do I need a preprocessor?
                  • A small site or a class project: no. Native custom properties, nesting and calc() cover the essentials, with no build step.
                  • A big site split across many files: Sass partials (or a bundler) combine them into one download.
                  • Many repeated patterns with variations: Sass mixins and loops still have no native equivalent.
                  • Joining a team: use what the project already uses. Plenty of professional codebases are written in SCSS, so learn to read it.

                  Native CSS has caught up

                  Much of what made Sass essential is now built into CSS, and the native versions run in the browser, so they can do things a compiler never could.

                  • Custom properties (--brand: #1d7a55;, read with var(--brand)) are live: change one in a media query, for dark mode, or from JavaScript, and the page updates instantly. You used them in Chapter 4.
                  • Native nesting uses almost the same syntax as Sass, & included, with no compile step.
                  • calc() mixes units the compiler can't know, such as calc(100% - 2rem), and color-mix() blends colors the way darken() does.

                  PostCSS and Autoprefixer

                  Preprocessors aren't the only tools that transform CSS. PostCSS works the other way round: you write standard CSS, and plugins post-process it. The best known plugin, Autoprefixer, adds vendor prefixes (such as -webkit-) that older browsers need, based on a list of the browsers you choose to support, so you never write them by hand. Other plugins minify the file or let you use brand-new CSS features before every browser supports them. Many build tools run PostCSS automatically.
