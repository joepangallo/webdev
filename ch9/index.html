The Document Object Model (DOM)

When a browser downloads an HTML file, it reads the text once, top to bottom, and builds a structure in memory called the Document Object Model, or DOM. Every element, every run of text, even every comment becomes an object called a node, and the nodes are arranged in a tree that mirrors how your tags nest. From then on the browser draws the page from that tree, not from your file.

That is what makes JavaScript on a web page possible. Your script never edits the .html file on the server. It reads and changes the tree inside the visitor's browser, and the browser redraws whatever changed, instantly. In Chapter 8 you built your own objects with properties and methods. The DOM is a huge set of objects the browser builds for you, with properties (like textContent) and methods (like querySelector()) ready to use.

The browser turns that markup into a family tree, and the vocabulary is the same as in a real family. The <ul> is the parent of the three <li> elements; they are its children and siblings of each other. The <body> is an ancestor of every <li>, and each <li> is a descendant of the body. At the very top sits the document object: the root of the tree and your starting point for everything in this chapter. Step through the tree below.

  1. document is the root of the tree. Every path through the DOM starts here, which is why so much of your code begins with document.

  2. <html> is the only child of document, and it always has exactly two children: <head> and <body>. The shortcuts document.head and document.body jump straight to them.

  3. <body> is the parent of <h1> and <ul>. Those two share a parent, so they are siblings, and the <h1> comes first because it comes first in the HTML.

  4. The <ul> has three <li> children. They are also descendants of <body>, <html> and document, so a search that starts at any of those can find them.

  5. Text is a node too. The word "Groceries" is a text node, the only child of the <h1>. (Each <li> has a text node inside it as well; there is no room to draw them.)

  6. Attributes such as class="done" belong to their element but are not children. You read them with methods like getAttribute(), not by walking down the tree.

Nodes: the pieces of the tree

Everything in the tree is a node, but nodes come in different types, and each type can do different things. An element node can have children and attributes; a text node only holds characters. Every node has a nodeType property (a number) and a nodeName property (a string) that tell you which kind you are holding. You will work with element nodes 95% of the time, but the other types explain a lot of surprising results, as you will see in a moment.

When you meet it. Constantly. Every selection method in this section returns element nodes, and almost every change you make in 9.2 is made to one.

When you meet it. When you use the "raw" navigation properties such as firstChild, childNodes and nextSibling, which include every node, not just elements. Watch out. The line breaks and indentation between your tags are text too. When you meet it. Rarely, and usually by surprise: walking childNodes and finding an extra node you did not expect. Some tools and frameworks also leave comment nodes behind as invisible bookmarks in the page.

Watch out. You will almost never need the attribute node itself. Ask the element for the attribute's value instead; that is shorter and works the same in every browser.

What it is. The root node: the object called document, which represents the whole page. It sits above <html>, and it is where the most useful methods live: getElementById(), querySelector(), createElement() and many more.

When you meet it. At the start of nearly every DOM statement. It also has shortcuts to the main parts of the page: document.documentElement (the <html> element), document.head, document.body, document.title and document.forms.

Watch out. document only covers the page itself. The browser window (its size, its scroll position, its address) belongs to a different object, window.

Finding elements

Before you can change anything on a page, you have to get hold of it. The document object (and every element) has methods that search the tree and hand back the nodes you asked for. There are five you will see in real code. The two newest, querySelector() and querySelectorAll(), accept any CSS selector from Chapter 4, so everything you learned about selectors pays off again here.

What it is. The oldest and most direct search: give it an id (without the #) and it returns the one element with that id, or null if there is none. Because ids must be unique on a page, there is never more than one answer.

When to use it. For the important, one-of-a-kind parts of a page that you gave an id on purpose: the shopping cart, the search box, the main menu. It is short, fast and easy to read.

Watch out. Writing getElementById('#cart') looks for an element whose id is literally #cart, so you get null, and the next line that uses it crashes with Cannot read properties of null. It only exists on document, not on elements.

What it is. Returns every element that has the class (or all of the classes) you name, as an HTMLCollection. Pass the name without a dot. 'event free' finds elements that have both classes, in any order.

When to use it. In older code you will read, and in the rare case where you want a live collection: one that automatically gains and loses elements as classes change on the page.

Watch out. An HTMLCollection has no forEach() method; loop with for...of or convert it with Array.from(). And because it is live, removing the class from items while you loop over it makes items vanish from under you, so the loop skips some.

What it is. Returns every element with a given tag name, such as 'li' or 'img', as a live HTMLCollection. '*' matches every element. Like most search methods, it also works on an element, where it searches only that element's descendants.

When to use it. Quick counts and older code: how many images does this page have? How many paragraphs are in this article?

Watch out. Same as the class version: no forEach(), and it is live. Anything you could write with it, you can write with querySelectorAll('img') instead.

What it is. Takes any CSS selector and returns the first element that matches, in document order, or null. '#cart', '.btn.primary', 'nav a[href^="http"]' and 'ul > li:last-child' all work.

When to use it. Whenever you want one element and the selector you already know is the clearest way to describe it. Call it on an element to search only inside that element: card.querySelector('h3') finds the heading of that card.

Watch out. It only returns the first match, silently. If your selector matches five buttons, the other four are ignored. An invalid selector (like 'li:') throws a SyntaxError.

What it is. Takes any CSS selector and returns every match as a NodeList, in document order. If nothing matches you get an empty list (length 0), never null.

When to use it. Whenever you need to do something to a group of elements: every card, every required field, every link in the footer. A NodeList has forEach(), so the loop is one line.

Watch out. The list is a snapshot taken when you called it. Elements added to the page later are not in it; call the method again to get a fresh list. And to use array methods such as map() or filter(), convert it first with Array.from() or [...list].

Which one should I pick?
  • One element with an id: getElementById(). Example: document.getElementById('cart')
  • One element, described by any selector: querySelector(). Example: document.querySelector('.site-nav a.active')
  • A group of elements to loop over: querySelectorAll() with forEach(). Example: document.querySelectorAll('.card').forEach(...)
  • Only inside one part of the page: call the method on that element. Example: footer.querySelectorAll('a')
  • A collection that must update itself: getElementsByClassName(). Rare in new code.

Try the methods on a real page. Pick a method, type its argument (or press an example), and every matching element lights up. Watch the type of what comes back, and try the classic mistakes: a # in getElementById, or a dot in getElementsByClassName.

NodeList or HTMLCollection? Live or static?

Methods that return several elements give you a list-like object, not a real array. There are two kinds, and the difference that matters is whether the list keeps itself up to date:

  • A static list is a snapshot. querySelectorAll() returns a static NodeList: it holds exactly the elements that matched at the moment you called it, forever.
  • A live list is a window onto the page. getElementsByClassName(), getElementsByTagName() and an element's children return a live HTMLCollection: add a matching element to the page and it appears in the collection; remove one and it disappears.

Both have a length and numbered items (list[0]), and both work with for...of. Only the NodeList has forEach(). Neither has map() or filter() until you convert it with Array.from(). Press the buttons below and watch the two lengths.

    Walking the tree

    Searching from document is not the only way to reach an element. Every node knows its relatives, so once you hold one element you can step to its parent, its children or its siblings. This is called traversing the DOM. It is handy when the element you want has no id or class of its own but sits right next to one you already have: the label beside a field, the list item that contains the button that was just clicked.

    Each relationship comes in two flavors. The element versions (children, firstElementChild, nextElementSibling) skip text and comment nodes. The node versions (childNodes, firstChild, nextSibling) include everything, whitespace included. Use the element versions unless you specifically want text.

    What it gives you. parentElement is the element that directly contains this node. parentNode is almost always the same thing; the only difference is at the very top, where document.documentElement.parentNode is document but its parentElement is null (the document is not an element).

    When to use it. To go one level up: from a clicked button to the card that holds it, from an input to the <div class="field"> around it so you can mark the whole field as having an error.

    Watch out. Chains such as .parentElement.parentElement.parentElement break as soon as someone adds a wrapper <div> to the HTML. To climb more than one level, closest() is safer.

    What it gives you. children is a live HTMLCollection of the element's child elements. childNodes is a NodeList of every child node, including whitespace text nodes and comments.

    When to use it. To count items (list.children.length) or to visit each direct child with a for...of loop. For "every descendant that matches", use querySelectorAll() instead: children only goes one level down.

    Watch out. On a normally indented list, childNodes.length is roughly double what you expect, because of the whitespace between tags. children has no forEach().

    What it gives you. firstElementChild and lastElementChild are the first and last child elements, or null if there are none. firstChild and lastChild are the first and last child nodes of any type.

    When to use it. To grab the newest or oldest entry in a list, a table's first row, or the single element inside a wrapper.

    Watch out. firstChild is the number one cause of "why is this a text node?" confusion. If the HTML has a line break after the opening tag, firstChild is that line break.

    What it gives you. nextElementSibling and previousElementSibling are the neighboring elements with the same parent, or null at either end. nextSibling and previousSibling are the neighboring nodes, which are usually whitespace text.

    When to use it. To move between items in a list (a "Next" button in a slideshow), or to reach the hint paragraph placed right after a form field.

    Watch out. Always handle null: the last item has no next sibling, and calling a method on null stops your script with a TypeError.

    What it gives you. el.closest(selector) checks the element itself, then its parent, then its grandparent, and so on up the tree, and returns the first one that matches the CSS selector, or null.

    When to use it. Whenever you know what kind of ancestor you want but not how many levels up it is: "the card this button is in", "the row this cell is in", "the form this field is in". You will use it constantly for event delegation in 9.3.

    Watch out. It includes the element itself, so li.closest('li') returns the same li. It only looks up, never down or sideways.

    Which one should I pick?
    • The element that contains this one: parentElement. Example: input.parentElement.classList.add('has-error')
    • A container several levels up: closest(). Example: button.closest('.card')
    • The direct children, one level down: children. Example: list.children.length
    • The first or last item: firstElementChild / lastElementChild. Example: list.lastElementChild.remove()
    • The neighbor: nextElementSibling. Example: field.nextElementSibling.textContent = 'Required'
    • Text nodes on purpose: the node versions (childNodes, firstChild). Rare.

    Modifying the DOM

    Finding elements is only half the job. Every interactive page you have ever used works by changing the DOM: a cart count goes up, an error message appears under a field, a menu opens, a new chat message slides in. JavaScript can change four things about the tree:

    • Content: the text or markup inside an element.
    • Attributes: an image's src, a link's href, a button's disabled.
    • Appearance: its classes and inline styles.
    • Structure: which nodes exist, by creating, moving and removing them.

    The moment you change the tree, the browser redraws the affected part of the page. There is no "save" or "refresh" step. That immediacy is what makes the DOM feel alive, and it is also why a careless change can break a page instantly.

    Changing what is inside an element

    Three properties read and replace an element's contents. They look similar but behave very differently, and one of them is a well-known security hole when used with the wrong data.

    What it is. Reading textContent gives you every character of text inside the element and all its descendants, with the tags stripped out. Writing it removes all the element's children and puts in a single text node containing exactly the string you gave it. Any < or > in the string is shown as a character, never treated as a tag.

    When to use it. Your default for putting text on a page: a name, a price, a count, an error message, and above all anything a user typed or a server sent you.

    Watch out. Setting it wipes out child elements too. If a button contains an icon <svg> and a <span> label, set the span's textContent, not the button's.

    What it is. Reading innerHTML gives you the element's contents as a string of HTML. Writing it hands your string to the HTML parser, which builds brand-new nodes from it and replaces every child the element had.

    When to use it. To insert a chunk of markup that you wrote in your own code, such as a template for an empty state, or to quickly clear an element with el.innerHTML = ''.

    Watch out. Never put user input, or anything from another website, into innerHTML. If the string contains HTML, the browser builds it, including attributes like onerror that run JavaScript. This attack is called cross-site scripting (XSS), and the demo below shows exactly how it works. Also, el.innerHTML += '...' rebuilds every existing child, which destroys their event listeners and anything typed into them.

    What it is. Like textContent, but aware of CSS: reading it gives only the text a user can actually see, with line breaks where the layout has them. Text in elements with display: none or the hidden attribute is left out.

    When to use it. When you want text exactly as it appears on screen, for example to copy what a user sees to the clipboard. Setting it is safe like textContent, and line breaks in your string become <br> elements.

    Watch out. To work out what is visible, the browser has to calculate the layout first, so reading innerText in a loop can be slow. If you just want text, textContent is faster and more predictable.

    Which one should I pick?
    • Text from a user, a form or a server: textContent, always. Example: msg.textContent = name + ' joined the chat';
    • Markup you wrote yourself in the code: innerHTML, or better, build elements with createElement() (below).
    • Text exactly as it looks on screen: innerText, sparingly.

    Attributes and properties

    Attributes are the name="value" pairs in your HTML. JavaScript gives you two ways to work with them: a set of general methods that work for any attribute, and convenient properties that the browser creates for the common ones. The properties are shorter and often smarter (a link's href property gives you the full URL), while the methods give you exactly what is written in the HTML.

    What it does. el.getAttribute('name') returns the attribute's value as a string, exactly as it appears in the HTML, or null if the attribute is missing. el.setAttribute('name', 'value') adds the attribute or replaces its value.

    When to use it. For attributes that have no property shortcut, especially ARIA attributes (aria-expanded, aria-pressed, aria-invalid) that tell assistive technology about state changes. Also when you need the original text, such as a relative href.

    Watch out. Values are always strings. setAttribute('aria-expanded', true) stores the string "true", which is fine, but getAttribute() hands back "false" as a string too, and a non-empty string is truthy, so if (el.getAttribute('aria-expanded')) is always true. Compare with === 'true'.

    What it does. hasAttribute('name') returns true or false. removeAttribute('name') deletes the attribute completely.

    When to use it. For boolean attributes such as disabled, hidden, required and checked, where the attribute's presence is what matters, not its value. disabled="false" still disables a button, because the attribute is there.

    Watch out. The matching properties are usually easier: button.disabled = false removes the attribute for you, and panel.hidden = true adds it.

    What they do. For common attributes, the element object has a property with the same name: img.src, img.alt, a.href, el.id, input.value, checkbox.checked, button.disabled. They are faster to type, and they use real types: checked and disabled are booleans, not strings.

    When to use them. Most of the time, for attributes that have one. Swapping an image is just photo.src = 'large.jpg'.

    Watch out. A few names differ from the attribute: the class attribute is the className property (because class is a JavaScript keyword), and for on a label is htmlFor. And for form fields, the value property is what the user typed now, while the value attribute stays the original default.

    What it does. Any attribute that starts with data- is yours to invent, and el.dataset collects them into an object. data-product-id="42" becomes el.dataset.productId: the data- prefix is dropped and dashed names turn into camelCase.

    When to use it. To attach small pieces of information to elements, such as an id, a price or a state, so your script can read them later without searching an array. It is perfect with event delegation in 9.3: the clicked element carries its own id.

    Watch out. Values are always strings, so Number(el.dataset.price) before doing math. Never store anything secret: anyone can read data- attributes with View Source.

    Which one should I pick?
    • A common attribute with a property: the property. Example: img.src = 'cat.jpg';
    • An ARIA attribute: setAttribute(). Example: btn.setAttribute('aria-pressed', 'true');
    • A true/false attribute: the boolean property. Example: submit.disabled = true;
    • Your own information on an element: dataset. Example: row.dataset.id = '17';

    Styles and classes

    You can change how an element looks in two ways: set CSS properties on it directly through its style object, or add and remove classes that your stylesheet already describes. The second way is almost always better. It keeps all the visual decisions in the CSS, where a designer can find and change them, and your JavaScript only says what state the element is in: open, selected, invalid, dark.

    When to use it. To read what an element really looks like: is it currently visible? How wide did it end up? What color is it?

    When to use it. For almost every visual change: opening a menu, highlighting the selected tab, marking a field invalid, switching on dark mode. Write the look once in CSS (.open { display: block; }) and let JavaScript flip the class.

    Watch out. Class names go in without the dot: classList.add('open'), not '.open'. toggle() returns whether the class is now present, which is handy for updating an aria- attribute to match.

    What it does. className is the whole class attribute as a single string, such as "card featured". Reading it gives that string; writing it replaces every class at once.

    When to use it. When you build a brand-new element and want to set all its classes in one go: li.className = 'item done'.

    Watch out. On an existing element, el.className = 'active' deletes all its other classes, which often breaks its styling. Use classList.add('active') instead.

    Which one should I pick?
    • Switching a state on or off: classList.toggle(). Example: nav.classList.toggle('open');
    • A value only known while the page runs: style. Example: bar.style.width = pct + '%';
    • Reading what an element looks like: getComputedStyle(). Example: getComputedStyle(el).display
    • All classes of a new element at once: className. Example: li.className = 'item';

    Watch out. Calling a method on null crashes, so check that the element exists before removing it. The older form is parent.removeChild(el).

    Events

    Every script you wrote in Chapter 8 ran from top to bottom and then stopped. Interactive pages work differently: most of the time, your code is just waiting. An event is the browser announcing that something happened: a button was clicked, a key was pressed, a form was submitted, the page finished loading, a video ended. You write a function and ask the browser to call it when a particular event happens on a particular element. That function is called an event listener (or event handler).

    This style is called event-driven programming. Think of a doorbell: you do not stand at the front door all day checking for visitors. You go about your business, and the bell tells you when someone arrives. Your setup code runs once, attaches listeners, and finishes. After that, the browser rings the bell, and your listeners run one at a time, as things happen.

      Removing a listener

      To stop listening, call removeEventListener() with the same event type and the same function you added. "The same function" means the same function object, which is why you can only remove a listener you stored in a name. Writing the function out again, even character for character, creates a new, different function, so nothing is removed.

      How events travel: capture, target and bubble

      Click a button inside a <div> inside the <body>, and you have clicked all of them: the button is on top of the div, which is on top of the body. So the browser delivers the event to every one of those elements, in a fixed order called propagation, in three phases:

      1. Capture phase: the event travels down the tree from window and document to the target's parent, running any listeners registered with { capture: true }.
      2. Target phase: the event reaches the element that was actually clicked, event.target, and runs its listeners.
      3. Bubble phase: the event travels back up through every ancestor to window, running ordinary listeners, like a bubble rising through water.

      Ordinary listeners (with no options) run during the bubble phase, so most of the time you only think about bubbling: a listener on a parent hears clicks on all of its children. That one fact makes event delegation possible. In the visualizer, click any of the three boxes (or use the buttons) and watch the event's path.           Event delegation: one listener for many elements

          Imagine a to-do list with 200 items, each with a Delete button. You could attach 200 listeners. But because clicks bubble, a single listener on the <ul> hears every click on every button inside it. In that listener, event.target tells you what was clicked, and closest() climbs from there to the element you care about. With per-item listeners, every piece of code that adds an item must remember to attach a listener too, and forgetting is one of the most common bugs in front-end code.

                Touch events, briefly

                Touchscreens fire touchstart, touchmove and touchend, and their event objects carry a touches list with one entry per finger. You need them less than you might think. A tap already fires click, so ordinary buttons and links work on phones with no extra code. And for dragging, swiping and drawing, pointer events handle fingers, mice and pens with a single set of listeners. Reach for touch events only for true multi-finger gestures, such as a pinch to zoom.

                Taming noisy events: debounce and throttle

                Some events fire far more often than you need: input on every keystroke, scroll and mousemove dozens of times a second, resize continuously while a window is dragged. If each one triggers real work (a search request, a layout calculation), the page slows down or hammers a server. Two small helper functions fix this, and both build on closures from Chapter 8.

                • Debounce: wait until the events stop for a moment, then run once. Perfect for search-as-you-type: search when the user pauses, not after every letter.
                • Throttle: run at most once every so many milliseconds while the events keep coming. Perfect for scroll and mousemove: steady updates, never a flood.

                Forms in JavaScript

                In Chapter 5 you built forms that work with no JavaScript at all: the browser checks required, type="email" and pattern, then sends the data to the server and loads a new page. That is still the foundation. JavaScript adds a layer on top: reading values while people type, checking rules HTML cannot express, showing clear error messages right beside the field, and handling the submission without leaving the page.

                  Error messages everyone can perceive

                  A red border is not an error message. People who are color-blind may not see it, and a screen reader does not announce it at all. Accessible validation follows a few rules:

                  • Put a text message right next to the field that says what is wrong and how to fix it.
                  • Connect the message to the field with aria-describedby, so a screen reader reads it when the field gets focus.
                  • Set aria-invalid="true" on the field while it is wrong, and "false" once it is fixed.
                  • After a failed submit, show an error summary at the top with a link to each problem, and move focus to it (or to the first bad field). A container with role="alert" or aria-live is announced when its text changes.
                  • Time it kindly: reward early, punish late. Do not complain while someone is still typing their first attempt. Check when they leave the field or submit; but once a field is showing an error, re-check on every keystroke so the error disappears the moment it is fixed.

                  Timing matters more than you might think. Choose a strategy, then type an email address slowly (or press "Simulate typing") and notice how each one feels.

                    Regular Expressions

                    A regular expression (regex for short) is a tiny language for describing patterns in text: "exactly five digits", "a word, then an @, then a domain", "any line that starts with #". You met one in Chapter 5, in the pattern attribute. In JavaScript, regular expressions are objects with methods that test whether text fits a pattern, find and extract the parts that match, replace them, and split text apart.

                    They show up everywhere: form validation, search boxes, the find-and-replace in your code editor, cleaning up data, and every programming language you will learn after this one. The syntax looks like line noise at first, but it is built from a small set of pieces, and once you can read those pieces, any pattern breaks down into plain English. The tester in this section does exactly that for you.

                    Pick a family of tokens to see what it does, when to use it, what to watch out for, and a commented example.

                    What they are. Tokens that match one character from a group. \d is any digit, \w any letter, digit or underscore, \s any space, tab or line break, and . almost anything. Square brackets build your own set: [aeiou] is one vowel, [a-z0-9] one lowercase letter or digit, and [^aeiou] one character that is not a vowel.

                    When to use them. Whenever "a character of this kind" is what matters, which is most of the time: digits in a ZIP code, letters in a course code, the separators in a phone number ([ .-]).

                    Watch out. \w only knows English letters: it does not match "é" or "ñ", so it is a poor test for names. Inside brackets most special characters lose their meaning ([.] is a real dot), but a hyphen between two characters makes a range, so put a literal hyphen first or last, or escape it: [ .\-].

                    What they are. Symbols placed after an item to say how many times it repeats: * (zero or more), + (one or more), ? (zero or one, so "optional"), {n} (exactly n), {n,} (at least n) and {n,m} (between n and m). The item can be one character, a class, or a whole group in parentheses.

                    When to use them. Lengths and optional parts: \d{5} for a ZIP code, colou?r for both spellings, (-\d{4})? for an optional ZIP+4.

                    Watch out. Quantifiers are greedy: they grab as much as they can. /<.+>/ on <b>hi</b> matches the whole string, not just <b>. Add ? after the quantifier to make it lazy: /<.+?>/. And a quantifier applies only to the item right before it: /ab+/ is "a, then one or more b".

                    What they are. Tokens that match a position, not a character. ^ is the start of the text, $ the end, and \b any edge between a word character and a non-word character (or the start or end).

                    When to use them. For validation, wrap the pattern in ^ and $ so the whole value must fit. Without them, /\d{5}/ happily matches "abc12345xyz". Use \b to find whole words: /\bcat\b/ skips "concatenate".

                    Watch out. With the m flag, ^ and $ match at the start and end of every line instead of the whole text. Inside square brackets, ^ means "not", which is a completely different job.

                    What they are. Parentheses do two jobs: they group items so a quantifier or | applies to all of them, and they capture what that part matched so you can use it later. (?<year>\d{4}) captures under a name. (?:...) groups without capturing. | means "or": cat|dog. Inside the pattern, \1 means "the same text group 1 matched".

                    When to use them. Pulling pieces out of text (the area code from a phone number, the year from a date), reformatting with replace(), and choices like (jpe?g|png|gif).

                    Watch out. | has the lowest priority of all: /^cat|dog$/ means "starts with cat" OR "ends with dog". Wrap the choices in a group: /^(cat|dog)$/. Groups are numbered by their opening parenthesis, left to right.

                    What it is. A backslash in front of a special character makes it ordinary. The characters with special meanings are . * + ? ^ $ { } ( ) [ ] | \ /, so to match a real dot you write \., and a real dollar sign \$.

                    When to use it. Prices (\$\d+\.\d\d), file extensions (\.pdf$), domain names, anything with punctuation that happens to be special.

                    Watch out. Forgetting the backslash usually still "works" on your test data, which hides the bug: /.pdf$/ also matches "notapdf". In a new RegExp() string, every backslash must be doubled.

                    What they are. Letters after the closing slash that change how the whole pattern behaves. g (global) finds every match instead of stopping at the first. i ignores upper and lower case. m (multiline) makes ^ and $ work on each line. Less common: s lets . match line breaks, and u or v turn on full Unicode support.

                    When to use them. g with matchAll(), replace() of every occurrence, and counting. i for user input where case should not matter. m when working through text line by line.

                    Watch out. A regex with g remembers where its last match ended (its lastIndex), so calling test() on it twice in a row can give true then false for the same text. For yes/no checks, leave g off.

                    Which one should I pick?
                    • A whole value must fit (validation): anchors. Example: /^\d{5}$/
                    • One character of a kind: a class. Example: /[A-Z]/ or /\d/
                    • A length or an optional part: a quantifier. Example: /\d{3,4}/, /-?\d+/
                    • Pull out or reorder pieces: capture groups. Example: /(\d{3})-(\d{4})/
                    • A choice between words: a group with |. Example: /^(red|green|blue)$/
                    • Find every occurrence, any case: flags gi.

                      When to use it. Validation and if statements: is this a valid ZIP code? Does the password contain a digit?

                      Watch out. Use anchors for "the whole value", and leave off the g flag, or repeated calls give alternating answers.

                      What it does. Without the g flag, returns an array describing the first match: [0] is the whole match, [1], [2]… are the capture groups, plus .index and .groups. With g, returns a plain array of every matched string. Returns null when nothing matches.

                      When to use it. Without g to pull pieces out of one match; with g to list or count every occurrence.

                      Watch out. Check for null before using the result: text.match(re).length crashes when there is no match. Use (text.match(re) || []).length.

                      What it does. Returns every match, each with its groups and position, as an iterator you can loop over with for...of or spread into an array. The regex must have the g flag.

                      When to use it. When you need the details of every match: every date in a document with its year and month, every link with its address.

                      Watch out. Without g it throws a TypeError. The result is not an array until you spread it: [...text.matchAll(re)].

                      What it does. Returns a new string in which the match (or, with g, every match) is replaced. In the replacement string, $1, $2… insert capture groups, $<name> a named group, and $& the whole match. You can also pass a function that receives the match and returns the replacement.

                      When to use it. Cleaning and reformatting: removing everything but digits, reordering a date, collapsing extra spaces, masking all but the last four digits of a card number.

                      Watch out. Without g, only the first match is replaced. Strings never change in place: store the result (s = s.replace(...)).

                      What it does. Cuts a string apart wherever the regex matches and returns the pieces as an array.

                      When to use it. When the separator varies: commas with or without spaces, any amount of whitespace, a mix of commas and semicolons.

                      Watch out. Capture groups in a split regex are included in the result. Use (?:...) if you only need grouping.

                      Which one should I pick?
                      • Yes or no: regex.test(text).
                      • Pieces of one match: text.match(regex) without g, then [1] or .groups.
                      • A list of every match: text.match(regex) with g; with details, matchAll().
                      • Clean up or reformat: text.replace(regex, ...).
                      • Break text into parts: text.split(regex).

                      Common patterns, and what they get wrong

                      Regular expressions are excellent at checking format and hopeless at checking truth. A pattern can tell you that "33101" looks like a ZIP code; it cannot tell you that the ZIP code exists, that a date is real, or that an email inbox is there.
