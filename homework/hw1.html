What you will build

Harbor Street Library is a small public library on a city waterfront. (It is made up, so you can use it freely.) The library has written the words for its new website, and it needs someone to turn those words into real web pages and put them online. That is your job.

You will build three pages and publish them together as one website:

index.html: Home

A welcome, opening hours, services, how to get a library card, a featured event, a short FAQ, an announcement and contact details.

events.html: Events

Three upcoming events, each with a date and time, plus a photo with a caption.

report.html: Web Report

Your own investigation of how your live home page travels from GitHub's servers to your browser, with real values you record.

Set up from scratch

This section assumes nothing is installed on your computer yet. If you already have a tool, check that it works and move on to the next step. By the end you will have a placeholder page online at your own address, which proves every tool is working before you write the real pages.

1Install Visual Studio Code

A code editor is a text editor built for writing code. It colors your HTML so mistakes stand out, closes tags for you, shows your whole project folder at once, and has a terminal built in. Visual Studio Code (VS Code) is free and works the same on Windows and macOS.

  1. Go to code.visualstudio.com and download the version for your computer.
  2. Windows: run the installer. On the Select Additional Tasks screen, keep Add to PATH ticked and tick both Add "Open with Code" action boxes. Those let you open a folder in VS Code by right-clicking it.
  3. macOS: open the downloaded file, then drag Visual Studio Code into your Applications folder. Start it from Applications or with Spotlight (Cmd+Space, then type "Visual Studio Code").
VS Code is not Visual Studio

Visual Studio (with a purple icon) is a different, much larger program. You want Visual Studio Code, which has a blue icon.

2Add the Live Server extension

An extension adds a feature to VS Code. Live Server runs a small web server on your own computer and reloads the page in your browser every time you save. You met this idea in Chapter 2.6: your computer acts as the server, at the address http://127.0.0.1:5500. Your page arrives over HTTP, the same way it will on the real web, and you see every change right away.

  1. In VS Code, open the Extensions view: select the icon of four small squares on the left edge, or press Ctrl+Shift+X (Cmd+Shift+X on macOS).
  2. Type Live Server in the search box.
  3. Choose the one by Ritwick Dey and select Install.

You will use it in Step 8: right-click an HTML file and choose Open with Live Server, or select Go Live in the blue status bar at the bottom of VS Code.

  3. Keep the default Git Credential Manager option. Later it lets you sign in to GitHub through your browser.
  1. Open the Terminal app: press Cmd+Space, type Terminal and press Return.
  2. Type git --version and press Return.
  3. If Git is missing, macOS offers to install the command line developer tools. Select Install, accept the license, and wait for it to finish. Git is part of those tools.
  4. Run git --version again. This time it prints a version number.

Now check that VS Code can find Git. In VS Code, choose Terminal > New Terminal from the menu bar. A terminal panel opens at the bottom of the window. Type this and press Enter:

5Tell Git who you are

Every commit records who made it. Git will refuse to make a commit until it knows your name and email, so set them once now. Type these three commands in the VS Code terminal, one at a time, pressing Enter after each. Put your own name and the email address you used for GitHub inside the quotation marks.

git config
Changes one of Git's settings.
--global
Applies the setting to every repository on this computer, so you only do this once per computer.
user.name "Your Name"
The name stamped on your commits. Use your real name as you would like it shown.
user.email "you@example.com"
The email stamped on your commits. Use the same email as your GitHub account, so GitHub can link your commits to your profile.
git config --global --list
Prints your settings so you can check both lines for typos. If you spot one, run the same command again with the correct value.

6Create the repository on GitHub

A repository (or "repo") is a project folder that Git tracks. On GitHub, each repository also gets its own web page where anyone you share it with can browse your files.

  1. On GitHub, select the + button near the top right and choose New repository.
  2. For Repository name, type harbor-street-library exactly: all lowercase, words joined by hyphens. The name becomes part of your website's address, and the next homework expects it.
  3. Set the visibility to Public. GitHub Pages is free for public repositories, and a public repository opens for anyone who has the link.
  4. Turn on Add README (on some versions of the page it is a checkbox labeled Add a README file). This gives the repository a first file, so you can copy it to your computer right away.
  5. Leave the .gitignore and license options as they are, and select Create repository.

GitHub opens the new repository's page, showing its one README file.

7Clone the repository to your computer

Cloning copies a repository from GitHub to your computer, including its full history. The copy remembers where it came from (Git calls that address origin), so later you can send your work back with a single command.

  1. On your repository's page, select the green Code button, make sure the HTTPS tab is chosen, and copy the address. It looks like https://github.com/<username>/harbor-street-library.git.
  2. In VS Code, open a terminal (Terminal > New Terminal). With no folder open, it starts in your home folder, the folder named after your user account.
  3. Run these three commands, one at a time:
mkdir web-projects
"Make directory": creates a folder named web-projects to hold your course work. A directory is another word for a folder.
cd web-projects
"Change directory": moves the terminal into that folder, so the next command runs there.
git clone <address>
Downloads the repository into a new folder named harbor-street-library and connects it to GitHub.
Keep the repository out of synced folders

Do not clone into a folder that OneDrive, iCloud Drive, Dropbox or Google Drive is syncing, and never inside another repository. Syncing tools and Git both try to manage the same files and can end up fighting over them. The web-projects folder in your home folder avoids both problems.

Save before you look

VS Code shows a dot on the tab of any file with unsaved changes. Live Server, the validator and Git only see what is saved. If you like, turn on File > Auto Save so VS Code saves for you.

9Commit your work and push it to GitHub

Your placeholder page exists only on your computer. Saving a file does not change your repository's history, and nothing reaches GitHub until you push it. Getting work online takes three moves: add the changes you want to include, commit them as a snapshot with a message, and push the new commit to GitHub. Run these in the VS Code terminal:

git status
Shows which files are new or changed since the last commit, and which are ready to be committed. It never changes anything, so run it whenever you are unsure what state you are in. Right now it lists index.html in red as an untracked file.
git add .
Stages your changes: it puts them in the next snapshot. The dot means "this folder and everything in it." Run git status again and index.html turns green.
git commit -m "Add placeholder home page"
Records the staged changes as a commit. The text after -m is the commit message: a short note saying what changed, so you (and anyone reading your history) can tell your commits apart.
git push
Uploads your new commits to the repository on GitHub, the origin you cloned from.

The first time you push, you have to prove to GitHub that the repository is yours. VS Code asks to sign in with GitHub, or on Windows the Git Credential Manager does, and a browser window opens. Sign in and approve the request. Git remembers the sign-in, so you do this once per computer.

Reload your repository's page on GitHub. index.html is there, next to your commit message.

The empty images folder does not upload

Git tracks files, not folders, so an empty folder never reaches GitHub. That is fine: images/ uploads with your first photo in Part 1.

10Turn on GitHub Pages

GitHub Pages is a static host, the kind of hosting you read about in Chapter 2.6. It sends the files in your repository to visitors exactly as they are, over HTTPS, for free.

  1. On your repository's page, select the Settings tab. (On a narrow window it may be hidden under the … menu.)
  2. In the left sidebar, under Code and automation, select Pages.
  3. Under Build and deployment, set Source to Deploy from a branch.
  4. Under Branch, choose main and the folder / (root), then select Save.
  5. Publishing is not instant. Wait a little, then reload the Pages settings until the top says Your site is live at https://<username>.github.io/harbor-street-library/. Select Visit site.

Read the address you just opened. The host, <username>.github.io, is your own corner of GitHub Pages. The path, /harbor-street-library/, is your repository. The path ends in a slash, which asks for "this folder" rather than a particular file, so the server sends the folder's default file: index.html. That is why the file must be named exactly index.html and sit at the top level of the repository.

From now on, every push republishes the site. Your repository's Actions tab shows a pages build and deployment run for each push; when it has a green check, your changes are live.

The cycle you will repeat

For the rest of this homework, and for the rest of the course: edit and save, check the page in Live Server, validate it, then git add ., git commit -m "..." and git push, and finally check the live site. Commit often, with messages that say what changed, such as "Add opening hours" or "Fix FAQ markup".

Part 1: Mark up the library's pages

The library has written the words for its Home and Events pages. They are below as plain text. Your job is to choose the right HTML element for every piece, based on what that piece is: a heading, a list of steps, a date, a self-contained event, a side note. That choice is the heart of semantic markup, and it is the skill this part practices.

You will not write any CSS in this homework. Your pages will look plain, with the browser's default fonts, black text and blue links. That is expected, and it is a good sign: well-structured HTML is readable before any styling. Styling comes next.

How to work

  1. Replace everything in your placeholder index.html with the page frame below, and put your name in the comment at the top.
  2. Paste the index.html content inside <main>, then move the site name and menu into the header, and the contact details, copyright line and photo credit into the footer. Then work down the page, wrapping each piece of text in the element that matches its meaning.
  3. Save often and watch the result in Live Server.
  4. Validate the page and fix every error (see Check your pages with the W3C validator).
  5. When index.html is done, create events.html in the same folder, copy in the whole frame from index.html, and change the title, description, top comment, aria-current link, <h1> and main content.
  6. Commit and push, then check both pages on your live site.

What your finished pages must use

Every item below was taught in Chapter 3; the link under each group takes you back to the section that explains it. These apply to index.html and events.html, and the first three groups apply to report.html too.

Every page's skeleton

Taught in 3.4 Structure of HTML Documents 3.2 HTML Syntax

  • <!DOCTYPE html> as the very first line, so the browser uses standards mode.
  • <html lang="en"> around everything else.
  • <meta charset="utf-8"> as the first element in the <head>.
  • The viewport <meta>: <meta name="viewport" content="width=device-width, initial-scale=1">.
  • A <title> that is different on every page, such as Home · Harbor Street Library and Events · Harbor Street Library.
  • A <meta name="description"> on every page that summarizes that page in a sentence or two.
  • An HTML comment at the top of each page, right after the DOCTYPE, saying which page it is and who wrote it.

Page structure and navigation

Taught in 3.6 HTML5 Semantic Structure Elements

  • <header>, <nav>, <main> and <footer> on every page, with the <nav> inside the header and exactly one <main>.
  • The same menu on every page, in this order: Home, Events, Web Report, linking to index.html, events.html and report.html.
  • Optional but recommended: aria-current="page" on the menu link for the page you are on.

Headings

Taught in 3.5 Quick Tour of HTML Elements: Headings

  • Exactly one <h1> per page, naming that page's main topic, inside <main>: "Welcome to Harbor Street Library" on the home page and "Upcoming events" on the events page.
  • No skipped levels on the way down: the parts of an <h1> are <h2>s, and the parts of an <h2> are <h3>s. Never pick a level for its size.

Lists

Taught in 3.5 Quick Tour of HTML Elements: Lists

  • <ul> for the services, and for the menu links inside <nav>. Their order does not change their meaning.
  • <ol> for the steps to get a library card. Their order matters.
  • <dl> for the opening hours: each day (or range of days) is a <dt>, and its hours are the <dd> that follows.

Grouping the content

Taught in 3.6 article, section, aside or div?

  • <section>, each starting with its heading, for the themed parts of the home page: opening hours, services, library card, featured event and FAQ.
  • <article> for each of the three events on the events page. Each one makes sense on its own.
  • <aside> for the announcement on the home page. It is related to the page but not part of its main flow.

Dates, the FAQ and the figure

Taught in 3.6 figure, details and time

  • <time datetime="..."> around every calendar date, with a machine-readable datetime such as 2026-11-26 for a date, or 2026-10-22T19:00 for a date and time (24-hour clock). The copyright year does not need one.
  • <details> for each FAQ question, with the question in its <summary> and the answer after it.
  • At least one <figure> with a <figcaption>: the photo on the events page.

Images

Taught in 3.5 Quick Tour of HTML Elements: Images

  • At least one image on index.html (in the welcome part) and one on events.html (inside the figure).
  • Every image file saved in your images folder with a lowercase name and no spaces, such as images/storytime.jpg, and linked with that relative path.
  • Meaningful alt text on every image that carries information: what the image shows, in the context of the page, in a sentence or less. A purely decorative image, if you add one, gets alt="" so screen readers skip it.
  • width and height attributes on every image, set to the file's real size in pixels, so the page does not jump while images load.
  • Your own photo or an openly licensed one, credited in the footer of the page that shows it (see Find photos you are allowed to use).

Text that carries meaning

Taught in 3.3 Importance and emphasis: strong, em, b and i

  • <strong> at least once, for something important, serious or urgent.
  • <em> at least once, for stress that changes how a sentence reads.
  • Both chosen by meaning, not by looks. Do not use <b> or <i> just to get bold or italic text.

Links, contact details and entities

Taught in 3.5 Links, relative paths and character entities 3.6 address

  • Relative links between your own pages: href="events.html". Never an address that starts with / and never a full https:// address for your own pages.
  • "See all upcoming events on the Events page" links to events.html, with meaningful link text (not "click here").
  • The contact details inside <address> in the home page footer, with a mailto: link for the email and a tel: link for the phone number (for example, tel:+15555550142). Copying the same footer to every page is fine.
  • The © symbol written as the entity &copy; in the copyright line on every page.

House style and validity

Taught in 3.2 HTML Syntax 3.1 Validate as you go

  • File and folder names in lowercase with no spaces: index.html, events.html, report.html, images.
  • Lowercase element and attribute names, attribute values in double quotes, every non-void element closed, and nested elements indented by two spaces.
  • Every page passes the W3C Nu Html Checker with no errors.
Why links must not start with a slash here

A link like /events.html starts at the root of the host (Chapter 2.3). On GitHub Pages the root of your host is https://<username>.github.io/, but your site lives one folder down, in /harbor-street-library/. So /events.html leads to a 404, while events.html is resolved against the current page and lands in the right folder. The same goes for images: write images/storytime.jpg, never a path from your own computer's disk.

Hint: an FAQ question with details and summary

Each question is its own <details>. The browser shows only the <summary> until a visitor opens it, with no JavaScript needed.

Hint: writing dates with time

People read the text inside <time>; software reads the datetime attribute. Keep the visible text exactly as the library wrote it, and put the machine-readable version in the attribute. Hours use the 24-hour clock, so 7:00 PM is 19:00.

Hint: an image inside a figure

Notice that the alt text and the caption say different things. The alt text replaces the picture for someone who cannot see it; the caption adds information for everyone.

Hint: where do strong and em belong in this content?

Read the text aloud and listen. Some sentences carry a warning or a requirement that visitors must not miss: that is importance, so <strong>. Some sentences would sound different, or mean something slightly different, if you stressed one word: that is emphasis, so <em>.

Good candidates: the fact that registration is required for Code Club, the fact that the library will be closed on Thanksgiving, and the word "do" in "please do return items".

Hint: how do I find my photo's width and height?

Drag the image file from your images folder onto an empty browser tab. Chrome, Edge and Firefox show the size in the tab title, for example storytime.jpg (800×533): the first number is the width, the second the height. You can also look in the file's properties: on Windows, right-click it and choose Properties > Details; on macOS, select it in Finder and choose File > Get Info > More Info.

Find photos you are allowed to use

You may not use any picture you find online: photos belong to the people who took them. Use one of these instead:

  • Your own photo. A bookshelf, a library, a reading nook, the water. Credit it as "Photo by (your name)".
  • An openly licensed photo. Search Openverse or Wikimedia Commons. Their photos carry licenses, such as Creative Commons (CC BY, CC BY-SA) or public domain (CC0), that let anyone reuse them, usually as long as you credit the creator. Openverse shows the exact credit text to copy, for example: "Reading Room" by A. Photographer, licensed under CC BY 2.0.

Download the photo into your images folder and rename it in lowercase with hyphens instead of spaces. If it is very large (thousands of pixels wide), make a smaller copy about 800 to 1200 pixels wide so your page loads quickly: on Windows use the Photos app's Resize image; on macOS open it in Preview and choose Tools > Adjust Size. Then put the credit in the footer of the page that shows the photo.

Do not link to images on other websites

Every image must be a file inside your repository, linked with a relative path. An image loaded from someone else's site uses their server without asking and can disappear at any time.

Check your pages with the W3C validator

Browsers quietly repair broken HTML (Chapter 3.1), so a page that looks right can still be wrong, and a different browser, a screen reader or a search engine may repair it differently. The validator shows you every mistake the browser was hiding.

  1. Go to validator.w3.org/nu, the W3C Nu Html Checker.
  2. In the Check by menu, choose file upload, select Choose File, and pick your saved index.html. (After you push, you can instead choose address and paste your live page's URL.)
  3. Select Check.
  4. Fix the first error, save, and check again. Work from the top down: one early mistake, such as an element you forgot to close, often causes several messages further down, and they all vanish when you fix the first one.
  5. Repeat until the page says Document checking completed. No errors or warnings to show. Then do the same for every other page.

Errors must all be fixed. Read every warning too and fix it if you can. Messages labeled Info, such as "Trailing slash on void elements has no effect", are notes rather than mistakes.

What common validator messages mean
"End tag for body seen, but there were unclosed elements." or "Unclosed element section."
Something was opened and never closed. Find the element the message names and add its closing tag in the right place. Consistent indentation makes the gap easy to spot.
"Stray end tag li."
A closing tag has no matching opening tag, often left over after you moved code around. Delete it, or add the opening tag it belongs to.
"No p element in scope but a p end tag seen."
You put a list, heading or section inside a <p>. A paragraph can only hold text and inline elements, so the browser ended it early. Move the block element outside the paragraph.
"Element li not allowed as child of element nav in this context."
An <li> must sit directly inside a <ul> or <ol>. Put a <ul> between the <nav> and its list items.
"An img element must have an alt attribute, except under certain conditions."
Add an alt attribute: a description of the image, or alt="" if it is purely decorative.
"Bad value ... for attribute datetime on element time."
The datetime attribute needs the machine format: 2026-10-22, or 2026-10-22T19:00 with a time. The friendly version goes between the tags, not in the attribute.
"Element details is missing a required instance of child element summary."
Every <details> must start with a <summary>.
"A charset attribute on a meta element found after the first 1024 bytes."
The browser has to learn the encoding almost immediately. Keep <meta charset="utf-8"> as the first line inside the head, and keep the comments above it short.

A row for favicon.ico with a 404 status is expected: browsers ask for a tab icon automatically, and your site does not have one yet. Count it in your total and say what it was. 4. Explain the journey from Enter to pixels

Review Chapter 2 Review: trace one request

In the From Enter to pixels section, write an <ol> that explains, step by step, what happened between pressing Enter on your live address and seeing your home page. Use one <li> per step, one to three sentences each, in your own words, and name your real values wherever they fit: your host name, the addresses you found, your protocol, your status code. It must cover these steps, in this order:

  1. The browser checks whether it already knows the host's address: its own DNS cache, then the operating system's.
  2. Your recursive resolver finds the address. If it has no cached answer, it asks a root server, which refers it to the servers for the io top-level domain, which refer it to the authoritative servers for github.io, which answer. The answer is cached for its TTL.
  3. The browser opens a TCP connection to the remote address on port 443 with the three-way handshake (SYN, SYN-ACK, ACK). If your Protocol column showed h3, say instead that HTTP/3 connects with QUIC over UDP, which has no TCP handshake.
  4. The TLS handshake: the browser and server agree on encryption keys, and the browser checks GitHub's certificate.
  5. The browser sends an HTTP GET request for your path, with request headers such as Host.
  6. The server sends the response: the status code, response headers such as Content-Type, and the HTML as the body.
  7. The browser decodes the bytes into characters and parses the HTML into the DOM.
  8. While parsing, it finds your <img> elements and sends a request for each image.
  9. It renders the page: it builds the render tree, works out the layout, paints the pixels and composites the layers onto the screen.
