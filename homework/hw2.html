Two path mistakes that only break online Both of these work on your laptop and fail on GitHub Pages, which is why they are so confusing.
A leading slash. href="/css/styles.css" means "start at the root of the web server". On GitHub Pages your site lives in a subfolder, https://<username>.github.io/harbor-street-library/, so the root is <username>.github.io/ and the browser looks for the stylesheet in the wrong place. Step 1: Link the stylesheet on every page

Why an external stylesheet instead of the other two places CSS can live (4.3)? One file styles every page, so a design change means editing one file instead of six. The browser downloads it once, caches it, and reuses it on every page, so later pages load faster. An inline style="" attribute styles only one element, cannot be reused, and beats every normal rule in your stylesheet, which makes it hard to override later. A <style> element works for only one page.

  • No page contains a <style> element or a style="" attribute. All presentation lives in styles.css. 4.1 4.3

Step 3: Design tokens, colors and units

Design tokens are the few values your whole design is built from: a handful of colors, two font stacks, a spacing size. You store them as custom properties on :root (the <html> element) and read them everywhere else with var() (4.8). Then a design change, such as a new brand color, is one edit instead of a search through the whole file. The example below uses made-up names and values; choose your own colors for a library.

Units matter as much as values (4.2). rem is relative to the root font size, so text sized in rem grows when a reader turns up the browser's default size. em is relative to the element's own font size, so padding in em grows with the text inside it. ch is the width of the "0" character, which makes it perfect for limiting line length. px stays fixed, which suits thin borders.

  • A :root rule defines custom properties for your colors (at least text, background, brand and link), your font stacks, and your spacing. 4.8
  • Every other rule reads those values with var(). Outside :root, no color and no font stack is typed out directly. 4.8
  • Your colors use at least two notations: hex (#1d4e89) and rgb() or hsl(). 4.2
  • Units are chosen on purpose: rem for font sizes, rem or em for padding and margins, ch or % for line length and widths, and px only for small fixed details such as borders. 4.2

Step 4: Typography

Most of your site is text, so typography does more for it than almost anything else (4.7). A font stack lists fonts in order of preference, and the browser uses the first one the visitor's device actually has, which is why the stack must end with a generic family such as sans-serif or serif that always exists. Headings in a different stack from the body text give the page a clear voice and help readers see its structure.

  • The body uses a font stack that ends in a generic family. 4.7
  • Headings use a different font stack, which also ends in a generic family. 4.7
  • h1, h2 and h3 each have a font-size in rem, getting smaller from h1 to h3. 4.7
  • Body text has a line-height of about 1.5, written without a unit. 4.7
  • Paragraphs and lists have a readable measure: a max-width of about 70ch (anywhere from 60ch to 75ch is fine). 4.7
Optional: using a web font

If you want a font your visitors probably do not have, you can load a hosted web font (4.7). Paste the font service's <link> into each page's <head> before the link to styles.css, then put the font's name at the front of a normal font stack in your tokens, keeping the fallbacks and the generic family after it. Load only the weights you use.

Step 5: The box model and page layout

Every element is a box: content, then padding, then a border, then margin (4.6). By default, width sets only the content area and padding and border are added on top, so a box grows wider than the width you wrote. The border-box rule below changes that for every element, which makes every size you set predictable.

Chapter 4 centered boxes with margin: 0 auto. margin-inline: auto is the same idea written as one property: it sets only the left and right margins (the "inline" direction is the direction a line of text runs) and leaves the top and bottom margins alone. Use it for this homework.

For the navigation, remember the three display types from 4.6. List items are block, so they stack. Links are inline, so padding on them does not push anything away. inline-block keeps a link on the line but lets its padding count, which turns each link into a comfortable, easy-to-tap target (5.6 recommends about 44 by 44 pixels for thumbs).

  • The stylesheet starts (after the tokens) with *, *::before, *::after { box-sizing: border-box; }. 4.6
  • The main content is centered with a max-width and margin-inline: auto. 4.6
  • Boxes use padding for space inside them (header, footer, main) and margins for space between them (sections, figures, paragraphs). 4.6
  • At least one element has a visible border and at least one has a background color, both from your tokens. The announcement <aside> on the Home page and each event <article> on the Events page are natural places for both. 4.6
  • Navigation links are display: inline-block with padding, and the list bullets are gone. 4.6
Hint: my nav links still stack up with bullets

The bullets and the stacking come from the list, not the links. nav ul needs list-style: none to drop the bullets and padding-left: 0 to remove the indent browsers add to lists. Each nav li is a block box by default, so it starts on a new line; making the list items display: inline-block too lets them sit side by side.

Hint: an image is wider than the screen on a phone

An image is as wide as its file unless you say otherwise. img { max-width: 100%; height: auto; } lets an image shrink to fit its container while keeping its proportions, and it never makes a small image bigger.

Step 8: Explain your cascade in a comment

When two rules set the same property on the same element, the cascade picks exactly one winner (4.5). Specificity is written A-B-C: A counts ids, B counts classes, attributes and pseudo-classes, and C counts element names and pseudo-elements. Compare A first; only if A ties, compare B; only if B ties, compare C. If specificity ties completely, the rule that comes later wins. Separately, some properties, mostly text ones like color and font-family, inherit from parent to child, while box properties like padding and border do not.

Write a comment block at the very top of styles.css that shows you can apply this to your own stylesheet. The example below is from a different site (the hiking club from Chapter 4) so you can see the format; your notes must use selectors from your file.

  • The top comment lists three of your own selectors with their specificity written as A-B-C. 4.5
  • It names two of them that set the same property on the same element, says which rule wins, and explains why (specificity, or order when specificity ties). 4.5
  • It gives one example of inheritance from your stylesheet: a property you set on a parent that its children inherit. 4.5
Hint: check your specificity numbers

Chapter 4's specificity calculator scores any selector you type. You can also check in the browser: right-click an element, choose Inspect, and in the Styles pane hover over a selector. Step 9: Check color contrast

Text is only readable if it stands out from its background. The accessibility guidelines ask for a contrast ratio of at least 4.5:1 for normal body text (4.2, 5.5). Your browser can measure it for you:

  1. Inspect a paragraph

    Right-click a paragraph on your page and choose Inspect. DevTools opens with that paragraph selected.

  2. Open the color picker

    In the Styles pane, find the color declaration that applies (it may be inherited from body) and click the small colored square next to its value.

  3. Read the contrast ratio

    Chrome and Edge show a Contrast ratio line with a number and check marks. One check mark means it meets the 4.5:1 minimum for normal text. A warning icon means the text is too faint: make the text darker or the background lighter by editing your tokens, then check again.

  4. Repeat for links

    Check a normal link, a nav link, the table header text and your form's button text, each against its own background.

  • Body text and links have a contrast ratio of at least 4.5:1 against their backgrounds, checked in DevTools. 4.2 5.5

The markup

Here is the technique on a different, smaller table. Your schedule follows the same pattern with five columns and eight rows.

  • The table has a <caption> as its first child, such as "Weekly program schedule". 5.1 5.5
  • The header row is inside <thead>, and every data row is inside <tbody>. 5.1
  • The five column headers are <th scope="col">: Day, Time, Program, Ages, Room. 5.1 5.5
  • Each day cell is a row header, <th scope="row">; the other cells are <td>. 5.5
  • All eight rows from the data above are present, and the Sunday row uses one colspan="4" cell. 5.1
  • The table sits inside a wrapper element (a <div> with a class) so it can scroll inside itself. 5.2
  • Tables are used for data only, never to position things on a page, and no page uses the obsolete border, cellpadding, cellspacing or bgcolor attributes. 5.1 5.2

The styles

An unstyled table is hard to read: no lines, cramped cells, headers that do not line up with their data (5.2). Add the table rules to the components section of styles.css. The wrapper matters most on a phone: a table cannot shrink narrower than its content, so without the wrapper a wide table pushes the whole page sideways. With overflow-x: auto, only the wrapper scrolls, and only when the table does not fit. (overflow-x is the horizontal-only version of the overflow property from 4.6.)

  • border-collapse: collapse, so neighboring cell borders merge into single lines. 5.2
  • Padding on th and td, so the data has room to breathe. 5.2
  • Styled column headers: for example a background color, bold text and a bottom border, all from your tokens. 5.2
  • Zebra stripes on the body rows with :nth-child(). 5.2
  • Aligned text: header cells use the same text-align as the data under them (browsers center <th> by default), and times line up with font-variant-numeric: tabular-nums. 5.2
  • The wrapper has overflow-x: auto. At 390 pixels wide, the table scrolls inside its wrapper and the page does not scroll sideways. 5.2
Common table mistakes
  • Cells stick out past the right edge. A row has too many cells. Count the slots: a colspan="4" cell uses four, so the Sunday row needs exactly one more cell (the day).
  • table > tr matches nothing. The browser puts rows inside a <tbody>, so no row is a direct child of the table. Use tbody tr.
  • The header row is striped too. tr:nth-child(even) also counts rows in <thead>. Start the selector with tbody.
  • The page still scrolls sideways on a phone. The overflow-x rule is on the table instead of the wrapper, or the wrapper's class in the HTML does not match the class in the CSS.

The library card application form

On card.html, under the <h1>, write a sentence or two inviting visitors to apply for a library card, then build the form. When a visitor presses the submit button, the browser checks their answers and then goes to thanks.html.

Where the answers go, and why GET

A form's action is the address that receives the data, and its method is how the data travels (5.3). A real library would send this form to a program on its web server with method="post", over HTTPS, because POST keeps personal details out of the address bar, browser history and server logs. You cannot do that here: GitHub Pages is a static host. It can only hand out files you uploaded; it has no program to receive a POST, so it answers one with an error.

So your form uses method="get" with action="thanks.html". With GET, the browser adds every name=value pair to the address as a query string, the same query strings you took apart in 2.3, and GitHub Pages simply serves thanks.html. That turns the address bar into a window on exactly what your form sends:

https://<username>.github.io/harbor-street-library/thanks.html?full_name=Ana+Ruiz&email=ana%40example.com&phone=941-555-0123&birth_date=2004-05-17&card_type=adult&interests=history&interests=events&branch=main&notes=&agree=yes

Notice the details from 5.3 and 5.4: a space becomes +, @ becomes %40, each checked box sends its own pair (so interests appears twice), an empty text box still sends its name with nothing after the =, and a date always travels as YYYY-MM-DD whatever the visitor saw on screen.

Hint: writing the phone pattern

pattern takes a regular expression, and the browser checks it against the whole value (5.7). [0-9] means "one digit", {3} means "exactly three of the thing before", and a hyphen outside square brackets is just a hyphen. So three digits, a hyphen, three digits, a hyphen and four digits is pattern="[0-9]{3}-[0-9]{3}-[0-9]{4}". Test it: 941-555-0123 should pass, and 9415550123 and 941-5550-123 should fail.

Hint: where do I find today's date for max?

Write the date you build the page in the same format a date input sends: four-digit year, two-digit month, two-digit day, separated by hyphens. The fifth of March 2026, for example, is written max="2026-03-05". The date picker then refuses any later date, and typing one in makes the field invalid.

  • Field borders are dark enough to see against the background (at least 3:1). 5.6
  • Every control shows a clear focus ring with :focus-visible. 5.6
  • Invalid fields get an error style with :user-invalid, one that does not rely on color alone (for example, a thicker border as well as a red one). 5.6
  • The fieldsets, hints and submit button are styled from your tokens, and the button text meets 4.5:1 contrast. 5.6
Hint: I added :user-invalid and nothing turns red

That is :user-invalid doing its job: it waits until the visitor has interacted. Type a bad email, then press Tab to leave the field, or press the submit button with bad data. :invalid would match immediately, painting every empty required field red before anyone has typed a thing, which is why 5.6 recommends :user-invalid.

Hint: the radio buttons and checkboxes stretched across the whole form

A rule like input { width: 100%; } hits every input, including radios and checkboxes. Aim the width rule only at the text-style inputs, for example with input:not([type="radio"], [type="checkbox"]) as in 5.6, or by listing the types you want.

Use the site with only the keyboard

Many people never use a mouse: they navigate with a keyboard, a switch device or voice control, all of which move focus the way the Tab key does (5.5). Put your mouse away and try it on card.html:

  1. Tab through everything

    Press Tab repeatedly. Focus should visit every nav link and every form control in the same order you see them, and your focus ring should be clearly visible each time. Shift + Tab goes backward.

  2. Answer every question

    Type into the text fields. In the card type group, Tab lands on one radio and the arrow keys move between the options. Space checks and unchecks a checkbox. On the select, the arrow keys change the option.

  3. Submit

    Press Enter while you are in a text field, or Tab to the button and press Enter or Space. Try it once with bad data (focus should jump to the first problem) and once with good data.

Using Safari on a Mac? Safari skips links when you press Tab unless you turn on Press Tab to highlight each item in its settings. Chrome, Edge and Firefox do not need that, so use one of them for this test.
