      Part 1 · 10.1, 10.3 and 10.5

      Data from an API, summarized with array functions

      Chapter 10 replaced most loops with array functions, which each do one job and give back a new value instead of changing the array: filter keeps the items that pass a test, map turns each item into something else, reduce folds a whole array into a single value such as a total, and toSorted gives back a sorted copy (plain sort reorders the original array in place). Because each one returns a new value, they chain into something that reads like a sentence: tools.filter(isAvailable).map(getName).toSorted() means "the available tools, as names, in order".

      Data from a server takes time to arrive, so fetch(url) does not wait for it: it returns a promise, a placeholder for an answer that will arrive later. Inside a function marked async, the word await pauses that function, and only that function, until the promise settles, while the rest of the page keeps responding. Two details catch everyone out. First, fetch rejects only when no answer arrives at all, such as when the connection drops; a 404 or a 500 is still an answer, so the promise resolves and you must check res.ok, which is true only for statuses from 200 to 299. Second, reading the body is asynchronous too, so the data comes from await res.json().

      Challenge 10The tool report

      The skill. Most front-end code does two jobs over and over: it asks a server for data, and it boils that data down to the few facts a page needs. Doing the first job carefully, so that a server error or a dropped connection gives a clear message instead of a crash, and the second job clearly, one array function per step, is the heart of Chapter 10.

      Your task. The Elm Street Tool Library lends tools the way a library lends books. Its practice API is described at the top of the JS tab. Finish getReport() so that it:

      1. Fetches /api/tools, and returns { error: 'Could not reach the library server.' } when no answer arrives at all.
      2. Returns { error: 'The library server answered 500.' }, with the real status, when the answer is not ok.
      3. Otherwise returns an object with four properties: available, the names of the tools on the shelf from A to Z; onLoan, how many tools are out; totalLoans, every tool's loans added up; and busiest, the name of the tool with the most loans, or null when there are no tools.
      4. Uses filter, map and reduce, with no for or while loop.

      The last line of the starter prints your report in the Console. The checks call getReport() themselves, with other tools, an empty list, server errors and a dropped connection, so it must work for any answer.

      Hint for Challenge 10

      Declare let res; before the try, so it still exists after the block: try { res = await fetch('/api/tools'); } catch (error) { return { error: OFFLINE }; }. Then if (!res.ok) return { … }; and const tools = await res.json();. Each property is one chain: tools.filter((t) => t.available).map((t) => t.name).toSorted() for the names, and .length of a filter for a count. reduce needs a starting value: tools.reduce((sum, t) => sum + t.loans, 0). For busiest, return null first when tools.length === 0; then reduce can keep whichever of two tools has more loans, and you take .name of the winner.

      Part 2 · 11.2 and 11.3

      A React component that follows its state

      In React you do not change the page step by step. You write components: functions that receive data and return a description of what the page should look like, written in JSX. A parent passes data down to a child as props, like attributes: <ToolCard tool={drill} /> hands the card one tool, which the card reads but never changes. A component that draws a list turns an array into elements with map(), and gives each element a key taken from the item's id, so React can tell the items apart when the list changes.

      Data that changes while the page is open, such as what a visitor types in a search box, is state. const [query, setQuery] = useState(''); gives the component the current value and a setter. Calling the setter tells React to run the component again, and the new JSX it returns becomes the new page. A form field whose value comes from state is controlled: value={query} shows the state, and onChange={(e) => setQuery(e.target.value)} stores each keystroke. Anything that can be worked out from state and props, such as the list of tools that match the search, is calculated during the render. Keeping a second copy of it in state would give the page two versions of the truth that can fall out of step.

      Challenge 11Search the tool shelf

      The skill. A search box and a filter are the smallest complete example of React's model: two pieces of state, two controlled inputs, and one list worked out from them on every render. Once this pattern is familiar, sorting, paging and tabs are the same idea with different rules.

      Your task. The data, the page and the App component are ready. In the JSX tab, finish the two components so that:

      1. ToolCard draws one <li className="tool">, with the extra class on-loan for a tool that is out, holding the name in an <h2> and a <p className="meta"> that reads like Garden · Available or Power tools · On loan.
      2. ToolBrowser keeps two pieces of state: the search text and whether Available only is ticked. Both controls are controlled inputs.
      3. The tools shown are worked out during the render: names that contain the search text, ignoring upper and lower case and spaces at either end, and only available tools while the box is ticked.
      4. A <p className="summary"> reads like Showing 4 of 6 tools, followed by a <ul className="tools"> with one <ToolCard> per tool shown, each with key={tool.id}, or <p className="empty">No tools match.</p> when nothing matches.

      Everything is drawn with JSX: no innerHTML, append or querySelector. The checks also draw ToolBrowser with tools of their own, and type and tick in that copy, so it must work for any array.

      Hint for Challenge 11

      A class name can be chosen with a ternary: className={tool.available ? 'tool' : 'tool on-loan'}, and text mixes with expressions: <p className="meta">{tool.category} · {tool.available ? 'Available' : 'On loan'}</p>. For the search, tidy the query once with query.trim().toLowerCase(), then keep a tool when tool.name.toLowerCase().includes(…) is true and (!onlyAvailable || tool.available) is true too. A checkbox stores e.target.checked, not e.target.value. To choose between the list and the message, use a ternary inside the JSX: {shown.length === 0 ? <p …>…</p> : <ul …>…</ul>}.

      Part 3 · 13.3 and 13.4

      The other side: an API in Node.js and Express

      Parts 1 and 2 ran in the browser. Part 3 is the other end of the request: the server that answers /api/tools. In Node.js with the Express framework, each route pairs an HTTP method and a path with a function that Express calls for every matching request: app.get('/api/tools/:id', (req, res) => { … }). The function reads the request from req and answers through res. Three parts of a request are read in three different ways. A route parameter such as :id arrives in req.params.id, always as text. The query string, everything after ? in the URL, arrives in req.query. The body of a POST, where a client sends the details of something new, arrives in req.body, but only after app.use(express.json()) has turned its JSON text into an object.

      A good API also answers with the right status code, because clients decide what to do from it: 200 OK for a normal answer, 201 Created when the request made something new, 400 Bad Request when the request is missing something, and 404 Not Found when there is nothing at that address. The res.ok test you wrote in Part 1 depends on exactly these codes. The server must also check every request itself, because anyone can send any request with a tool such as curl, without ever opening your web page.

      Challenge 13The tool library API

      The skill. Reading the three parts of a request, answering with the right status, and refusing bad input are what every API route does, whatever it is about. These three routes are the core of the CRUD API from Chapter 13.

      Your task. In the server.js tab, add the JSON body parser and three routes:

      1. GET /api/tools sends every tool as JSON, or only the available ones for GET /api/tools?available=true.
      2. GET /api/tools/:id sends the tool with that id, or answers 404 with { "error": "Tool not found" }.
      3. POST /api/tools answers 400 with { "error": "name is required" } when the body has no name or a blank one. Otherwise it adds a new tool with the next id (one more than the highest), the name without spaces at either end, the category sent (or 'Other' when none is sent), available: true and loans: 0, and answers 201 with that tool.

      Try each route with the pretend client under the code. To send a POST, choose it as the method and type a JSON body such as { "name": "Tile cutter", "category": "Hand tools" }. The checks send their own requests, including bad ones.

      Hint for Challenge 13

      Start the list route with let list = tools; and replace it with a filtered copy when req.query.available === 'true'. In the id route, const tool = tools.find((t) => t.id === Number(req.params.id)); gives undefined when nothing matches, and return res.status(404).json(…) stops the function there. In the POST route, const name = (req.body.name || '').trim(); turns a missing name into an empty string, so one if (!name) catches both cases. The next id is Math.max(...tools.map((t) => t.id)) + 1, and req.body.category || 'Other' supplies the default.
