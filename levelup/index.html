Flexbox Layout

In Chapter 4, boxes either stacked on top of each other (block) or flowed along like words in a sentence (inline). That works for an article, but not for a navigation bar, a row of cards, or a button you want dead center. Flexbox is the CSS layout mode built for exactly that.

Flexbox lays out items in one direction at a time, a row or a column, and decides how to share the space between them. You switch it on for a parent element with display: flex. That parent becomes the flex container, and its direct children become flex items. After that, you only need two ideas:

  • The main axis runs the way the items are placed: left to right for a row, top to bottom for a column. justify-content spaces items along it.
  • The cross axis runs at a right angle to it. align-items lines items up along it.

Change the container settings, then click an item to give just that item its own settings. Watch the axis arrows: switch to a column and the main axis turns with it.

Growing, shrinking and the flex shorthand

Every flex item has three sizing properties. flex-basis is its starting size. flex-grow is its share of any leftover space. flex-shrink is how much it gives up when there isn't enough room. The default is flex: 0 1 auto: don't grow, allow shrinking, start at the content's size.

You will usually write the shorthand. flex: 1 means 1 1 0%: start from zero and share all the space equally, which is how you get equal columns. Try the Equal columns and Sidebar + content presets above and read the generated CSS.

Centering, solved display: flex; justify-content: center; align-items: center; on a parent centers its child both ways. Give the parent a height (for example min-height: 100vh) if you want it centered on the whole screen.
order is only visual Screen readers and the Tab key still follow the HTML order. If the order matters for meaning, change the HTML instead of using order.

CSS Grid

Flexbox thinks in one direction at a time. CSS Grid thinks in rows and columns at once, which makes it the tool for whole-page layouts, photo galleries and dashboards.

With Grid, the container does the planning. You describe the column and row tracks, and the children drop into the cells in order, left to right and top to bottom. The lines between tracks are numbered, starting at 1, so you can also tell an item exactly where to go.

A few pieces of Grid vocabulary do most of the work:

  • fr is a fraction of the leftover space. In 1fr 2fr, the second column gets twice as much as the first.
  • repeat(3, 1fr) is shorthand for 1fr 1fr 1fr.
  • minmax(150px, 1fr) means "never narrower than 150px, but grow to share the space."
  • repeat(auto-fit, minmax(200px, 1fr)) means "as many columns of at least 200px as fit." That is a responsive grid with no media query at all.
  • Negative line numbers count from the end, so grid-column: 1 / -1 spans the full width no matter how many columns there are.

Type any track list or pick a preset. The numbered tags mark the grid lines you use with grid-column and grid-row. Narrow the container to watch fr, minmax() and auto-fit react.

Flexbox or Grid?

They are partners, not rivals, and real pages use both. A good rule of thumb: if you are lining things up in one direction and letting their content decide their size, reach for Flexbox. If you want items to line up in rows and columns at the same time, reach for Grid. The page skeleton is often Grid, and the header inside it is often Flexbox.

Responsive Design

Your visitors use phones, tablets, laptops, huge monitors, even TVs and folding phones. Responsive web design means one site, built from one set of HTML, whose layout adapts to whatever screen it lands on.

Web designer Ethan Marcotte coined the term in 2010 and named its three ingredients. They are still the core of the job today:

1. Fluid grids

Size layout columns with relative units such as %, fr and minmax() instead of fixed pixels, so they stretch and shrink with the screen.

2. Flexible images

img { max-width: 100%; height: auto; } keeps images inside their container. srcset lets the browser download a right-sized file.

3. Media queries

@media (min-width: 900px) { … } applies rules only when a condition is true, such as the screen being at least 900px wide.

Because one codebase runs everywhere, a responsive site is already a cross-platform application: you don't build a separate phone site and desktop site. You can go further. Add a web app manifest and a service worker, and your site becomes a progressive web app (PWA) that people can install to a home screen or desktop and that keeps working offline. Tools such as Electron (used to build desktop apps like VS Code) and Capacitor (mobile apps) wrap the same HTML, CSS and JavaScript into installable native apps.

Think mobile-first

Write your base CSS for the smallest screen, usually a single column. Then add min-width media queries that layer on changes as space grows. Phones download and apply the least CSS, and you design for the hardest case first. The widths where your layout changes are called breakpoints; choose them where your content starts to look stretched, not to match particular devices.

Modern browsers also understand the newer range syntax, @media (width >= 600px), which means the same thing as (min-width: 600px).

    The viewport meta tag

    The first smartphones had to show websites built only for desktops. So mobile browsers pretend the screen is about 980px wide, lay the page out at that width, and zoom out to fit. That means tiny text, and your phone-sized media queries never fire. One line in the <head> switches that behavior off. Put it in every page you build.

    Responsive images, tables and forms

    Images. max-width: 100% and height: auto stop an image from ever overflowing its box. Also give every <img> width and height attributes so the browser can reserve the right space before the file arrives (no jumping page), and add loading="lazy" to images further down the page so they only download when needed.

    A 2400px photo is wasted on a 390px phone. With srcset you list several sizes of the same image, and with sizes you tell the browser how wide the image will be displayed. The browser then does the math and downloads a sensible file.

    JavaScript Fundamentals

    HTML is the structure, CSS is the presentation, and JavaScript is the behavior: menus that open, forms that check themselves, content that updates without reloading the page.

    JavaScript is a full programming language, and every browser has a JavaScript engine built in (V8 in Chrome and Edge, SpiderMonkey in Firefox, JavaScriptCore in Safari).     A quick tour of the language

    Click through the tabs. Each one is a small piece of JavaScript you'll use constantly. Paste any example into the warm-up playground above to run it.

    A variable is a named box for a value. Use const by default; switch to let only when the value needs to change. Avoid the old var: it ignores block scope and causes confusing bugs.

    Every value has a type. JavaScript figures it out for you, and typeof tells you what it decided.

    Math works as you expect, plus % (remainder). Watch out: + also joins strings, and it wins whenever either side is a string.

    Template literals use backticks and ${…} to drop values into text. Strings also come with handy methods.

    if runs a block only when a condition is true. Conditions are checked top to bottom and the first true one wins.

    Loops repeat code. Use for...of to visit every item in an array, and the classic for when you need a counter.

    A function is a reusable, named recipe. It takes inputs (parameters) and can hand back an output with return. Arrow functions are a shorter way to write the same thing.

    Arrays hold ordered lists (counting from 0). Objects hold named properties. Real data is usually an array of objects.

    The DOM and Events

    When the browser reads your HTML, it doesn't keep the text around. It builds the Document Object Model (DOM): a tree of objects, one for every element and piece of text, that JavaScript can read and change while the page is open.

    The tree starts at document. Each element is a node with a parent, children and siblings, exactly like the nesting you practiced in Chapter 3. Change a node and the browser updates the screen immediately; no reload needed. That is how every interactive page works: find an element, listen for something the user does, then change the DOM in response.

        1. You click the ★ button inside a list item. The browser creates one click event object, and event.target is the button: the element where it started.

        2. Capture phase. The event travels down from window through document, body, ul and li toward the target. Listeners added with { capture: true } run on the way down. Most code never needs this.

        3. Target phase. Listeners on the button itself run.

        4. Bubble phase. The event travels back up: li, ul, body, document, window. Ordinary addEventListener listeners on those ancestors run now, in that order. Inside each one, event.currentTarget is the element whose listener is running, while event.target is still the button.

        6. event.stopPropagation() ends the trip early, and event.preventDefault() cancels the browser's default action (following a link, submitting a form). They are different things.         Library or framework?

        The two words get mixed up constantly, but there's a useful difference, often summed up as "you call a library; a framework calls you." A library is a toolbox: your code stays in charge and calls its functions when it wants. A framework is a skeleton: it decides the structure and when things run, and you fill in the pieces it asks for. (React calls itself a library, but most real React apps are built with a framework on top, such as Next.js.)

        Why frameworks exist: thinking in components

        In L.5 you changed the DOM by hand: find the element, patch it. That's perfect for small pages. In a big app, with hundreds of pieces of data and dozens of ways to change them, keeping every element in sync by hand gets messy fast. Frameworks flip the approach. You write components, functions that turn data into UI, and when the data changes you re-render. Here is the idea in plain JavaScript, no framework needed:

        Version control with Git and GitHub

        Git is a version control system: it records snapshots (commits) of your project so you can see what changed, when and why, and roll back mistakes. GitHub is a website that hosts Git repositories online, so your work is backed up, shareable, and can be reviewed by teammates. You'll use both for the course project.

        Working directoryThe files you edit index.html (modified) + teammate's changes
        Staging areaChanges picked for the next commit index.html
        Local repositoryThe .git folder: your history empty history ● "Add responsive nav"
        GitHub (remote)The online copy ● "Add responsive nav" Pull request #1 ● teammate's commit

        1. git init turns a folder into a repository by creating a hidden .git folder that will store every snapshot. (On GitHub, you can also create the repository first and git clone it.)

        2. You edit index.html. git status now lists it as modified. Nothing is in the history yet.

        3. git add index.html stages the change: you choose exactly what goes into the next snapshot.

        4. git commit -m "Add responsive nav" saves a snapshot with a message that explains why. Commit small and often.

        5. git push uploads your commits to GitHub, where they're backed up and visible to your team (and to GitHub Pages).

        6. For a bigger change, work on a branch (git switch -c dark-mode), push it, and open a pull request on GitHub. Teammates review and discuss the changes, and when everyone agrees, it's merged into main.

        7. git pull downloads commits your teammates pushed and merges them into your copy, so you're always working on the latest version.

        DevTools, validators and AI assistants

        Your browser's DevTools are the most important tool on this page, and they're free and already installed. Elements shows the live DOM and lets you edit CSS on the fly. Console shows errors and runs JavaScript. Network shows every request (Chapter 2 in action). The device toolbar (Ctrl+Shift+M, or Cmd+Shift+M on a Mac, in Chrome) previews phone and tablet widths, and Lighthouse audits performance and accessibility. Pair them with the W3C Markup Validation Service to catch invalid HTML.

        AI coding assistants Tools such as GitHub Copilot, ChatGPT, Claude and Cursor can explain an error message or draft code. Follow your course's policy on when you may use them and how to disclose that you did. Never hand in code you can't explain line by line: it's your name on it, and the fundamentals on this page are exactly what you need to judge whether the AI got it right.
