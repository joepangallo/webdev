Final Project: Build a Website

Build one multi-page website about a topic you choose and publish it on the web with GitHub Pages. The project grows with the class: it covers Chapters 2 to 5 so far, and new requirements are added here as we cover new chapters.

What you build
One website with at least four pages, a data table and a form
Where it lives
A public GitHub repository, live on GitHub Pages
What it covers
Chapters 2 to 5, and each new chapter as we cover it
What you submit
Your GitHub repo link

The project

You will build a real website: several pages that link to each other, share one look, show some data in a table and invite visitors to fill in a form. It lives in a public GitHub repository and GitHub Pages publishes it for free, so anyone with the address can visit it.

Why one site instead of separate exercises? Because each chapter adds a layer to the same thing. Chapter 2 puts it on the web, Chapter 3 gives it structure, Chapter 4 gives it a look, and Chapter 5 adds a table and a form. At the end you have one piece of work that shows everything you have learned, at an address you can share.

The project grows with the class It only uses material we have covered, which right now is Chapters 2 to 5. When we cover a new chapter, a new group of requirements is added to this page and you apply it to the same site. Nothing you build now gets thrown away.

Choose a topic

Pick something you know or care about. You will write real content for it, and that is much easier when you like the subject. A good topic naturally has three things:

  • Enough for 4 or 5 pages. A home page plus three or four pages with a clear job each.
  • Some data that belongs in a table. Prices, a schedule, stats, ratings: anything with rows and columns.
  • A reason for a visitor to fill in a form. An order, a sign-up, a question, a review.

Requirements

Each group below is what one chapter adds to your site. The links under each heading go to the chapter sections that teach those skills, so if an item looks unfamiliar, start there.

Chapter 2 · How the Web Works

Put it on the web

Taught in 2.3 Uniform Resource Locators and 2.6 Web Servers

  • A public GitHub repository for your site, with index.html at the top level of the repository, not inside a folder. When someone visits your site's address without a file name, the server sends index.html.
  • File and folder names in lowercase with no spaces, such as menu.html and images/food-truck.jpg. Use hyphens between words. Web servers treat Menu.html and menu.html as two different files, and a space has to be encoded in a URL.
  • A css/ folder for your stylesheet and an images/ folder for your images.
  • The site is live on GitHub Pages, and every page loads from its https://your-username.github.io/your-repo/ address.
  • Relative links only for your own files: about.html, css/styles.css, images/logo.png. No paths that start with /, and no file:/// or C:\ paths. Your live site sits in a folder named after your repository, so a path that starts with / jumps to your-username.github.io and misses your files. A file:/// path only exists on your own computer.
Chapter 3 · HTML 1: Introduction

Give it structure

Taught in 3.3 Semantic Markup, 3.4 Structure of HTML Documents, 3.5 Quick Tour of HTML Elements and 3.6 HTML5 Semantic Structure Elements

  • At least 4 pages, all linked from the nav. The thank-you page for your form is extra and does not count toward the four.
  • Every page is a complete document: <!DOCTYPE html>, <html lang="en">, <meta charset="utf-8">, the viewport <meta>, a <title> that is different on every page, and a <meta name="description">.
  • <header>, <nav>, <main> and <footer> on every page, with the same nav on every page. Landmarks let screen reader users jump straight to the menu or the content, and a nav that never moves means visitors never get lost.
  • One <h1> per page and no skipped heading levels: the subsections of an <h2> are <h3>s, not <h4>s.
  • Lists (<ul> or <ol>) wherever the content really is a list, including the nav links.
  • Images with meaningful alt text, plus width and height set to the image's real size in pixels. Use alt="" only for a purely decorative image. Alt text is what a screen reader reads aloud and what shows if the image fails to load. Width and height let the browser save space for the image, so the page does not jump as it loads.
  • At least one <figure> with a <figcaption>.
  • <section>, <article> and <aside> where they fit the content.
  • Real content you wrote yourself. No lorem ipsum and no leftover placeholder text.

Chapter 4 · CSS

Give it a look

Taught in 4.2 CSS Syntax, 4.3 Location of Styles, 4.4 Selectors, 4.6 The Box Model, 4.7 CSS Text Styling and 4.8 CSS Frameworks and Variables

  • One external stylesheet, css/styles.css, linked from every page with <link rel="stylesheet" href="css/styles.css">. No <style> blocks and no style="…" attributes. One file styles every page, so one change updates the whole site.
  • Custom properties in :root for your colors, fonts and spacing, used everywhere with var(--…). When you change your brand color, you change it in exactly one place.
  • Font stacks that end with a generic family, such as Georgia, "Times New Roman", serif. If a visitor does not have your first choice, the browser moves along the list instead of falling back to its default.
  • box-sizing: border-box on every element, a readable max-width for your content (roughly 45 to 75 characters per line), and deliberate spacing: padding inside boxes, margins between them.
  • A styled nav that looks like a menu, with a :hover state, a :focus-visible state for keyboard users (5.6 Styling and Designing Forms) and a style for the current page.
  • At least five selector types from this list: element, class, id, descendant or child, attribute, pseudo-class.
  • Text contrast of at least 4.5:1 against its background, including links and button text. Low-contrast text is hard for everyone to read, and impossible for some visitors.

For layout, use what Chapter 4 covered: block and inline-block boxes, padding and margins, and a max-width with margin: 0 auto (or margin-inline: auto) to center a column. That is all this project needs.

Chapter 5 · HTML 2: Tables and Forms

Add a table and a form

Taught in 5.1 HTML Tables, 5.2 Styling Tables, 5.3 Introducing Forms, 5.4 Form Control Elements, 5.5 Table and Form Accessibility and 5.7 Validating User Input

  • One data table with real or realistic data, at least 5 rows and 3 columns. Tables are for data, never for page layout.
  • The table has a <caption>, a <thead> and a <tbody>, and <th> header cells with scope="col" (and scope="row" on row headers). Scope tells a screen reader which header goes with each cell, so a visitor who cannot see the table still knows what "$4.50" is the price of.
  • The table is styled (padding, borders or zebra rows) and wrapped in an element with overflow-x: auto, so on a phone it scrolls inside its own box instead of widening the page.
  • One form with a visible <label> for every control, connected by matching for and id. A placeholder is not a label.
  • At least one <fieldset> with a <legend>. Every group of radio buttons needs one.
  • Input types that fit the data: email, tel, number, date, radio buttons, checkboxes, <select>, <textarea>. The right type gives phone users the right keyboard and gets you free checking, such as "that is not an email address".
  • A name on every control. The browser only sends values from controls that have a name.
  • Built-in validation where it fits the data: required, min and max, minlength, pattern. Test it by trying to submit bad data.
  • action="thanks.html" and method="get", plus a thanks.html page that thanks the visitor. GitHub Pages is a static host: it only sends files and has no program to receive form data, so it cannot accept a POST. With GET, the browser simply asks for thanks.html with the answers in the query string, and GitHub Pages can serve that.

Every chapter · Quality

Make it solid

The Nu Html Checker is introduced in 3.1 What Is HTML and Where Did It Come From?

  • Every HTML page passes the W3C Nu Html Checker with no errors.
  • css/styles.css passes the W3C CSS Validator with no errors. Browsers quietly repair or skip your mistakes, so a page can look fine in one browser and break in another. The validators show you every mistake, with a line number.
  • Works at phone width with no sideways scrolling of the page. To test it in Chrome, open DevTools and turn on the device toolbar (Ctrl+Shift+M, or Cmd+Shift+M on a Mac).
  • Credit every image you did not make: who made it and where it came from, with a link. Put credits in the footer or on a credits.html page.

How to build it

Start from the starter files or from scratch

The course has a small, valid three-page starter site you can copy: starter/index.html, starter/about.html, starter/contact.html and starter/css/styles.css. It already has a complete page skeleton, a shared nav and a stylesheet organized with comments. Copy those files, plus starter/images/placeholder.svg, into the same folders in your repository, then rename, rewrite and add pages until the site is yours. Every placeholder has to go, including that image.

Or start with an empty folder and write every line yourself. It is slower, but you will understand every line. Either way is fine.

Build it as we go

Do not save the project for the end. After each chapter, apply that chapter to your site and push it. Small steps are easier to fix when something breaks, and your site is always live and working.

Create the repository and publish it

  1. On github.com, create a new repository. Make it Public and give it a short lowercase name, such as corner-cup-coffee.
  2. Clone it to your computer, add your files, and send them back to GitHub:
  1. On GitHub, open your repository's Settings, then Pages. Under Build and deployment, choose Deploy from a branch, pick the branch main and the folder / (root), and press Save.
  2. After a short wait, refresh the Pages settings. Your address appears at the top, for example https://your-username.github.io/corner-cup-coffee/. Open it in a private (incognito) window to be sure you are not seeing an old copy.
  3. From then on, every time you finish a piece of work: git add ., git commit -m "…", git push. GitHub Pages republishes your site on every push.
Commit often Commit every time something works: a new page, a finished table, a fixed validator error. Each commit is a snapshot you can go back to, and messages like "Add menu table" tell the story of how you built the site. For a picture of how add, commit and push fit together, see Version control with Git and GitHub in Frameworks and Developer Tools.
If Git asks who you are, or asks you to sign in

The first time you commit on a computer, Git may stop and ask for your name and email. Run the two git config commands it shows you, using your name and the email address of your GitHub account, then commit again.

The first time you push, GitHub may ask you to sign in, usually in a browser window. Follow the prompt. If you would rather use buttons than the terminal, GitHub Desktop or your editor's Source Control panel runs the same add, commit and push steps.

A warning that you "appear to have cloned an empty repository" is normal for a brand-new repository.
